# Project Rules

How to work on this project. One short rule per line. These OVERRIDE default behavior.

> The rules that must fire **without anyone opening a file** stay in [CLAUDE.md](CLAUDE.md) and are deliberately NOT repeated here: the purpose and the evidence ladder, the seamless-for-the-consumer and backwards-compatibility directives, the pre-merge/pre-release gate commands, the support-surface docs checklist, the **C# coding conventions**, the git commit conventions, and the no-local-memory directive. Every rule has exactly one home.

## Never

- Never swap in a substitute compiler to make a host work; a different compiler means different output and silently breaks the mgfxc-equivalence promise.
- Never fork or own compiler internals; fail loudly, patch minimally and reversibly on our side of the boundary (the `D3d9BytecodePatcher` pattern), and record an upstream-fix follow-up.
- Never bump a pinned native version casually; pins exist because output byte-stability is a product promise, and a bump re-baselines every golden and re-runs rung 4.
- Never commit native binaries; they are restored, pinned, and hash-verified.
- Never bump `Silk.NET.SPIRV.Cross.Native` (or `Vortice.Dxc`) without moving the Android build to the same compiler: measure which SPIRV-Cross commit the new desktop BINARIES contain (not the package's submodule pointer; see `project_facts.md`), set it in `tools/build-spirv-cross-android.sh`, rebuild with `spirv-cross-android-build.yml`, host the files under a new tag and re-pin; the emulator lane's on-device corpus check must stay 50/50.
- Never take on a native dependency that has no Linux and macOS build; prefer a pinned prebuilt GitHub Release artifact, and fall back to building and hosting it ourselves.
- Never destroy a background agent's uncommitted output; commit or copy out first, clean up last, and verify a "done" claim by re-running its gate rather than trusting an estimate. (operator)
- Never add a `PackageVersion` **property** to a csproj; the ShadowDusk version lives only in `Directory.Build.props`.

## Testing and validation

- A green `dotnet test` is necessary but NOT sufficient for any change to shader output, transpilation, the MGFX/KNIFX/FNA writers, render state, or matrix handling; the render gates in CLAUDE.md are the other half of the bar.
- Run the full `dotnet test ShadowDusk.slnx`, never a filtered subset, when touching the parser, pre-parser, writers, or render state; a whole class of valid HLSL can fail to compile while every test you happened to run stays green (this is how issue #106 escaped).
- Every fixed bug earns a permanent regression fixture or test so it can never silently return.
- Testing gaps get closed, not noted (owner directive). A change that shows something needs more coverage adds that coverage in the same PR. When something cannot be tested because no harness exists (a native that only runs on one host, a runtime with no headless driver), raise it to the owner loudly before shipping, never as a quiet "unverified" line in a doc. A check that only runs by hand on the owner's machine is itself a gap to close by building the CI lane (software rasterizers: llvmpipe for GL, WARP for D3D, lavapipe or SwiftShader for Vulkan), never a request for the owner to run it.
- A test that cannot fail is worse than no test: a soft-skip reported as PASS is indistinguishable from real coverage. `SHADOWDUSK_REQUIRE_GL` exists because headless ImageTests soft-skipped as passes and masked three latent failures, including a GLFW registration race on real Windows hosts.
- A corpus that cannot see a bug class proves nothing about it: PS-only, matrix-free, modern-syntax-only corpora hid issue #70 and issue #145 entirely. Widening the corpus is part of the fix, not a follow-up.
- A diagnostic test that does not assert the line and column is not testing the location contract: every FNA test asserted the file and the message while vkd3d's coordinates drifted by 581 lines on a real shader (issue #202). Plant a known construct at a known line behind known drift and assert the exact `(File, Line, Column)`.
- Measure what the reference compiler emits before recording that it does or does not do something: compile the one-liner with `fxc /T ps_3_0` (or `mgfxc`) and read the assembly. Rule 16 first shipped without `tan` on the unmeasured claim that fxc has no D3D9 `tan` to mirror, and that claim was written into two docs; fxc in fact lowers `tan` to the same range reduction plus `sincos` (issue #215).
- A cancellation test that passes an already-cancelled token only proves the ENTRY check: every backend throws at the top of `Compile`, so the test stays green with any later check deleted. To pin a check that sits between native calls, cancel from inside the run (a fake probe for pure code; the `onNativeCallReturned` seam of `Vkd3dShaderCompiler.CompileCore` for real vkd3d) and assert how many calls were made (issue #255).
- A test never rewrites a tracked file during a normal run: it compares and FAILS on drift, naming the lines that moved and how to regenerate (issue #361; a full `dotnet test` used to rewrite `plan/PHASE-41-appendix/structural-divergence-matrix.md`, so adding a fixture dirtied the tree). After any test run, `git status` must be clean. The generated file holds nothing tied to the host or the version (the assembly-version stamp it once carried changed on every release). To regenerate the Phase 41 appendix after a fixture or compiler change, run `SHADOWDUSK_REGENERATE_PHASE41_APPENDIX=1 dotnet test tests/ShadowDusk.Integration.Tests --filter FullyQualifiedName~Phase41StructuralDivergenceMatrixTests` (PowerShell: `$env:SHADOWDUSK_REGENERATE_PHASE41_APPENDIX='1'` first), review the diff (a moved cell is a real signal) and commit it with the change that caused it.
- Scripts bash or a shebang runs (`*.sh`, `*.bash`, `*.py`) are `eol=lf` in `.gitattributes`, and a test runs the checked-out script, never an LF-converted copy (issue #357). A checkout older than an `eol=lf` rule keeps CRLF copies until they are deleted and re-checked-out (see `project_facts.md`); `ScriptLineEndingTests` names them.
- Never append a path to `$(NuGetPackageRoot)` directly: with a custom `NUGET_PACKAGES` or `globalPackagesFolder` it has no trailing slash. Wrap it in `$([MSBuild]::EnsureTrailingSlash('$(NuGetPackageRoot)'))`; `NuGetPackageRootUsageTests` scans every project file for this (issue #362). Code and scripts that locate the global-packages folder read `NUGET_PACKAGES` before falling back to `~/.nuget/packages`.
- Unit tests stay pure (no disk, no process); integration tests are tagged `[Trait("Category","Integration")]`.
- **Assertions use Shouldly. `FluentAssertions` is banned** (issue #171) — a licence obligation, not a style preference; see `project_facts.md`. Never add the package back and never write `.Should()`, including in a new test file where it would be the reflexive thing to type. Two Shouldly gotchas the migration paid for: string `ShouldContain`/`ShouldNotContain` default to **case-insensitive**, so pass `Case.Sensitive` explicitly on every string receiver; and `ShouldBe(…, ignoreOrder: true)` compares with `Equals`, so reference types without value equality need `ShouldBeEquivalentTo`.
- No `Thread.Sleep` in tests; use `CancellationToken` with reasonable timeouts.
- A test starts a child process only through `ChildProcess` (`tests/ShadowDusk.Integration.Tests/ChildProcess.cs`; `CliProcess` for the CLI), never a hand-rolled `Process.Start`. Reading stdout to the end before stderr deadlocks on a child that fills the stderr pipe first, and a bare token timeout reports only a cancellation while the child keeps running. The helper drains both pipes concurrently, kills the process tree, and fails with the elapsed time, the command line, the child's CPU time and thread states, the output so far and a pre-kill dump (issue #316).
- CI's `--blame-hang-timeout` and `TestSessionTimeout` change together: session timeout >= slowest healthy assembly run + blame timeout + dump time + 1 minute of slack. The blame timer is reset by every test that starts or finishes, so it fires that long after the LAST test event, while the session timeout is absolute and leaves no dump; a session cap that is too close turns every late stall into an undiagnosable abort (issue #312). `CiHangGuardTests` fails when the pair stops agreeing.
- **Integration lane load (issues #373, #316, #351).** CI's integration step runs `dotnet test -m:2`: at most two test hosts at once. With one host per assembly and TFM (four at once on a 4-vCPU runner) the Windows run queue sat at 20 to 60 and one host at a time made no progress at all for 40 to 176 s, blocked starting new threads (a blame dump of one: a thread in `Thread.StartCore` and every native compiler idle; xUnit v2's default `conservative` algorithm starts a new OS thread for every `await` continuation in a test, so a host whose thread starts are starved stops completing tests). Every 30 and 60 s budget that expired on Windows was a test inside such a stall, never a slow or stuck compile. Do not raise `-m` and do not switch xUnit to `aggressive` (measured on 4 pinned cores: aggressive pushed the slowest test from 95 s to 185 s; `-m:2` cut it to 34 s at the same wall time) without re-measuring the gaps below.
- **The unit lane (`Build & Test`) does not show the stall and stays at full parallelism** (measured 2026-10-04 from every `test-results-<os>` `.trx` of 93 CI run attempts per lane, 2026-10-01 to 2026-10-04). Longest stretch with no test event in one host: windows-latest 18 s (always at host start-up, never mid-run), ubuntu 13 s, macOS 7 s; slowest passing test 12 s on Windows (`NativeCompileStackTests`), 3 s on ubuntu, 6 s on macOS; slowest assembly run 34 s. Its tests are short and spawn no slangc or CLI children, so four hosts at once never starve one for long. Re-measure the same way before adding heavy tests to that lane, and give it `-m:2` if a mid-run gap passes 30 s.
- **A test's compile budget is `TestBudget.Compile` (3 minutes), never a hand-picked 30 or 60 s** (`tests/ShadowDusk.Integration.Tests/TestBudget.cs`, linked into the other test assemblies). It only fails one test that is far slower than it should be while the rest of the assembly runs on; `--blame-hang-timeout` is the hang guard, and a budget shorter than it buys nothing. A cancelled compile's `OperationCanceledException` already names the native call that took the time and what else was in flight, so read that message before raising anything.
- **`--blame-hang-timeout 3m` headroom (issue #351), measured from every integration `.trx` on CI.** The blame timer is an inactivity timer, so what it must clear is the longest stretch in which one healthy host records no test event, not the slowest test. Before `-m:2` (74 run attempts per lane, 2026-10-02 to 2026-10-03): windows-latest 176 s (1.02x headroom, a near miss; slowest test 155 s), ubuntu 39 s (slowest test 166 s), macOS 42 s (slowest test 103 s). After `-m:2` (5 run attempts per lane of PR #376, 2026-10-04, all green): windows-latest 22 s (8.2x headroom; slowest test 67 s), ubuntu 28 s (6.5x; slowest test 67 s), macOS 34 s (5.3x; slowest test 149 s, `SlangRoute_Bytes_MatchCommittedManifest`, which has no per-test budget, on a runner instance that was slow across the board); the slowest test under `TestBudget.Compile` was 67 s (2.7x), and the slowest assembly run 5 min 32 s (macOS, Slang), which is why `CiHangGuardTests` assumes 6 minutes and the session cap is 11 (6 + 3 min blame + 1 min dump + 1 min slack, which the test now requires; the blame dump is `full`, 378 MB and 1.2 s for an Integration host with DXC loaded, measured locally, because a mini dump gives `dotnet-dump` no managed stacks). Re-measure (`gh run download` the `integration-results-<os>` artifacts and take, per `.trx`, the largest gap between consecutive test start/end times, counting from the run's start) whenever a slow test is added or the lane's parallelism changes, and keep the worst gap under half the blame timeout.
- Treat a slow integration run as environmental (antivirus scanning cold natives) before treating it as algorithmic; see `docs/integration-test-performance.md`.
- A dump of a stalled test host is taken from OUTSIDE the process (CI's `tools/ci/hang-watchdog.sh`), never trusted to `--blame-hang-timeout` alone: the blame timer is reset by every test that keeps running around the frozen ones, and the runtime dumps itself by `fork()`ing createdump, which the very lock that caused the stall can block (issue #312, measured). Read the sidecar's lldb/gdb stacks and the host's `host-hint-*.txt` before theorizing.
- Never make a `fork()` wait for a DXC compile (an atfork handler that blocks on compiles in flight): libSystem hands the handler dyld's dlopen lock, and a `-Zi` SPIR-V compile `dlopen`s from inside DXC (issue #312). The gate covers one locale-changing preprocess and nothing else; `DxcSetlocaleAudit`'s steady-state half is the premise that keeps the compiles ungated.

### A green PR with `skipping` jobs is NOT a green PR (learned the hard way, PR #170)

The heavyweight CI jobs are label-gated, so the default PR run comes back all-green while silently skipping them. Merging on that is how an unverified change ships.

- **`Pack & Consume` is the one that bites.** It is gated on the **`run-integration`** label **and has NO push-to-main trigger** (only a weekly cron), so *merging does not run it either*. It is the only check that proves the NuGet packages actually pack and a cold consumer can install and use them, and its own header calls it "the check that would have caught the 0.2.0 disaster". **Apply the label on any PR that changes packaging, TFMs, project files, or natives.**
- The labels: **`run-integration`** (cross-OS integration tests + Pack & Consume), **`run-validation-render`** (GL render gates on ubuntu/Mesa llvmpipe), **`run-browser`** (browser render smoke + WASM), **`run-win-arm64`** (`win-arm64.yml`: native win-arm64 vs win-x64 byte identity of the core pipeline, and `ShadowDusk.Slang`'s `SD0620` there; apply it on any change to natives, packaging, or the DXC/SPIRV-Cross load path), **`run-android`** (`android-emulator.yml`: the on-device compile + `Effect` load and the Android DXC / SPIRV-Cross identity checks on an API-34 x86_64 emulator; apply it on any PR that touches the DXC or SPIRV-Cross loaders, `ElfImages`, `validation/AndroidGl` or the Android restore pins). `android-emulator.yml` also listens to `labeled`, so adding `run-android` starts it at once.
- **Adding a label does not retrigger anything** (except `android-emulator.yml`, which listens to `labeled` and starts when `run-android` itself is added; any other label is ignored there). Those workflows listen only to the default `pull_request` types (`opened`/`synchronize`/`reopened`), not `labeled`, so the job `if:` was already evaluated on the earlier run. **`gh run rerun` does not help either** - it replays the original event payload, which had no labels.
- **To make them run:** push another commit (fires `synchronize`), or `gh pr close && gh pr reopen` (fires `reopened` with the labels present, no fake commit). `pack-consume.yml` additionally accepts `workflow_dispatch`, so it can be dispatched directly against the branch.
- **Close/reopen works; check before concluding it did not** (issue #258, measured on PRs #235, #241, #246, #248). After a reopen, `gh run list --branch <b>` shows the new runs within seconds and `Pack & Consume` runs instead of skipping. Two things make it look broken: pushing a commit right after the reopen cancels the reopened runs through the workflow concurrency group (PR #248's "retrigger" empty commit, 13 s later, did exactly that), and GitHub starts no `pull_request` run at all on a PR with a merge conflict (PR #239's reopen fired nothing and the branch was rebased minutes later). Rebase first if `gh pr view --json mergeable` says `CONFLICTING`.
- `vkd3d export gate (standing)` is push-to-main + schedule only. It cannot run on a PR by design; it fires after the merge. Its local equivalents are `node-test-vkd3d-wasm.mjs` and `browser-vkd3d-gate.mjs`.
- Read the check list, not just the overall verdict: count `skipping` and decide whether each one matters for what you changed.
- **A dependency or lock-file change gets ALL THREE labels before merge** (learned on PR #279, issue #291). Changing a package version or range in `Directory.Packages.props` stales the `packages.lock.json` of projects OUTSIDE `ShadowDusk.slnx` too (`tests/ShadowDusk.BrowserTests/*`, `validation/*`), and only the label-gated jobs restore those. PR #279 merged green with Browser render smoke skipped and broke it on main. Before merging such a change, run `tools/check-lock-files.sh` (a locked-mode restore of every tracked lock file; the `Lock files` CI job runs it on every PR, but it SKIPs the Android and FNA projects when their prerequisites are absent, so run it locally too). Regenerate a stale one with `dotnet restore <project> --force-evaluate`, and only on a box with its out-of-tree sources restored (`validation/FnaValidation/external/FNA`), or the lock silently loses that project reference.
- **Deep validation runs BEFORE merge, not after.** On 2026-10-01 one review pass per PR ran before merge and the deeper post-merge validation (rebuilding the pre-change tree, probing edge shapes, real-engine checks) found six regressions that had already landed (#263, #267, #279). For a change to shader output, native loading, packaging or a new rewrite rule, get an independent adversarial review that reproduces the claims, and fix what it finds, before merging. Parallel PRs touching the same files (CHANGELOG, project_facts, lock files, the Slang compiler) must each be re-verified after merging main into them.

## Docs and phases

- Read `plan/plan.md` first for phase status; each phase's own doc is the detail.
- Keep XML doc-comments on the public API accurate; they render into the published API reference, so a stale "not yet implemented" ships to the site.
- When a phase completes, move its doc and appendix to `plan/DONE/` and fix relative links in the moved doc and in every referrer.
- Update the phase index row in `plan/plan.md` in the same commit as the status change.
- Add the change to the `[Unreleased]` section of `CHANGELOG.md` in the same PR.
- Regenerate `docfx/images/pipeline-overview.svg` whenever `docs/pipeline-overview.puml` changes; the site embeds the SVG, so an un-regenerated SVG silently ships the old diagram.
- `docs/validation-matrix.md` is the living tracker: update the cell and its date whenever evidence changes, and give every new `validation/*` driver a §6 row with its exact run command.
- Keep `.claude/skills/` and `.claude/agents/` current when paths or conventions change.

## Working practice

- While chasing a stated backend or target-completion goal, fix bugs found along the way instead of stopping to ask; only a genuine scope or backwards-compatibility question warrants a check-in. (operator)
- Work on a branch off `main`; commit or push only when asked.
- Before any loop where one iteration is slow (building a native from source, a long CI job), first search for an existing prebuilt artifact, then debug locally where an iteration takes minutes, and cache any one-time build keyed on its inputs. CI is where a fix is confirmed, not where it is debugged.
- **An issue is "ready for validation" only when nothing in it is left.** A handoff comment carrying a "still open" line, a fix that waits on another PR, or a remainder "tracked in #N" is not done: finish the remainder, or get the owner to re-scope it explicitly, before handing the issue to the person who filed it. On 2026-10-02 eight of one requester's issues went out as "ready" with such remainders (#215, #227, #230, #252, #255, #256, #257, #258), and their review the next day had to file a dozen follow-ups (#349 to #362).
- **Prove a requested feature on the requester's own inputs, not only on our proxy.** #197 (SkSL) shipped proven in desktop SkiaSharp, but the requester's consumer was Gum in XnaFiddle in the browser, and every one of its example shaders reads `COLOR0`: none converted until #349, #368 and #371. When an issue names a consumer, a sample set or a host, run those through the change before calling it done.
- **Fix the defect class, not the reported instance.** #270 closed the PATH hijack for the DXC loader and left the vkd3d and SPIRV-Cross loaders with the same bare fallback (#350); #263's register fix left the neighbouring shapes (combined `Sampler2D`, arrays, authored `s` registers) untested (#355, #356). Grep for the sibling call sites and test the adjacent shapes in the same PR.
- **A handoff starts from a clean full run:** `dotnet test ShadowDusk.slnx` finishes without a hang or a hand kill, and `git status` is clean afterwards. A suite that cannot finish, or that rewrites tracked files, hides the next regression (#345, #361).
- Size delegated work to one verifiable unit: one gate, one bug, one PR. A batch whose every step needs its own CI round stalls, and an unfinished batch leaves nothing mergeable.
- Don't run parallel agents on overlapping files (the same Slang sources, `validation-render.yml`, `CHANGELOG.md`); sequence them, or the second PR to merge has to be redone.
- Use `/release` to cut a release; `RELEASING.md` is the human runbook and the ground truth it follows.
- Bump the single `<Version>` line in `Directory.Build.props`, merge that PR to `main`, and only then dispatch `release.yml`; the workflow is dispatch-only and a pushed tag publishes nothing.
- Run the Windows render gate before bumping the version, not after: it is the longest and most likely step to fail, so a divergence should stop the release before any version churn.

## Handoff — leave nothing that only you know

The next person or agent starts with CLAUDE.md and these three files and nothing else. Anything you know that they do not is lost work. These rules exist because a check nobody remembers to run is the same as a check that does not exist.

- **A check that cannot run under `dotnet test` must be registered somewhere it will be found, or it will never run again.** Put it in `validation/run-windows-render-gates.ps1` if it can run there, and give it a `docs/validation-matrix.md` §6 row with its exact command either way. Adding the driver is not finishing the work.
- **If a check is deliberately opt-in or excluded** (needs hardware, a heavy restore, a specific OS), say so in its §6 row *with the reason and the exact opt-in flag* — an unexplained exclusion reads as "not needed" to the next reader.
- **Anything that must be refreshed at release time** (a regenerated artifact, a version-stamped doc, a manual verification) goes into `RELEASING.md` **and** the `/release` skill in the same PR that creates the need. Your memory is not a release step.
- **A new always-on obligation goes in CLAUDE.md, not in a phase doc.** Phase docs are read when someone works that phase; CLAUDE.md is read every session. If it must happen on *every* relevant change, it belongs in the support-surface checklist or the gate block.
- **Before ending a work session, write what you learned into these three files.** A fact you discovered, a rule you were corrected on, a choice you settled. If it only exists in the conversation, it is gone when the session ends.
- **When picking up unfamiliar work**, read `git log --oneline -20`, `CHANGELOG.md`'s `[Unreleased]` section, and `plan/plan.md`'s status rows before assuming the state of anything.

## Maintaining the three source-of-truth files

- `project_facts.md`, `project_rules.md`, and `project_decisions.md` are the only home for durable facts, rules, and decisions. Do not create memory files. Exceptions that stay separate: phase docs, user-facing docs and readmes, reference docs, temporary files.
- Update them in the same commit as the change that alters them.
- Edit in place and delete entries that become false; never append changelogs or dated progress notes, since history lives in git.
- When a conversation surfaces a new durable fact, a correction to behavior, or a resolved choice, write it to the right file immediately without being asked.
- Facts state what is true; rules state how to work; decisions state what was chosen and why. An entry with no rejected alternative and no reason is a fact, not a decision.
- Record only what reading the code cannot tell you; folder layout, file names, diagnostic codes, and format constants are derivable and belong in the code or `docs/repository-layout.md`.
- Never record per-target **proof status** in these three files; `docs/validation-matrix.md` is its only home (CLAUDE.md carries a cold-start summary table that the support-surface rule keeps in sync). Status changes as evidence advances, so a second copy always drifts.
