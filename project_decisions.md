# Project Decisions

Decisions made, with the why - consult before re-litigating anything. One per line: decided X (not Y) because Z.

## Pipeline and backends

- Chose the Option B pipeline (DXC -> SPIR-V -> SPIRV-Cross -> GLSL/MSL), not Option A (FXC/MojoShader), because Option A requires Wine on Linux and macOS and so cannot deliver the reach that justifies the project.
- Chose vkd3d-shader for the DX11 DXBC backend, not DXC, because DXC only emits SM6 DXIL and D3D11 rejects DXIL unconditionally; DXC's DXIL path is retained only for DX12 and KNI.
- Chose vkd3d as the shipping DXBC backend on every OS (default since 0.5.0), not `d3dcompiler_47`, because it makes output host-independent; `d3dcompiler_47` stays an opt-in Windows-only correctness oracle and never ships.
- Chose to pin vkd3d and treat a bump as a deliberate event, not to track upstream, because output byte-stability is a product promise and a bump re-baselines every golden and re-runs rung 4. Upstream's stubbed fx_2_0 writer stays a background watch, not a dependency.
- Chose to move the pin 1.17 → **2.1** (Phase 56, 2026-09-10) rather than stay put or take the researched 2.0. Issue #212 needed the SM2-3 loop support that landed in 2.0, and since the churn is paid once either way, 2.1 was taken for its SM1-3 dead-store-elimination pass, which brings the constant-table layout closer to `fxc`'s. Measured result: ten fixtures moved from failing to compiling on FNA with zero regressions, every DirectX and FNA byte moved, and OpenGL/Vulkan/DirectX 12 bytes were proven unchanged.
- Chose to stay on vkd3d 2.1 despite its slower optimizer on large branchy shaders (issue #255: the upstream Apos.Shapes pixel shader takes 5.3 s on 2.1 and 3.3 s on 1.17), not to roll back to 1.17. 1.17 cannot compile that same file for FNA at all, and it lacks the SM2-3 loops and the register allocator the pin was moved for. The mitigation that ships is a per-`Compile` memo of distinct vkd3d requests (`MemoizingDxbcCompiler`), which is output-neutral by construction. Compiling distinct entry points in parallel was deferred: it does nothing for the one-giant-pixel-shader case that motivated the issue, and vkd3d's thread safety under concurrent `vkd3d_shader_compile` calls has not been measured. The real fix is upstream.
- Chose to fix vkd3d 2.1's stricter SM4 semantic validation with the `MAP_SEMANTIC_NAMES` compile option rather than by widening `FxPreParser`'s `COLOR` → `SV_Target` source rewrite to struct fields. The rewrite cannot tell a pixel-shader output struct from a vertex-shader output struct, where `COLOR` is legal, so widening it would have been a per-shader guess; the option is what `fxc`'s own legacy behavior does and covers the whole class.
- Chose to pass the vkd3d compile options from the managed side through the JS shim into the WASM wrapper (`sdw_vkd3d_compile_options`), not to set them in the wrapper's C for the DXBC_TPF target (issue #295). A copy of the list in C is what drifted: the desktop gained `MAP_SEMANTIC_NAMES` and the wrapper kept passing none. With `Vkd3dCompileContract.ResolveCompileOptions` as the only owner, a future option reaches both hosts without rebuilding and re-hosting the module, and the wrapper has nothing to get wrong. The option-less `sdw_vkd3d_compile` export was removed rather than kept beside the new one, so a rebuilt module has no entry point that can compile without the caller's options.
- Chose our own pinned macOS `libdxcompiler.dylib` loaded via Vortice's `Dxc.ResolveLibrary` event, not `SetDllImportResolver`, because Vortice's assembly already registers a resolver and a second registration throws.
- Chose to load the pinned Windows `dxil.dll` + `dxcompiler.dll` (and Linux `libdxcompiler.so`) ourselves, by absolute path, before the first DXC call, and to refuse (`SD0219`) when they are missing, not to rely on Vortice's resolver or on name-based search, because DXC binds its validator by bare name at `DllMain` and any bare-name load reaches `PATH` (2026-10-01: the Windows SDK's `dxil.dll` broke every DX12 compile). A fallback to a DXC or validator found on the search path would be a substitute compiler. A foreign `dxil.dll` already in the process refuses only validated-DXIL (DirectX 12) compiles, not every DXC request: SPIR-V, `-Vd` and preprocessing never use it, refusing them would break targets that compiled correctly before and that the consumer cannot repair (seamless directive; review of PR #268). Identity is by file content, not path string. Our handler is inserted ahead of Vortice's in `Dxc.ResolveLibrary` by reflection on the event's backing field (falling back to `+=`), not appended after it, because Vortice's bare-name fallback can load a different DXC on Linux plugin hosts.
- Chose to identify the pinned vkd3d-shader and SPIRV-Cross files by SHA-256 of the file, checked before loading (issue #350), rather than by a build stamp like DXC's file version / build id / `LC_UUID`, or by SPIRV-Cross's own `spvc_get_commit_revision_and_timestamp` after loading. We ship (or pin through a locked NuGet version) the exact bytes, so the hash is the exact identity on every OS with one reader; the restore scripts already pin these hashes; and a post-load check would already have run a foreign library's initializers. Same RID-keyed rule as DXC: a file of another architecture is skipped, any other file refused. Also chose to delete the MGCB plugin's `ResolvingUnmanagedDll` fallback rather than keep it as a harmless last resort: the loaders now answer for these names themselves (a handle or a thrown refusal), so it was unreachable, and a resolver with no identity check is exactly the shape #350 removed.
- Chose a build warning (`SD0225`, buildTransitive in ShadowDusk.GLSL) for a consumer graph that resolves a `Silk.NET.SPIRV.Cross.Native` other than 2.23.0, not to tighten ShadowDusk.GLSL's dependency to the exact `[2.23.0]` range like Vortice.Dxc's (issue #350). The runtime refusal (`SD0103`) already guarantees no different SPIRV-Cross runs, and the warning names it at build time; an exact range would add `NU1608` but means re-locking every `packages.lock.json` for no change in what a consumer can do, and 2.23.0 is the newest release, so nothing can lift it yet. Same seamless rule as `SD0220`: DirectX 11/12, Vulkan and FNA never use SPIRV-Cross and must keep building, so a warning, never an error. (2026-10-03)
- Chose to warn (`SD0220`, from a `buildTransitive` .targets in ShadowDusk.HLSL) when a consumer's graph resolves a Vortice.Dxc other than 3.3.4, not to fail the build and not to rely on NuGet's `NU1608` alone (issue #282): DirectX 11 and FNA consumers never touch DXC and must keep building (seamless directive), while `NU1608` names neither the consequence nor the fix. At runtime the same condition is `SD0219` for every DXC-backed target, checked on the managed assembly BEFORE any native, rather than letting a lifted Vortice.Dxc try: its natives are a different DXC and, measured for 3.8.3, its API is binary-incompatible, so the only alternative outcomes were a substitute compiler or a misleading `MissingMethodException`. (2026-10-02)
- Chose NOT to ship our own Windows/Linux DXC natives inside ShadowDusk.HLSL in the #282 PR (split into issue #303), although that would stop Vortice's version resolution from choosing our DXC binary, because both cheap shapes were measured unsafe and the payoff is nil while the managed wrapper still comes from Vortice: native assets under Vortice's names or in a `runtimes/<rid>/native/<sub>/` subdirectory are flattened by RID-specific builds and conflict-resolved per file by version (measured: Vortice 3.8.3's `dxcompiler.dll` 1.9 beside our `dxil.dll` 1.7), `dxil.dll` cannot be renamed because DXC binds it by base name, and a consumer on Vortice.Dxc 3.8.3 fails on its binary-incompatible API whichever native loads. Owning the binary only pays off together with owning the managed bindings. (2026-10-02)
- Chose to verify Android's DXC from the MAPPED image (GNU build id read through `dl_iterate_phdr`) rather than accept the APK's copy unchecked or look for its file, because the APK is not a directory and a Release build does not extract libraries, while another package bundling its own `libdxcompiler.so` for the same ABI lands in the APK with no warning. An ABI with no pin is refused, consistent with every other OS. The x86_64 emulator copy is pinned too (no package ships it) so the emulator harness keeps running with the check on; the alternative, skipping the check where no pin exists, would leave exactly the unshipped ABIs, the ones where any DXC present came from someone else, unchecked. (issue #289, 2026-10-02)
- Chose the pure-managed `RdefReader` for DXBC reflection, not P/Invoking `D3DReflect`, because `D3DReflect` is Windows-only and blocked DX11 end-to-end on Linux and macOS; proven deeply equal to the D3DReflect oracle for both backends with zero `.mgfx` byte change.
- Chose the pure-managed `SpirvReflector` over the DXIL reflection oracle, because the DXIL path was Windows-only and blocked the WASM host; proven equivalent 10/10 with byte-identical `.mgfx` output.
- Chose to un-park Vulkan only when MonoGame 3.8.5 shipped a stable `DesktopVK`, not earlier, because a backend with no validatable consumer runtime cannot reach rung 4; Metal stays parked for exactly that reason, not because the compilation is hard.
- Chose to build DX12 as a genuine new backend, not treat it as a render-validation rung on existing work, because source inspection tripped Phase 52's own decision gate: no `PlatformTarget.DirectX12` existed.
- Chose to range-reduce every non-literal OpenGL `sin`/`cos`/`tan` argument in the managed rewriter (Rule 16, issue #215) with a **Cody-Waite two-constant split** (`k = floor(x/2pi + 0.5)`, `r = (x - k*6.28125) - k*0.0019353071795864769`), not MojoShader's printed `fract(x*0.159155 + 0.5)*6.283185 - 3.141593`, not the single full-precision-constant `fract` form, and not a gate on provably small arguments. Measured in fp32 over 4M random arguments per range: for |x| <= 1000 rad (Dots.fx reaches ~792) the max phase error is 1.3e-7 rad for the split, 1.0e-4 for the single-constant form, 3.8e-4 for mgfxc's constants; at |x| <= 10 000 it is 1.9e-7 / 8.3e-4 / 3.7e-3. A driver that reassociates the split into `x - k*(C1+C2)` degrades to the single-constant figure, never worse, and `C1` has 8 significant bits so `k*C1` stays exact to |x| ~ 400 000. The issue's literal suggestion `fract(x/2pi)*2pi - pi` (no `+0.5`) is wrong: it shifts the phase by pi and negates every result. No smallness gate, because the rewrite layer has no value-range analysis and a uniform, varying, or texture read can be arbitrarily large; only a bare numeric literal (which DXC folds anyway) is skipped, and a shader with no `sin`/`cos`/`tan` is byte-unchanged. The cost is a deliberate byte change to every GL shader that calls them (goldens/manifests re-baselined, rung 4 re-run), accepted because the reduction is what fxc itself does before every D3D9 `sincos`, so mgfxc's GLSL never hands a driver a large argument either. FNA needs nothing: vkd3d's SM1 lowering already emits the same reduction with full fp32 constants in the `.fxb`. (issue #215, 2026-10-01)
- Chose to reduce `tan` through the same `sd_reduce_angle` helper as `sin`/`cos`, not leave it on the raw argument and not give it a helper of its own that reduces by pi. The first cut of Rule 16 skipped `tan` on the belief that fxc has no D3D9 `tan` to mirror; that was wrong, and the missing instruction is exactly why fxc reduces it. Measured: `fxc /T ps_3_0` lowers `tan(input.TexCoord.x * 800.0 * scale)` to `mad / frc / mad / sincos / rcp / mul` (the same [-pi, pi] reduction as `sin`/`cos`/`sincos`, then sin over cos), so mgfxc's GLSL never takes the tangent of a large value, and vkd3d's SM3 lowering puts the same sequence in ShadowDusk's FNA `.fxb`. One helper serves all three because 2pi is two of `tan`'s pi periods, so the reduction is exact for it; a pi-period variant would add bytes to every `tan` shader for no accuracy the phase bound does not already give. `sin`/`cos`/`tan` are the complete set: HLSL `sincos` reaches GLSL as a separate `sin` and `cos`, `asin`/`acos`/`atan` take a ratio rather than an angle, and fxc lowers `sinh`/`cosh`/`tanh` to `exp` with no reduction. (issue #215 follow-up, 2026-10-01)
- Chose `RELAX_NAN_CHECKS` on the OpenGL SPIRV-Cross profile to fix issue #149, not a managed rewrite stripping `isnan()`, because flipping the upstream option produced zero byte changes anywhere else in the corpus.
- Chose to own only the container writers, the runtime-dialect adapters, and real-runtime validation, not compiler internals, because HLSL compilation and cross-compilation are multi-year efforts maintained by the people who own the formats, and the validation is the actual moat. (operator, 2026-06-09)
- Chose to treat the browser as a full export station (any host may emit any target), not a WebGL-only compiler, because compile-target and render-backend are independent; the in-browser artifact must be byte-identical to the desktop one, which is the bar for every future host. (operator, 2026-06-09)
- Chose to key the `.mgfx` sampler table on the reflected TEXTURES for DirectX and DirectX 12, on the (texture, sampler) PAIRS for OpenGL, and on the reflected SAMPLERS for Vulkan, not one rule for all, because each runtime binds differently: mgfxc keys its DX table on the texture's bind point (so a sampler-keyed table drops textures sharing one `SamplerState`); GL binds by NAME and the record must name a `ps_s{k}` uniform the emitted GLSL declares, which is one per pair; Vulkan binds through the descriptor layout on raw SPIR-V bindings that the binding rewriter has already co-located per pair. Only the pair list can be right for GL, and neither reflected list is it. The 1:1 case is byte-identical under any of the three rules. (Phase 51 A7, 2026-07-29; superseded the earlier sampler-keyed GL rule and its `SD0215`/`SD0216` rejections.)
- Chose to derive the GL combined-sampler pair list in pure managed code from the SPIR-V (`SpirvCombinedSamplerPairs`), not by reading `spvc_compiler_get_combined_image_samplers` on the desktop, because `spirv-cross.wasm` exports 11 functions and that is not one of them: a native call would fix the desktop path only and break CLI-vs-WASM byte identity for the shape. Reading it off the emitted GLSL is also impossible, because SPIRV-Cross's readable `SPIRV_Cross_Combined<Image><Sampler>` name is applied by its command-line tool rather than by the pass, so through the C API the uniforms arrive as bare `_<id>` with no pair identity. The ordering rule is transcribed from the pinned SPIRV-Cross tree, and an internal cross-check against the sampler uniforms the emitted GLSL actually declares (`SD0217`) is what catches a drift from it. (Phase 51 A7, 2026-07-29)
- Chose to number the GL `ps_s{slot}` uniforms and their `.mgfx` records by the pair's HLSL DECLARATION index, not by the pair's position in SPIRV-Cross's first-use list, because that is how fxc (and therefore mgfxc) allocates OpenGL sampler slots. Measured on three shapes against the pinned mgfxc, including one with every `register` annotation stripped: declaration order in all of them, so the rule is not merely "honour `register(sN)`". The constraint the earlier decision was protecting (the record must name a uniform *our own* GLSL declares) is preserved by numbering BOTH from one shared `SpirvCombinedSamplerPairs.ResolveSlots` rather than by conceding the numbering to SPIRV-Cross. **This supersedes the A7-era position that ShadowDusk had to follow SPIRV-Cross's first-use numbering and that the divergence was behaviorally invisible** — it was not: `SpriteBatch` owns unit 0, so a `register(s0)` sampler that was not sampled first read the sprite. The evidence that had been cited for "invisible" (`validation/SamplerPairsGl` arm B, maxd 0) could not support it, because that arm gives its two textures identical pixels by design. Where two pairs share one texture their declaration indices collide and there is no mgfxc golden for the shape, so `ResolveSlots` falls back to positional numbering rather than inventing an answer. (GitHub issue #189, 2026-08-02; rung-4 proved by `validation/SamplerRegisterOrderGl`.)
- Chose to model fxc's OpenGL sampler-register ALLOCATOR rather than to special-case declaration forms: in texture-declaration order, a pair whose sampler declared an explicit register takes it, and every other pair takes the lowest register neither already taken nor reserved by a modern `SamplerState : register(sN)`. One rule, verified against the pinned mgfxc on 10 shapes. It removes what looked like an arbitrary asymmetry: at `ps_3_0` a texture and a sampler are ONE object in ONE register namespace, so a legacy `sampler X : register(sN)` IS the combined object and lands on N, while a modern `SamplerState` is a sampler-only object that occupies its register and forces the synthesized combined samplers around it (one texture + `S : register(s0)` yields `ps_s1`, not `ps_s0`). A superseded earlier reading of this — "mgfxc simply ignores modern registers on OpenGL" — was drawn from too few samples and was wrong; it is corrected here rather than left in place. (GitHub issue #189, 2026-08-02.) Superseded detail, kept because the measurement stands: `mgfxc` emits `ps_s2` at unit 2 for `sampler X : register(s2);` (at `ps_3_0` the legacy sampler IS the combined sampler, so the clause pins its SM3 register), but for `Texture2D T : register(t3); SamplerState S : register(s2);` its OpenGL build puts the pair on unit 0 regardless, allocating by texture declaration order. Honouring modern registers would therefore be a divergence, so both behaviours are pinned by tests that fail if either is "corrected" later. The clause is RECORDED in `FxParseResult.ExplicitGlSamplerSlots` rather than re-emitted into the rewritten HLSL, because re-emitting it would change what DXC compiles and move the DirectX/DX12/Vulkan/FNA bytes for a defect none of them have. (GitHub issue #189 sparse half, 2026-08-02; rung-4 proved by `validation/SamplerRegisterOrderGl` arm "sparse".)
- **Chose to fix a legacy sampler the raw pre-parse cannot see (issue #308) as a RECOVERY after the raw compile has failed, compiling from the managed preprocessed view, not by pre-parsing the preprocessed source for every effect and not by expanding selected macro invocations in place (2026-10-02).** Pre-parsing the preprocessed source for every effect would hand DXC a text ShadowDusk produced instead of the author's, for every effect, with our preprocessor's fidelity on the critical path of every compile and every line and column shifted; the hard constraint was that no emitted byte may move for an effect that compiles today, and only "try the raw text first, recover on failure" meets it by construction (an effect that compiles is never touched; measured byte-identical on the whole corpus for OpenGL and DirectX_11). Expanding only the macro invocations that produce a legacy declaration, leaving DXC as the preprocessor, keeps DXC in charge of the text but is a heuristic over which invocations matter (a declaration spelled through an object-like type macro, a `tex2D` in a macro body, a sampler name that is itself a macro) and still needs the include-flattened raw text parsed with both `#if` arms visible; the preprocessed view is what `mgfxc` itself parses, so it is both complete and the reference's own model. The cost of the design is one failed DXC compile for every effect that needs the recovery (measured about 15 ms over the directly written twin on a small effect), accepted because it is paid only by effects that did not compile at all before. The view's fidelity to DXC `-P` is measured on the whole corpus rather than assumed, and a conditional on a compiler-predefined macro, which the managed view cannot evaluate as DXC would, refuses (`SD0016`) rather than guesses. Deliberately NOT extended to the macro-defined-technique `SD0010` gap on OpenGL: a raw pre-parse with zero techniques fails before any compile and stays out of the recovery's reach, because the stock effects' legacy branch was once measured to crash DXC's SPIR-V codegen and that path needs its own proof. **The raylib and SkSL converters take the same recovery through the same code (issue #327, 2026-10-02), not a converter-specific copy and not a preprocessed pre-parse for every conversion:** `LegacySamplerRecovery.Evaluate` and `Apply` are shared with the pipeline, and each converter re-enters its own validations from the preprocessed pre-parse (a `Retry` must re-run the converter, not just the seam, because the technique, pass, render-state and baked-`sampler_state` facts are read off the pre-parse too). A copy would have forked the outcome semantics (`SD0016` placement, the `Rejected` verdict) three ways; a preprocessed pre-parse for every conversion would have put the managed view on the critical path of every conversion, the same objection as above, and the byte-identity constraint held only by construction.
- Chose to rank a combined sampler's declaration index by SPIR-V MODULE order rather than by its `Binding` decoration, because the two agree only while DXC auto-allocates: once the source carries explicit registers the binding equals REGISTER order, and `mgfxc` allocates by DECLARATION order. Measured: for `Texture2D TexA : register(t3); Texture2D TexB : register(t2);` mgfxc puts TexA (declared first) on unit 0, where a binding-ordered rank puts TexB. This was a pre-existing divergence the first #189 fix inherited, found by an adversarial "modern registers must NOT be honoured" test rather than by any render. (GitHub issue #189, 2026-08-02)
- Chose to leave DirectX 11 and Vulkan sampler-slot allocation alone while fixing the OpenGL one, even though both also ignore `register(sN)`, because each is internally consistent with its own binding mechanism and no failure is reported against either: on DX11 fxc itself auto-assigns `t` registers by first use (measured — mgfxc puts the *second*-declared sampler's texture on `t0`), so matching the annotation there would move us AWAY from the reference compiler, and Vulkan binds through a descriptor layout rather than by slot number. The DX11 sampler-slot divergence (we emit 0/1 where mgfxc emits the declared 2/3) is recorded as a measured, unfixed divergence rather than silently corrected, because changing it would require re-proving two rung-4 backends for no reported symptom. (GitHub issue #189, 2026-08-02)
- Chose to keep naming the GL texture parameter after the TEXTURE (`DiffuseMap`), not to adopt mgfxc's MojoShader `<sampler>+<texture>` combined spelling (`TextureSampler+DiffuseMap`), even though mgfxc's own OpenGL goldens use the latter for every modern-syntax shader. Three reasons: MonoGame resolves a sampler's texture through the record's `Parameter` **index**, never the name (`EffectPass.SetShaderSamplers` does `_effect.Parameters[sampler.parameter]`), so the two spellings are behaviorally identical; renaming would break every existing consumer's `Parameters["DiffuseMap"]` lookup, which the backwards-compatibility directive forbids; and ours is the same name the DX, DX12, Vulkan, and FNA targets use, so one game's code works on every backend, whereas mgfxc's spelling is GL-only and makes an effect's parameter names backend-dependent. "Same as mgfxc" is behavioral equivalence plus `Effect`-loadability, not byte identity, so this is inside the promise. (Phase 51 A7, 2026-07-29)
- Chose to make `RuntimeProfileDetector.Recommend` throw for a target no `CapabilityProfile` models, not return the OpenGL profile, because a set `Profile` overrides `CompilerOptions.Target`: the fall-through silently compiled Vulkan/DX12/Metal to a GL artifact the consumer's runtime cannot load. Setting `Target` directly with `Profile` left null stays the supported path.
- Chose pipeline-side SYNTHESIZED register backing for the issue-#187 phantom-parameter class (a reflected numeric parameter whose only reads DXC's `-spirv` backend folds away, dropping its cbuffer from the SPIR-V), not won't-fix, not reflecting from the shipped SPIR-V, and not a DXC flag. Reflecting from shipped SPIR-V (`SpirvReflector`) removes the parameter NAME and was already tried and reverted (PR #186) — name presence is consumer-load-bearing (ShaderFiddle.Web keys ShaderToy detection on it); `-fspv-preserve-bindings` does not exist in the pinned DXC 1.7.2212.40 (a 1.8.x flag — re-evaluate at the DXC pin bump the DX12 `maxd 1` gap already motivates); won't-fix leaves ShadowDusk's own output structurally self-inconsistent and the regression test unwritable. Synthesis completes the one-directional layout→parameter join on our side of the compiler boundary (the blessed `D3d9BytecodePatcher` pattern), reproduces the mgfxc golden's exact structure for the one known member, matches the shape real mgfxc's DirectX profile ships for dead uniforms, and changed one pre-existing corpus output. Sized by the runtime's transposed matrix write model (Columns registers), never Rows — MonoGame/KNI `ConstantBuffer.SetParameter` writes `ColumnCount` 16-byte rows, so Rows-sizing crashes the first `EffectPass.Apply` on non-square matrices. (issue #187, 2026-08-01)
- Chose to isolate DXC's Unix process-global side effects at our boundary (`DxcSignalIsolation`: one serialized signal registration, then restore the runtime's handlers; `DxcForkGate`: a macOS `pthread_atfork` gate around only DXC's one locale-changing call, a `-P` preprocess the gate runs itself), not to serialize every DXC call, patch our DXC build, or cap test parallelism. The gate first wrapped every native compile; that was withdrawn (issue #312, 2026-10-03) because a fork that waits for a compile holds dyld's dlopen lock (libSystem's handler order) and a debug SPIR-V compile `dlopen`s from inside DXC, so no design in which a fork waits for a compile can be deadlock-free. Rejected alternatives: a bounded wait in the atfork handler (a timeout hides the cycle instead of removing it, and stalls every colliding `Process.Start` for the bound); dropping `-Zi`'s embedded source or the file name for SPIR-V (changes emitted debug bytes); re-emitting `OpSource` ourselves (owning compiler internals, and the `dxc-cl-option` string would still change); interposing `fork`/`dlopen` or releasing dyld's lock from our handler (dyld internals). The pin bump (#287) would retire the gate entirely, since DXC v1.9.2602 no longer calls `setlocale`. A global lock was measured to fix only the table-overflow crash: hosts still died by `SIGUSR1` (exit 158) because LLVM's handlers stayed installed, and a single compile still deadlocks against `fork()`. Patching DXC breaks the never-fork-compiler-internals rule and would not reach Vortice's Linux binary. Capping parallelism hid the crash without fixing it. Compiles stay parallel.
- Chose to make DXC's own leaf-name load of `libdxcompiler` (made from inside every `-Zi` SPIR-V compile to read the source for `OpSource`, issue #332) a question put to the dynamic linker without loading anything (`dlopen(leaf, RTLD_LAZY|RTLD_NOLOAD)`, glibc's "found a file but did not load it" report, `GetModuleHandleW`), and to refuse only the debug SPIR-V compiles (`SD0223`) when the answer is not the pinned build, rather than any of: (a) relying on the linker alone (measured by source and on the lanes: Windows returns the first module of the base name and dyld-1122+ (macOS 14) matches the leaf to the loaded image's `@rpath/libdxcompiler.dylib` install name, but glibc never matches the leaf to an object with `SONAME libdxcompiler.so.3.7` and dyld-940/1042 (macOS 12/13) search directories, so on those a decoy on `LD_LIBRARY_PATH`, in the working directory or on `DYLD_FALLBACK_LIBRARY_PATH` is loaded and initialized inside the compile); (b) registering the pinned image under the leaf name first, which no linker offers: dyld matches a leaf only by load path or install name and glibc only by the names an object was found under or its `SONAME`, so the only way to make the pinned image answer is in the shipped files themselves (`SONAME libdxcompiler.so` on the Linux build, which is Vortice's and the #303 ownership work, and the install name macOS already has), and loading the pinned file a second time BY the leaf name is the name search this loader exists to forbid; (c) loading the candidate once at `Register` to inspect it, which runs the decoy's initializer, the very thing the issue is about; (d) dropping `-Zi`'s source embedding or re-emitting `OpSource` ourselves (changes emitted debug bytes, rejected under #312 too); (e) refusing every `-Zi` SPIR-V compile whenever the leaf does not match the pinned image, which would break every debug OpenGL/Vulkan compile on Linux, where a miss is the normal, harmless case (DXC's load fails and the emitter falls back to the in-memory source). A byte copy of the pinned build found by the search is accepted, the same rule as at load time, because it is the same compiler; a glibc "found" with no locatable candidate is refused, never guessed benign. The answer is computed once (Windows and glibc cannot change it for the life of the process) and re-evaluated per debug SPIR-V compile on macOS only when dyld did not match (the working directory can change). The clean fix remains in the natives: a Linux build whose `SONAME` is the leaf name would make glibc answer like dyld-1122 does, and belongs to #303. (2026-10-03)
- Chose to keep `DxcForkGate` macOS-only rather than enable it on Linux "to be safe" (issue #256), because Linux was measured not to deadlock (thousands of DXC compiles against `Process.Start` and real `fork()` on ubuntu CI) and the gate would be inert there anyway: `Process.Start` is `vfork()` on glibc and runs no atfork handler, and glibc does not even export `pthread_atfork`. Enabling it would add an atfork hook that executes managed code inside every real `fork()` for no measured benefit. Revisit if `ProcessStart_ForkMechanism_MatchesTheForkGatePlatforms` or the fork probe ever fails on Linux, or when Android (bionic, which .NET forks on) is measured.
- Chose to run every native compiler call (DXC compile/preprocess/reflection, vkd3d, SPIRV-Cross, the fxc oracle) on a pool of ShadowDusk-owned 64 MB-stack worker threads (`NativeCompileStack`, issue #306), the calling thread blocking on a plain event until the worker returns, rather than (a) one long-lived worker, (b) a new thread per call, (c) running the whole pipeline on a big-stack thread, or (d) a source-level nesting-depth pre-check. (a) would serialize concurrent compiles, which stay parallel by decision; (b) was measured at about 100 microseconds per call on Windows against about 1 for a pooled handoff, and a compile makes several such calls; (c) would move the consumer's own callbacks (`IIncludeResolver`, MGCB context) off the thread that called the synchronous `Compile`, and would not cover direct users of the public `DxcShaderCompiler`/`Vkd3dShaderCompiler`/`SpirvCrossGlslTranspiler`; (d) was measured unreliable: stack use per nesting level differs about 5x between shapes on the same compiler (about 0.7 KB per additive term, 2 to 4 KB per unary operator, DXIL frames larger than SPIR-V frames) and macro expansion hides the depth entirely (twelve `#define` lines yield a 4,096-term expression), so any threshold both rejects valid shaders and misses crashing ones. Through the synchronous `Compile` only the native call moves: the caller keeps every lock and gate it held (so `DxcSignalIsolation` stays serialized and `DxcForkGate` is entered on the thread that is inside `setlocale`), and its `ExecutionContext` flows; measured about 0.1 ms per handoff on a real compile (the work changes core), about 0.4 ms on a 10 ms effect. `EffectCompiler.CompileAsync` instead hands the whole synchronous pipeline from its thread-pool thread to one worker (nested calls run inline), which measured no difference against the pre-fix build: an async caller was already on an arbitrary thread, so nothing observable moves, while the synchronous API keeps its callbacks on the calling thread. The async entry points stay `Task.Run` shells over the synchronous core (no `TaskCompletionSource` bridge), because that core is shared with the browser host and the public synchronous `Compile`, and because `Task.Run` keeps the thread pool's throttling of how many compiles run at once. 64 MB is address space only (measured: 16 live workers add 0.33 MB of private bytes); it is about 43x the 1.5 MB the .NET host gives a Windows thread and 8x the usual 8 MB on Linux/macOS. If a host cannot start the thread, the call runs inline as before. The residual ceiling is documented, not guarded (`project_facts.md`).

- **Chose to fold a resource array's per-element Shader Model 5 RDEF records into one binding in `DxbcReflectionExtractor` (`ResourceArrayBindings.Collapse`), not in `RdefReader`, not in the MGFX writer, and not by compiling DirectX 11 at the author's `ps_4_0` (issue #339, 2026-10-02).** `RdefReader` is deeply equal to `D3DReflect` by contract (the parity tests), and `D3DReflect` reports the SM5 per-element records as stored, so the collapse cannot live there without breaking the oracle. The writer sees textures only after the parameter list is built, too late to rename. Compiling at the author's model would reproduce mgfxc's RDEF directly but changes the DXBC of every DirectX 11 shader (ShadowDusk's SM5 compile model is rung-4 proven across the corpus) to fix one shape. The extractor is where the DXBC view is made to match the DXIL view (which already reports an array as one binding with `BindCount`), and the collapse is a no-op for every array-free effect, which the 668-cell corpus sweep confirmed byte for byte.
- **Chose to REFUSE an author-written sampler array (`SamplerState S[N]`) on DirectX 11 and 12 with `SD0224`, not to keep it as a documented superset, although the pre-fix effects loaded and drew correctly in both real engines (issue #340, 2026-10-02).** mgfxc refuses the shape on every profile in its own parser, so a `.fx` that relies on it fails under the reference compiler, and MonoGame's sampler record names no element; the owner's rule (an input shape we don't model gets a registered code, never a silent pass-through) and the issue's own direction chose parity over the superset the issue left open. The exception is slangc's lowering of a combined-sampler array (`Sampler2D T[N]` to a texture array plus `T_sampler_0[N]`): that is one author resource in a language mgfxc never parses, so it keeps the hand-written `Texture2D T[N]; SamplerState S;` table, carried through an internal `CompilerOptions` seam rather than a name heuristic in the pipeline (the pipeline must not learn slangc's naming) or a rewrite of slangc's HLSL into N separate samplers (which would move the Slang route's bytes and change which sampler slot each element uses).

## Output format and compatibility

- Chose MGFX v10 as the default, not v11 or KNIFX, because v10 is the one format both MonoGame 3.8.2+ and KNI load, making it the most backwards-compatible choice.
- Chose to ship MGFX v11 and KNIFX as additive opt-ins (`CompilerOptions.MgfxVersion`, `CompilerOptions.Container`), not as a default or a required flag, because the consumer must never pick a version to get correct output. The old `--mgfx-version 11` was corrupt (v10 body with a v11 version byte) and was fixed rather than kept.
- Chose to emit raw `.mgfx` from core, not `.xnb`, because wrapping is the content-pipeline layer's job; a hand-rolled XNB writer would be the first divergence from `mgfxc` parity and would duplicate and risk desyncing the Phase 29 plugin's validated envelope. Re-open only as a deliberate, explicitly-scoped feature if a downstream (e.g. XnaFiddle project export) needs pre-wrapped `.xnb`. (2026-06-08) **Superseded 2026-08-13 by Phase 60 on exactly that trigger:** issue #199 (vchelaru) asked for `.xnb` so a consumer changes no code, the owner committed to it the same day, and `XnbWriter` shipped as a container-only writer around the already-proven payloads (extension-driven on the CLI, `ToXnb()` on the library), validated against a real `dotnet-mgcb` build rather than left to drift.
- **Chose the XNA-4.0 type-reader name for the `.xnb` manifest** (`Microsoft.Xna.Framework.Content.EffectReader, Microsoft.Xna.Framework.Graphics, Version=4.0.0.0, Culture=neutral, PublicKeyToken=842cf8be1de50553`), **not the mgcb-shaped one Phase 60 first emitted** (`…, MonoGame.Framework, Version=3.8.4.1, Culture=neutral, PublicKeyToken=null`) and not a per-runtime manifest, because it is the only reader name measured to load on all six consumer runtime versions (MonoGame 3.8.1.263 / 3.8.2.1105 / 3.8.5, KNI 4.2.9001 / 4.3.9001, FNA 26.06 — each a real `ContentManager.Load<Effect>` rendering pixel-identical to that runtime's reference, maxd 0). The mgcb-shaped name fails on KNI 4.2.9001: KNI's `ContentTypeReaderManager.ResolveReaderType` appends its own assembly name to the stripped `…EffectReader, MonoGame.Framework` and `Type.GetType` throws `FileLoadException: The given assembly name was invalid.` before KNI's `MonoGame.Framework` fallbacks run (4.3.9001 catches it) — so stock mgcb's own `.xnb` fails on KNI 4.2 identically, and "emit exactly what mgcb emits" was right for MonoGame and FNA and wrong for the KNI version this repo's own harnesses pin. The XNA-4.0 name is what KNI's own `CompiledEffectWriter` and XNA itself write, and it is the intersection of the three resolvers by construction (MonoGame's `Graphics` replacement, FNA's regex alternative, KNI's first-choice mapping). A per-runtime manifest (e.g. keyed on `--target-runtime kni-*`) was rejected because plain `/Profile:OpenGL` v10 is the documented KNI route and a KNI ≤ 4.2 consumer would have had to opt in to get correct output, which the seamlessness directive forbids; "KNI ≤ 4.2 unsupported" was rejected because it contradicts the product statement. No compatibility cost: the mgcb-shaped string never shipped in a release (Phase 60 landed 2026-08-13, the last release is 0.18.0 of 2026-08-03). (Phase 64 C1, 2026-09-09)
- Chose to emit `mgfxc`'s `#define ps_oC0 gl_FragColor` form, not a raw `gl_FragColor` write, because KNI's HiDef runtime converter only rewrites that form, so one artifact serves Reach and HiDef with no consumer flag and is strictly more `mgfxc`-faithful.
- Chose to emit the correct full uniform-array layout, not `mgfxc`'s compacted MojoShader layout, because `mgfxc` + MonoGame GL is itself broken for statically-partially-read arrays.
- Chose `PlatformTarget.Fna` as a fully separate `RunFnaAsync` pipeline emitting a raw `.fxb`, not a variant of the `.mgfx` path, because a separate pipeline cannot change existing GL or DX output; the additive-and-cannot-regress property is the point.
- Chose vkd3d on every host for FNA output, never the `d3dcompiler` oracle, because that keeps the shipped bytes host-independent; `fxc /T fx_2_0` is a Windows test oracle only.
- **MGCB integration is the content-processor PLUGIN (`ShadowDusk.MgcbPlugin`), not a PATH-based `mgfxc` drop-in.** The original decision chose "Tier 1" (a drop-in binary named `mgfxc` on `PATH`) over a plugin, on the belief that MGCB shelled out to `mgfxc`. **That premise was measured false** (2026-07-28, Phase 52 Area E): `dotnet mgcb` compiles `.fx` in-process at 3.8.2.1105, 3.8.4.1, and 3.8.5 alike and launches no external `mgfxc` (a logging `mgfxc.exe` first on `PATH`: zero invocations, valid `.xnb` each time), so there was never a process for a PATH alias to intercept. [Phase 29](plan/DONE/PHASE-29-mgcb-content-processor-plugin.md) built the plugin (2026-07-31) and it is now the supported native route; the CLI-plus-`/copy:` route and runtime compilation remain valid and documented. The CLI is still a faithful `mgfxc` drop-in for anything that really does invoke `mgfxc` — that is just not MGCB.
- Chose to make the MGCB plugin a **TOOLS-ONLY package** (everything under `tools/net8.0/any/`, no `lib/`), not a normal library package, because MGCB's `/reference:` takes a path to an assembly and resolves that assembly's dependencies from its own directory: a `lib/`-shaped package would put the plugin somewhere its ShadowDusk and Vortice dependencies are not, and would also flow a build-time content-pipeline plugin into the consumer's shipped game assembly. `DevelopmentDependency` + `SuppressDependenciesWhenPacking` make that explicit. (Phase 29, 2026-07-31)
- Chose to give the MGCB plugin its own `AssemblyLoadContext.ResolvingUnmanagedDll` fallback rather than changing ShadowDusk's existing native loaders, because the problem is host-shaped, not loader-shaped: inside MGCB, `AppContext.BaseDirectory` and `NATIVE_DLL_SEARCH_DIRECTORIES` both point at MGCB, so every existing probe legitimately misses. `ResolvingUnmanagedDll` is the runtime's LAST resort, so the shim can never displace a native the normal loaders found, and it changes nothing outside an MGCB host. It loads the same pinned natives, so it is a lookup path and not a substitute compiler. (Phase 29, 2026-07-31)
- Chose a SECOND, library-shaped package (`ShadowDusk.ContentPipeline`, `lib/net8.0`, real dependency edges) for MonoGame 3.8.5's Content Builder project, not `lib/` added to the tools-only `ShadowDusk.MgcbPlugin` and not a namespace-only export, because the plugin's three tools-only properties (`IncludeBuildOutput=false`, `SuppressDependenciesWhenPacking`, everything under `tools/net8.0/any/`) are each required by MGCB's `/reference:` and each wrong for a library consumer, who needs the types at compile time and `ShadowDusk.Compiler` + the natives flowing into its own bin; one package cannot be both. Both compile the same five source files (pinned by test), so the byte-identity claims cost nothing extra. Kept the `MonoGame.Framework.Content.Pipeline` **3.8.2.1105 floor** for it too (the 3.8.2.1105-compiled pair binds in a 3.8.5 process, measured; nothing in it needs the `Builder` namespace; a 3.8.5 floor would exclude older custom hosts for no gain). Moved the pair's C# namespace to `ShadowDusk.ContentPipeline` in both packages (MGCB and the Builder resolve by simple type name, measured), rather than keeping `ShadowDusk.MgcbPlugin` as the `using` for a library that is not the MGCB plugin. Provides NO `ContentBuilder` subclass or collection helper: the consumer owns the Builder and ShadowDusk provides the two instances, which keeps the floor below 3.8.5. (Phase 63, issue #203, 2026-09-09)
- Chose a separate, public `CompilerOptions.EmbeddedSourceFileName` (default `null` = embed `SourceFileName` as passed), set to `<unknown>` by the content processor, to keep the build machine's path out of MGFX v11 output (issue #274), not any of: blanking `SourceFileName` in the processor (diagnostics would lose the file and relative `#include`s their anchor); changing the library default to `<unknown>` or the file's base name (that changes CLI output, breaks the measured `mgfxc` CLI parity, and the defect was on the content-build route only); or an internal option reached through `InternalsVisibleTo` from Core to the two delivery-shape assemblies (it would leave a library consumer who drives the compiler from their own build tool with the same leak and no fix). `<unknown>` rather than the file name or a project-relative path because it is byte-for-byte what MonoGame's stock `EffectProcessor` writes, and the processor has no reliable project root to relativize against. Debug information is deliberately out of this option's reach: it exists to name the source.
- Chose (owner, issue #280, 2026-10-02) the parity reference by OUTPUT KIND, not by delivery shape: the CLI's `.mgfx` output stays at `mgfxc` CLI parity (the source path as passed), and the CLI's `.xnb` output follows MGCB, writing `<unknown>` via `CompilerOptions.EmbeddedSourceFileName` exactly as `ShadowDuskEffectProcessor` does, because `mgfxc` has no `.xnb` mode and the `.xnb` route is pitched as a content-pipeline replacement. Not chosen: keeping the path in the CLI `.xnb` (a build script passing absolute paths would reproduce #274) or changing `.mgfx` output too (breaks the measured `mgfxc` parity).
- Chose (owner, issue #280, 2026-10-02) that the content processor's `DebugMode=Auto` follows stock MGCB exactly: debug information only for an explicit `DebugMode=Debug`, the build configuration never consulted (stock `EffectProcessor` at `v3.8.5`: `Debug = DebugMode == EffectProcessorDebugMode.Debug`; `v3.8.2` gates `/Debug` on the same test). Not chosen: "Auto = debug under `/config:Debug`", the earlier ShadowDusk behaviour, which diverged from stock bytes and leaked the build path through DXC debug info; nor scrubbing the path out of debug info (debug info exists to name the source, and stock's explicit `Debug` keeps it in Vulkan SPIR-V too).
- Chose to key the MGCB/Builder platform map on the platform's NAME (`platform.ToString()`), not on `TargetPlatform` members, because MonoGame renumbered the enum in 3.8.5 while the plugin is compiled against 3.8.2.1105 (the floor): member matching compiled the old numbers in and silently built an OpenGL payload for `/platform:DesktopVK` on 3.8.5. Names are what `/platform:`, `-p`, and `$(MonoGamePlatform)` actually carry, a name map can name `DesktopVK`/`WindowsDX12` without compiling against 3.8.5, and it lets those two derive Vulkan/DirectX 12 seamlessly (the `ShaderProfile` escape hatch stays only for MGCB before 3.8.5). Rejected raising the floor to 3.8.5 instead: it would not have loaded into older MGCBs and would still have needed a rule for every future renumbering. (Phase 63 Area B, 2026-09-09)
- Chose to own the `ID3D12ShaderReflection` interop (four interfaces + five `D3D12_*_DESC` structs over `SharpGen.Runtime`, transcribed from `d3d12shader.h`) and drop `Vortice.Direct3D12` from `ShadowDusk.HLSL`, not to route desktop GL/DX11/DX12 reflection through the pure-managed `SpirvReflector` and not to lazily isolate the reflector in a separate assembly, because the Builder's unguarded `GetTypes()` scan is a graph property (exactly one Vortice type fails type-load, in 3.5.0 and 3.8.3 alike), the interop is ~300 lines with zero byte change (same DXC, same `IDxcUtils::CreateReflection`, same vtable calls; every golden and the cross-host manifest unchanged), the SPIR-V route would have cost DX12 a parallel `-spirv` compile and a re-proof of its vertex-input semantics, and lazy isolation works only by load order. Upstream issues for MonoGame (guard the scan) and Vortice (the `Union` layout) are drafted in parallel, never as the fix. (Phase 63 Area A, 2026-09-09)
- Chose to exempt `ShadowDusk.MgcbPlugin` from the no-MonoGame guard **by name, with a second test pinning `IncludeAssets="compile" PrivateAssets="all"`**, not to weaken or delete the guard, because an MGCB plugin cannot exist without the `ContentImporter`/`ContentProcessor` contract while the guard's real concern (a MonoGame assembly shipping inside a ShadowDusk package, or a MonoGame dependency edge reaching a consumer) still has to hold. The exemption is the reference existing; the two attributes are what make it harmless. (Phase 29, 2026-07-31)
- Chose to pin the golden-generation `mgfxc` to the `dotnet-mgcb` version in `.config/dotnet-tools.json` and assert the MGFX version byte it writes, not to take the newest `mgfxc` on the machine, because the goldens are canonical v10 and "newest" resolved to two different broken answers at once: mgfxc 3.8.5 emits **v11** (0 of 46 goldens matched), and the `dotnet-mgcb-editor-windows` 3.8.4.1 `mgfxc.exe` cannot run at all (ships without `SharpDX.D3DCompiler.dll`). mgfxc 3.8.2.1105 and 3.8.4.1 reproduce all 46 goldens byte-for-byte, so the pin is a verified range, not a magic build. (2026-07-28, Phase 52 Area C)

## Scope and product shape

- Chose to treat `.fx` compilation as same-trust-domain, not untrusted input, because compiling a shader you chose to run is like compiling copied C++ or C#; the earlier path-traversal, size-limit, and macro-validation findings were removed as not-real-harm rather than answered with input-validation theater. (2026-06-12, closed by `SECURITY.md` 2026-06-15)
- Chose a synchronous `CompilationPipeline.Run` core with `CompileAsync` as a thin shell over it, not two pipelines, because sync and async output must be byte-identical by construction rather than by test; the only genuinely async work is the one-time WASM module load.
- Chose to publish `ShadowDusk.ShaderToy` as a standalone NuGet from 0.9.0, not to leave it unpackaged as originally deferred, because it is pure-managed with zero native dependencies and purely additive to the pipeline, so shipping it costs nothing.
- Chose to judge the ShaderToy frontend by pixel-fidelity against the original GLSL, not by mgfxc-equivalence, because `mgfxc` never compiles ShaderToy GLSL and so provides no oracle; calling it an mgfxc-equivalence proof would be dishonest.
- Chose to fold the MonoGame `ShaderToyEffect` runtime helper into `samples/ShaderToyViewer` as a single source file, not to keep (or resurrect) a shared `ShadowDusk.ShaderToy.Runtime` project, because a project by that name looks like a shippable `ShadowDusk.*` package and invites exactly the MonoGame-in-product mistake `NoMonoGameInProductLibrariesTests` exists to prevent; its one other consumer (the out-of-band render-proof driver) source-links the file instead. Revisit only if a third MonoGame consumer of the helper appears. (Phase 51 A4, 2026-07-31)
- Chose build-time precompile to `.mgfx` as the documented default for shipping Android games, not on-device compile, because build-time works today with zero Android-specific work; on-device stays additive reach.
- Chose to vendor Gum and Apos.Shapes shaders verbatim as fixtures, not to synthesize approximations, because the real third-party shaders surfaced real gaps our own corpus could not (the Gum FnaSample shader is what exposed Phase 41 GAP-1).
- Chose to resolve `#include` paths exactly as the host file system does and to WARN (`SD0008`) when a case-only mismatch resolved anyway, not to add the case-insensitive resolution fallback bug-hunt M12 proposed for Linux, because a fallback would open a file the file system says does not exist, is ambiguous wherever two real case twins live side by side, and hides a build break the author is about to ship to Android at the one moment they could still fix it. The comparer that decides whether two spellings are one file asks an injectable `IIncludePathCanonicalizer` rather than checking the OS, with **ordinal as the default and case-insensitivity as the exception**: wrongly merging two paths suppresses a header or invents a cycle, while wrongly separating two spellings of one file only costs a duplicated expansion the cycle check still terminates. (Bug-hunt N17 + M12, 2026-07-31)
- Chose **not** to make the `cpt-max/MonoGame` fork an in-scope consumer runtime, so ShadowDusk will not gain a fork target for the geometry / hull / domain / compute stages, because the fork's effect format turned out to be **a second container, not a superset**: its writer emits `(int)ShaderStage` (4 bytes) where stock emits a 1-byte bool and it drops the two v11 `SourceFile`/`Entrypoint` strings, so every shader record diverges from its first byte and stock MonoGame would **misparse** fork output rather than ignore it. Supporting it is therefore a second output writer, a second reference compiler (`dotnet-mgcb-compute`), a second pin, and a second render-gate family, for a fork whose last push is 2024-05-20 and whose packages stop at 3.8.3 against stock's 3.8.5 — the largest maintenance surface in the matrix for its smallest consumer base, and this project's repeated finding is that an unvalidated cell is worse than an absent one. Took the **middle option** instead, which is already shipped: the pre-parser knows the four stages and `FX0014` names both the permanent reason and the fork, so a user who wants it is pointed at it and a future reversal stays cheap. Two consequences worth keeping: a fork target could never be a silent auto-upgrade (it would have to be an explicit `PlatformTarget`, which constrains [Phase 57](plan/PHASE-57-universal-compiler-auto-detection.md)'s auto-detection), and this closes Phase 58 Area B as **declined, not deferred**. Revisit only if the fork resumes active maintenance AND a real consumer asks. (Owner decision, Phase 58 §5, 2026-08-11)
- **Chose to support Slang as an INPUT language only, never as an output format (owner direction, 2026-08-13).** [Issue #198](https://github.com/kaltinril/ShadowDusk/issues/198) was ambiguous and the scope moved twice before settling: it was briefly widened to input *and* output, then narrowed back when the requester clarified he meant input. Emitting Slang was closed **despite being the cheaper half** (source generation, no new native to package, and a self-contained round-trip byte oracle) because it had **no named consumer**. That asymmetry is the point worth remembering: cost is the easier signal to read, and reading it alone would have built the unrequested half first. Slang as a *substitute compiler* stays closed on Phase 23's measured evidence, now independently confirmed by the requester. Detail: [Phase 61](plan/DONE/PHASE-61-slang-support.md) §3.1.
- **Chose the HLSL-compatible subset of Slang, compiled by the existing pipeline — no Slang toolchain shipped or invoked, anywhere (owner direction, 2026-08-13, superseding two same-day directions).** The earlier directions ("accept valid Slang, reject only what MonoGame cannot hold" and "ship Slang input as a full runtime capability", both 2026-08-13) implied bundling the Slang compiler per-RID the way DXC ships; the owner rejected that on review. The chosen shape: Slang is a near-superset of HLSL, so the `.slang` body compiles through the **same DXC every `.fx` uses** — the frontend is a pure managed text transform ([shader(...)] entry discovery, technique synthesis, Slang-only-construct scan), which makes `.slang` input work on **every** host the pipeline works on, browser/WASM included, with zero new natives. The trade, accepted consciously: **Slang-only language features** (`import` modules, generics, `extension`s) are rejected by name (`SD0600`), never silently miscompiled — matching the requester's own framing (*"features not supported in HLSL are likely also not supported in MonoGame"*). Reversible without breakage: if real demand for full-Slang input appears, a bundled-toolchain route can be added additively later (Slang is Apache-2.0 with official Windows/Linux/macOS/wasm builds — the earlier slangc-based frontend was built and worked, and its measured findings are recorded in the Phase 61 doc). The interim slangc route never shipped in any release.
- **Reversed course: chose to build full, packaged-native, slangc-backed `.slang` input as a general product capability, not just the HLSL-compatible subset (owner direction, 2026-09-11).** The reversal followed a [Phase 65](plan/PHASE-65-full-slang-input-spike.md) spike ([PR #221](https://github.com/kaltinril/ShadowDusk/pull/221)) that re-measured the 2026-08-13 findings against real slangc v2026.14.1: 33/33 corpus shaders reached DXC, 32/33 reached the FNA route (the one failure a pre-existing vkd3d-shader SM≤3 loop ceiling, not a Slang-dialect problem) — refuting the SM6-only worry that had been the main technical fear. Real Slang-only syntax (generics/`interface`) was also confirmed to monomorphize into ordinary, working HLSL. The spike's own recommendation was the cheaper (a)+(b) path (fix messaging, ship an author-time-only `slang2fx` CLI) on the grounds of "no demonstrated demand" for arbitrary runtime Slang; the owner overruled that specifically, judging that community interest in "ShadowDusk supports Slang" (already circulating before the messaging gap was even known) plus a **complete** implementation is worth the packaging cost, rather than treating an unmeasured market bet as disqualifying the way an unmeasured technical risk would be. **Packaging shape:** a new standalone package, `ShadowDusk.Slang`, following the `ShadowDusk.ShaderToy` precedent — so the ~121 MB/RID slangc native (§4c of the Phase 65 doc; caveat: 84 MB of that is `slang-llvm.dll`, whose necessity for a `-target hlsl`-only embed is unmeasured and the first thing to shrink) is opt-in, landing only on consumers who add that package, never on every `ShadowDusk.Compiler` consumer. **Non-negotiables carried forward unchanged:** Slang still never becomes a substitute for DXC anywhere in the pipeline (§2.1 of Phase 61, closed on measured evidence); the FX9 technique/pass synthesis convention already shipped in `SlangFrontend.cs`/`SlangEntryScanner.cs` is reused, not rebuilt; and the acceptance rule is Phase 61 §6 A6's — accept whatever real slangc accepts, reject only what MonoGame/KNI/FNA cannot hold, loudly and by name, never approximated. See [Phase 66](plan/PHASE-66-full-slang-input-implementation.md) for the staged implementation plan.
- **Chose to respell slangc's texture objects into DX9 effect syntax on the Slang FNA route, while the `.fx` FNA route REJECTS the same texture objects (issue #230, 2026-10-01).** Measured: a `Texture2D` + `SamplerState` + `T.Sample(S, uv)` pair at an SM3 profile compiles through vkd3d into one texture-typed `S+T` sampler, and real FNA throws `Unhandled sampler state!` when a pass that samples it is applied (a technique in the same file that never samples the texture object did render, and is rejected along with the rest of the file now, as `fxc` does); `fxc /T fx_2_0` refuses the text. The two routes differ on purpose. A `.fx` author can write the DX9 form and `fxc` would reject what they wrote, so the `.fx` route keeps Phase 39's rule (never silently down-translate SM4-style source for FNA) and fails with `SD0303`, naming the DX9 spelling. A Slang author cannot write the DX9 form at all (slangc has no `sampler_state` grammar, Phase 66 A6) and slangc emits texture objects whatever the source says, so the Slang route rewrites exactly that emitted shape (texture, sampler, `Sample(S, uv)` only) into the identical SM3 program and rejects every other texture shape as `SD0627`. `validation/FnaValidation -- slang` proves the respelling renders like `fxc`'s build of the same text (21/21). **Accepted divergence between the two Slang routes:** the built-in HLSL-subset `.slang` frontend in `ShadowDusk.Compiler` hands its body to the ordinary `.fx` pipeline, so textured FNA source through THAT route now fails with `SD0303`, while the same source through `ShadowDusk.Slang` (real slangc) is respelled and compiles. The respelling was kept out of the subset route deliberately: that route hands its body to the `.fx` pipeline unchanged, and putting the rewrite in that shared pipeline would also down-translate hand-written `.fx`, which the Phase 39 rule forbids.
- **Chose slangc's own preprocess-only pass (`slangc -E`) to decide which registers a Slang author wrote, not a scan of the raw source, not a managed preprocessor, and not a differential compile (issue #252 follow-up, 2026-10-01).** The raw-text scan was wrong both ways (a register in an inactive `#if` branch counted; one written through a macro did not). A managed preprocessor would be a second implementation of slangc's `#if`/macro/splice rules that can drift from the compiler that actually resolves them, which is the substitute-component mistake at small scale. A differential compile (add a probe resource and see which registers move) was rejected as unsound, measured: slangc places a resource array in the first gap it fits, so next to an author's `register(t1)` an auto-numbered `Texture2D Arr[4]` sits at `t2` with or without a probe texture declared in front of it, and would be misread as author-bound. `-E` is the same binary, the same macros and the same argument prefix as the compile, and the existing WebAssembly glue answers it byte for byte like native with no rebuild (measured 200/200 over the corpora, error cases included), so both transports agree by construction. Accepted costs: one more slangc run (about 170 ms of process start on Windows, under 1 ms in-process), paid only when the source or a `-D` value could spell `register` at all; and `-E` does not expand `import`/`__include` (measured). **Issue #292 extended the same choice rather than replacing it:** a declaration from another file is judged from slangc's own `-E` over that file (the path slangc's `#line` names, plus quoted-path imports), never from a managed module resolver; an import by module name is NOT followed (that would re-implement slangc's search-path rules). A file's own text is trusted only when the file is provably a module (reached by quoted path, or opening with `module`/`implementing`), because an `#include`d fragment preprocessed on its own can read differently from what slangc compiled under its includer's macros; "trust the `#line` file's text as is" was rejected for that reason (a silent wrong verdict), at the price of `SD0628` for a name-imported file with no `module` declaration. **Cost was a stated constraint (owner, 2026-10-02):** no shape that compiled correctly before may pay an extra slangc run, and the overhead must follow the files that need judging, so the entry source and the `#line`-named files share one `-E` invocation (one line per input, measured), a located declaration stops the reading as soon as its module is trusted, and only a hoisted resource or a fragment reads the whole quoted-import closure (one invocation per level). "Keep every register from a non-`<stdin>` file" was rejected because slangc numbers an imported resource with no author register itself (measured). Hoisted names (`C_texture_0`, `gS_s_0`) map back to the author's global with the register class; see `project_facts.md`.
- **Chose to rename a combined sampler's hoisted texture to the author's global in slangc's HLSL text, and to REJECT a texture hoisted out of any other aggregate (`SD0640`), rather than map it or leave slangc's name (issue #302, 2026-10-02).** The texture half is renamed because that is the one name the author wrote and the measured reference: the hand-written `Texture2D Comb; SamplerState ...` reflects `Comb` through the `.fx` route on every target and `mgfxc` names the legacy `sampler2D Comb` `Comb`. Renaming in the HLSL text (before the `.fx` is assembled) was chosen over a parameter-table rename in the pipeline so the rest of the pipeline stays untouched and every target, the FNA respelling included, sees the declaration an author would write by hand. The sampler half keeps slangc's `Comb_sampler_0`: no author-written name exists for it, `Comb` is taken by the texture, and nothing binds a sampler by name; inventing `CombSampler` would be a convention of ours that can collide with an author global. Struct-held textures: rejected, not mapped. Three alternatives were measured and rejected: leaving `gM_t_0` (the issue's silent defect); mapping a single-texture struct to the global's name `gM` (an invented name the author never wrote for the texture, which collides with the struct's own data parameter the moment the struct holds a float, and turns a working shader into a failing one when a second texture is added); and the `.fx` route's `gM.t`, which is DXC's reflection spelling for the same declarations but cannot be produced by a text rename (no HLSL identifier holds a dot), would need a pipeline hook or re-aggregating slangc's flattened output, and rests on a `.fx` shape `mgfxc` itself rejects (`X3090`) and that the `.fx` route has never render-proven. A hoisted sampler alone (`struct S { SamplerState s; }`) still compiles under slangc's name, because a sampler is never set by name and rejecting it would break shaders that render correctly. **Soundness over cost, cost over convenience:** a name is treated as generated only when the source provably never spells it, because renaming an author's `tex_layer_0` or rejecting it would break a working shader silently; the proof is free in every ordinary case (raw text, or slangc's exact `#line` for an author global), reuses the register pass's `-E` texts when they exist, and pays one extra slangc run only for a combined sampler declared through a macro or a `-D` name. The residual the free proofs cannot cover (a generated name an author also spells as a local or in an inactive `#if`) resolves toward leaving the name as it was, never toward a wrong rename. **Issue #325 (2026-10-02) applied the same test to the register pass:** the hoisted shape counts as a hoist only for a name no read text spells, so a module's own `tex_layer_0` is matched verbatim by the module's text and never through the entry's `tex`. "Treat every hoisted-shaped name located outside slangc's core module as literal" was rejected because slangc's `#line` for a hoisted resource is sometimes a stale `<stdin>` line (measured in issue #302), so location alone does not prove authorship; what the located text spells does.
- **Chose to REFUSE two global declarations of one simple name in different namespaces (or in two modules) as `SD0643`, by declaration, rather than detect the merge in slangc's output, compile with mangling, or scan the raw text alone (issue #323, 2026-10-02).** slangc's `-no-mangle` (kept: it is what makes parameter names reach the effect as written) merges the pair into one declaration, silently, or crashes on constant-buffer members; ShadowDusk never passes silent wrong output through. Alternatives measured and rejected: reading the merge off the emission (impossible: the merged `T` looks like any single global; register gaps are also left by unused parameters and author registers); a second compile without `-no-mangle` to compare names (an extra slangc run for every shader, and a second compiler configuration as an oracle); judging from the raw text alone (wrong on a pair in mutually exclusive `#if` branches, which slangc compiles fine), or always from `-E` (a run for every namespace-using shader with a directive, against the owner's cost constraint). Chosen: the raw text decides when nothing can rewrite it, a raw candidate under a directive is confirmed by one `-E` run (paid only by sources that show a candidate), and the register pass's texts are re-read for free. The pair is refused whether or not both declarations are used, and `static`/`static const` pairs too, because the output is measured wrong (first initializer wins) and a working single-use shader breaks the moment the other side is used. Not covered, by the cost constraint and recorded as issue #337 for an owner decision: pairs no read text shows (macro-formed with no register pass, cross-module with the modules unread).
- **Chose to accept rendered-image fidelity as sufficient evidence for the SkiaSharp/SkSL target (owner direction, 2026-08-13), resolving [Phase 57](plan/PHASE-57-universal-compiler-auto-detection.md) §3 for this case.** Skia has no reference compiler to be equivalent to, so `mgfxc`-equivalence is unavailable *in principle*, not merely unimplemented. The bar instead is: render the emitted SkSL through real SkiaSharp, render the same `.fx` through an already-rung-4-proven backend, and compare the images. This is **not a new evidence model** — it is the one `ShadowDusk.ShaderToy` already ships under (measured 46/46, mean 0.00/255), so the decision keeps the two consistent rather than creating an exception. Two constraints ride with it: **the tolerance cannot be zero** (SkSL defaults to `half` precision and Skia rasterizes differently), and **an image comparison alone is insufficient** — SkSL has no varyings, so a pixel shader reading an interpolant must be **rejected loudly**, never silently converted with the input dropped. That failure is not hypothetical: Gum's own hand-written `Grayscale.sksl` drops the `* input.Color` its `.fx` twin applies.
- **Chose to accept rendered-image fidelity for the raylib target as well (owner direction, 2026-10-01), resolving [Phase 57](plan/PHASE-57-universal-compiler-auto-detection.md) §3 for [Phase 59](plan/PHASE-59-raylib-cs-backend.md) and unblocking it.** Raylib has no reference compiler either, so the bar and its constraints are the SkSL decision's: render the emitted raylib shader in real Raylib-cs, render the same source through an already-rung-4-proven backend, compare images within a non-zero tolerance.
- **Chose a standalone `RaylibConverter` returning a `RaylibShader` (text plus binding contract), not a `PlatformTarget.Raylib` member routed through `EffectCompiler` (Phase 59 A1/A4, 2026-10-01).** Every `PlatformTarget` produces `CompiledShader.Data` that consumers hand to `new Effect(...)`, and raylib's `LoadShaderFromMemory(vs, fs)` takes text with no container, so a GLSL string in that slot would load as garbage rather than fail. The SkSL converter is the precedent, and both now share `Internal/ModernGlslSeam` (Phase 62 OQ3: one seam, two emitters, rather than one phase). Input stays `.fx` text, so `.slang` arrives through the existing Slang frontends with no raylib-specific work.
- **Chose to emit raylib `glsl330` only and defer `glsl100` (Phase 59 A3, 2026-10-01).** The ES 1.00 lowerings are not cheap at this seam (they live inside `MonoGameGlslRewriter`'s 110 dialect), and no harness here can render `#version 100` in raylib: Raylib-cs's desktop native is GL 3.3 with a `#version 330` built-in vertex shader, macOS GL compiles no GLSL ES, and a Mesa run would need a hand-supplied ES vertex shader rather than raylib's own. An emitted-but-unrendered dialect is the unvalidated cell this project avoids; `glsl100` waits for a Raylib-cs `browser-wasm` or GLES harness.
- **Chose the same `.fx` on real MonoGame OpenGL as the raylib oracle, not the analytic math the SkSL tests use (Phase 59, 2026-10-01).** OpenGL is rung-4 proven against `mgfxc`, the comparison stays GL-to-GL (same-backend rule), and it scales to any shader in the corpus instead of only ones whose math is written out by hand. It is measured at maxd 0 on 13 shaders, with three positive controls (dropped tint, flipped V, curvature +0.01) that must diverge so the comparison provably can fail.
- Chose to bound the native loaders' dev-convenience `tools/` walk-up to a directory carrying a repo marker, and to run it AFTER the packaged-native probe, not before and unbounded, because the unbounded form reached the Windows volume root (a `tools/vkd3d/` directory directly under `C:\`), which any local user can create: an uncontrolled search path that both enabled DLL planting across a privilege boundary and could silently displace the pinned, hash-verified native.

- **Chose to convert `COLOR0` to the synthesized uniform `ShadowDusk_Color` BY DEFAULT in the SkSL converter, not to refuse it (`SD0611`) behind a `TreatVaryingsAsUniforms` opt-in (issue #368, owner decision 2026-10-03).** Gum authors one `.fx` for KNI and Skia and every shader it reuses reads `input.Color`, so refusing it by default made the converter unusable on exactly its consumer's shaders. The silent-loss failure the refusal guarded against (Gum's hand port dropped the tint) is still absent: the uniform is in the emission, listed in `SynthesizedUniforms`, and warned (`SD0614`, reused, no new code); Gum's Skia renderer sets it to the container tint, white when untinted. Reused `SD0614` rather than a new informational code because the contract is identical to `ShadowDusk_Resolution`'s. `TreatVaryingsAsUniforms` stays for other semantics and still names them `in_var_<SEMANTIC>`; `COLOR0` in it is a no-op, so older callers keep working (only the uniform's name changed). Both `COLOR0` and bare `COLOR` are treated as index 0; a `COLOR0` read narrower than `float4` is refused (`SD0611`) rather than widened or narrowed silently. Other interpolants still refuse by name. Rejected: folding `COLOR0` into the opt-in as its default value (a hidden list default, and the uniform name would still differ from the other semantics), and typing the uniform `half4` (the SPIRV-Cross body does `vec4` arithmetic on it).

## Process and infrastructure

- Chose a single `<Version>` in `Directory.Build.props`, not per-csproj `PackageVersion` properties, because per-project versions desync and collide by name with Central Package Management items.
- Chose dispatch-only release triggering with a version-input guard, not tag-push triggering, because publishing must be a deliberate human action and a mismatched version should fail before anything is packed.
- Chose to fail the release red when a packed nupkg is missing a native, not to warn, because a stopped release beats shipping the FNA target and `DxbcBackend.Vkd3d` broken for a consumer RID.
- Chose to vendor upstream's own slangc release binaries for the three Unix RIDs (issue #227), not to build slangc ourselves the way the macOS DXC dylibs are built, accepting upstream's macOS 26+ floor for now, because it ships the same pinned compiler on every RID today with no new build pipeline, and the floor fails loudly as `SD0620` instead of crashing. Self-building at `MACOSX_DEPLOYMENT_TARGET=11.0` is deliberately not planned ([issue #237](https://github.com/kaltinril/ShadowDusk/issues/237), closed): it would mean owning a macOS native build and re-baselining `slang-manifest.json` on every Slang pin bump, for zero requests, and `SD0620` already fails loudly and asks the consumer to open an issue. Reopen on a real user request, or when an upstream release lowers its `minos`. A silent fallback to the HLSL-subset frontend on old macOS is rejected: it would make the same `.slang` compile differently per host. The Linux pin is upstream's `glibc-2.27` zip, not the default one, because the default needs `GLIBC_2.34` and the variant needs only `GLIBC_2.17`.
- Chose NOT to bundle slangc for linux-arm64 or win-arm64 (issue #227), although upstream publishes both, because `ShadowDusk.Slang`'s RID set follows the core pipeline's, and the core pipeline is complete on neither. linux-arm64 has no DXC (Vortice.Dxc 3.3.4 ships win-x64/win-arm64/linux-x64 only; we self-build only osx-x64/osx-arm64/android-arm64) and no vkd3d, so slangc there would hand its HLSL to a compiler that cannot load. win-arm64 does have DXC and SPIRV-Cross natives (the OpenGL/Vulkan/DX12 half could load) but no vkd3d (no DirectX 11 or FNA), and no CI lane or measurement proves the core pipeline there. Meanwhile every consumer of the package (framework-dependent builds copy every `runtimes/<rid>/`) carries roughly 30 MB more for it. Those hosts get `SD0620` naming the bundled RIDs instead. Revisit when the core pipeline gains either RID: the linux-arm64 pin would then be upstream's `linux-aarch64-glibc-2.28` zip (sha256 `31c6b049c57881106b9175a1cc45736f1aeec2d5f837908178b988f1c087af09`), which measured `GLIBC_2.17` / `GLIBCXX_3.4.22` and no `slang-llvm`, the lowest floor of any Linux variant.
- Chose to make the real-slangc tests FAIL on a host without a usable slangc, not skip, because a skipped Slang suite reads as coverage that never ran (the soft-skip rule). Host-independent rejections (`SD0602`/`SD0603`/`SD0624`) run before the host check, so their tests are pure and run everywhere.
- **Chose to run the pinned slangc IN-PROCESS where no process can be spawned (issue #257, [Phase 67](plan/PHASE-67-slang-in-process-wasm.md)), linked from upstream's own prebuilt wasm static libraries behind a thin glue that replays slangc's `innerMain`, not upstream's own `slang-wasm.js`, not a from-source slang build, and not "the subset is enough in the browser".** Upstream's module exposes only a session API that takes a target and no flags or macros (no `-no-mangle`, no `-no-hlsl-pack-constant-buffer-elements`, no `-D`), and its session defaults differ from the command line's (`pack_matrix(row_major)`, profile `sm_6_6`): 0/20 corpus entries matched native slangc, which is exactly the "flags don't forward" defect that rejected slang-wasm in Phase 23. The glue hands `SlangcArguments.Build`'s list to slang's own command-line parser verbatim and feeds the source through `stdin`, so the same compiler objects produce the same text: 235/235 identical. Building slang from source would be a second build of the compiler to keep in sync for no measured gain; the libraries are upstream's release artifact at the pin. Slang stays INPUT only (the module emits HLSL; DXC/vkd3d compile it).
- **Chose ONE `SlangCompiler` with an internal in-process seam, not a second browser compiler class that copies the route (issue #257).** The argument list (`SlangcArguments.Build`), the output normalization that reproduces `Process.OutputDataReceived`'s per-line join, the register strip, the merge, the `.fx` assembly and the downstream compile are shared code, so the hosts cannot drift. The seam is `internal` and reachable only by `ShadowDusk.Slang.Wasm` (`InternalsVisibleTo`), so no public API lets a consumer plug a different "slangc" in; that is a convention, not a security boundary, since the assemblies are not strong-named. The browser codes live in the `SD19xx` browser/WASM-host range (`SD1904` load failure, `SD1905` module trap, the existing `SD1903` for a sync compile before init) because they are host conditions (a failure of the browser host, not of the Slang compile), which is what that range is for. The browser code lives in its own project (`ShadowDusk.Slang.Wasm`), not in `ShadowDusk.Wasm`, because the 23 MB module would otherwise ride in every browser consumer's publish output, breaking Phase 66's "no Slang cost unless you add the Slang package".
- **Chose an in-process route for full Slang on Android too, not spawning slangc (issue #257, measured 2026-10-01).** Upstream ships no Android slangc and its Linux build cannot exec on bionic; an Android app can spawn an NDK-built executable only from `nativeLibraryDir`, which holds the file only when native libraries are extracted, and default Release packaging does not extract them. A spawn route would need the consumer to set `AndroidUseLegacyPackaging`, which the seamless directive forbids. A P/Invoked NDK build of slang's library needs no extraction (how DXC and SPIRV-Cross already load there). Not built yet; see Phase 67 §3.3.
- Chose a hard `SHADOWDUSK_REQUIRE_GL` gate over letting headless hosts soft-skip GL tests, because a skip reported as a pass is indistinguishable from real coverage and had already masked three latent failures.
- Chose to gate the PR integration lane behind a `run-integration` label, not run it on every PR, because it is heavyweight and antivirus-scan sensitive.
- Chose to reuse the normal build's CLI binary in `CliBinaryFixture`, not a per-construction `dotnet publish -c Release`, because the cold Release build plus antivirus scan made the suite take 21m43s.
- Chose one collector phase (51) for leftover tails, not leaving parent phases open at 95%, because a phase open for one or two items obscures what is actually done.
- Chose to keep the Phase-41 structural-divergence appendix outside `plan/DONE/`, not archive it with its phase, because `dotnet test` regenerates it on every run, making it a live artifact rather than a record.
- Chose to make the local Windows render gate a hard pre-release requirement, not advisory, because CI structurally cannot produce that evidence and `release.yml` does not check it either.
- **Chose Shouldly over staying on FluentAssertions 7.2.2 (issue #171, 2026-07-30), and banned FluentAssertions outright.** The cap was a licence workaround, not a technical one: 8.x relicensed to the Xceed *"Community License Agreement (for Non-Commercial Use)"*, which requires a paid commercial licence for any organisation that earns revenue, so 7.2.2 (the last Apache-2.0 release) was pinned. But a pin only defers — the 7.x line receives no further fixes, so the real choice was "migrate now" or "migrate later from a frozen, unmaintained dependency", and later is strictly worse. Shouldly is **BSD-3-Clause at every version** with no commercial gate. (Issue #171 says MIT; the package's own nuspec says BSD-3-Clause. Both are permissive and ungated, so the reasoning holds, but BSD-3-Clause is the accurate licence.)
- **Chose to enforce that ban as a written rule, not a scanner test (owner directive, 2026-07-30).** A guard test that greps the repo for `FluentAssertions` and `.Should()` was written and then removed: the failure mode being guarded against is *an author reaching for the familiar API*, and that is addressed by the rule being stated where an author already reads (`project_facts.md`, `project_rules.md`, `CLAUDE.md`, the `Directory.Packages.props` comment). A repo-scanning test buys little over that and costs a permanent maintenance surface, including its own allow-list of files permitted to mention the name.
- **Chose to spell out `Case.Sensitive` on every string `ShouldContain`/`ShouldNotContain`, not to accept Shouldly's default.** Shouldly defaults string containment to `Case.Insensitive`; FluentAssertions' `Contain`/`NotContain` are case-**sensitive**. Taking the default would have silently *weakened* ~900 `ShouldContain` assertions over generated GLSL/HLSL, where case is meaningful (`texCoord` vs `TexCoord`, `vs_v0`, `MainPS`) — a coverage loss that no test failure would reveal. The explicit argument also forces the string overload: `string` is `IEnumerable<char>`, so a two-argument call can otherwise bind the *enumerable* overload instead.
- **Chose to convert `COLOR0` (SpriteBatch's vertex color) to a synthesized uniform by default in the SkSL converter, not to keep refusing it with `SD0611` and not to bake in opaque white (owner direction, 2026-10-03, [issue #368](https://github.com/kaltinril/ShadowDusk/issues/368)).** Gum authors one `.fx` for KNI and Skia, and every example shader reads `input.Color`. A synthesized uniform that Gum's Skia renderer sets to the container tint keeps a tinted container faithful to KNI, where constant white would silently differ. Other interpolants still refuse by name.
- **Chose to convert computed-UV sampling in the SkSL converter by scaling the coordinate with the existing `ShadowDusk_Resolution` uniform, not to keep refusing it (`SD0612`) and not to add a second uniform (owner direction, 2026-10-03, [issue #371](https://github.com/kaltinril/ShadowDusk/issues/371)).** XnaFiddle's Pixelated samples at `round()`-quantized UVs, and `.eval()` takes child pixels where HLSL passes normalized coordinates, so `child.eval((uv) * ShadowDusk_Resolution)` is exact when the uniform is the child's pixel size. That is the same value the arithmetic-UV path already needs (the element and its child are the same size in the 1:1 post-process case), so Gum sets one number; a separate child-size uniform would only make a consumer set two equal values. The meaning is widened from "output size" to "size of the drawn element, which is also the child size". Only a two-argument sample of a bound texture is modelled; a bias or extra argument, an unknown sampler or an unbalanced call stays `SD0612`. HLSL `round` (`roundEven`) gets an exact ties-to-even helper because SkSL has no `roundEven`; `floor(x + 0.5)` was rejected as it differs on ties.
