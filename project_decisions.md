# Project Decisions

Decisions made, with the why - consult before re-litigating anything. One per line: decided X (not Y) because Z.

## Pipeline and backends

- Chose the Option B pipeline (DXC -> SPIR-V -> SPIRV-Cross -> GLSL/MSL), not Option A (FXC/MojoShader), because Option A requires Wine on Linux and macOS and so cannot deliver the reach that justifies the project.
- Chose vkd3d-shader for the DX11 DXBC backend, not DXC, because DXC only emits SM6 DXIL and D3D11 rejects DXIL unconditionally; DXC's DXIL path is retained only for DX12 and KNI.
- Chose vkd3d as the shipping DXBC backend on every OS (default since 0.5.0), not `d3dcompiler_47`, because it makes output host-independent; `d3dcompiler_47` stays an opt-in Windows-only correctness oracle and never ships.
- Chose to keep vkd3d pinned at 1.17, not to track upstream, because output byte-stability is a product promise and a bump re-baselines every golden and re-runs rung 4. Upstream's stubbed fx_2_0 writer stays a background watch, not a dependency.
- Chose our own pinned macOS `libdxcompiler.dylib` loaded via Vortice's `Dxc.ResolveLibrary` event, not `SetDllImportResolver`, because Vortice's assembly already registers a resolver and a second registration throws.
- Chose the pure-managed `RdefReader` for DXBC reflection, not P/Invoking `D3DReflect`, because `D3DReflect` is Windows-only and blocked DX11 end-to-end on Linux and macOS; proven deeply equal to the D3DReflect oracle for both backends with zero `.mgfx` byte change.
- Chose the pure-managed `SpirvReflector` over the DXIL reflection oracle, because the DXIL path was Windows-only and blocked the WASM host; proven equivalent 10/10 with byte-identical `.mgfx` output.
- Chose to un-park Vulkan only when MonoGame 3.8.5 shipped a stable `DesktopVK`, not earlier, because a backend with no validatable consumer runtime cannot reach rung 4; Metal stays parked for exactly that reason, not because the compilation is hard.
- Chose to build DX12 as a genuine new backend, not treat it as a render-validation rung on existing work, because source inspection tripped Phase 52's own decision gate: no `PlatformTarget.DirectX12` existed.
- Chose `RELAX_NAN_CHECKS` on the OpenGL SPIRV-Cross profile to fix issue #149, not a managed rewrite stripping `isnan()`, because flipping the upstream option produced zero byte changes anywhere else in the corpus.
- Chose to own only the container writers, the runtime-dialect adapters, and real-runtime validation, not compiler internals, because HLSL compilation and cross-compilation are multi-year efforts maintained by the people who own the formats, and the validation is the actual moat. (operator, 2026-06-09)
- Chose to treat the browser as a full export station (any host may emit any target), not a WebGL-only compiler, because compile-target and render-backend are independent; the in-browser artifact must be byte-identical to the desktop one, which is the bar for every future host. (operator, 2026-06-09)
- Chose to key the `.mgfx` sampler table on the reflected TEXTURES for DirectX and DirectX 12, on the (texture, sampler) PAIRS for OpenGL, and on the reflected SAMPLERS for Vulkan, not one rule for all, because each runtime binds differently: mgfxc keys its DX table on the texture's bind point (so a sampler-keyed table drops textures sharing one `SamplerState`); GL binds by NAME and the record must name a `ps_s{k}` uniform the emitted GLSL declares, which is one per pair; Vulkan binds through the descriptor layout on raw SPIR-V bindings that the binding rewriter has already co-located per pair. Only the pair list can be right for GL, and neither reflected list is it. The 1:1 case is byte-identical under any of the three rules. (Phase 51 A7, 2026-07-29; superseded the earlier sampler-keyed GL rule and its `SD0215`/`SD0216` rejections.)
- Chose to derive the GL combined-sampler pair list in pure managed code from the SPIR-V (`SpirvCombinedSamplerPairs`), not by reading `spvc_compiler_get_combined_image_samplers` on the desktop, because `spirv-cross.wasm` exports 11 functions and that is not one of them: a native call would fix the desktop path only and break CLI-vs-WASM byte identity for the shape. Reading it off the emitted GLSL is also impossible, because SPIRV-Cross's readable `SPIRV_Cross_Combined<Image><Sampler>` name is applied by its command-line tool rather than by the pass, so through the C API the uniforms arrive as bare `_<id>` with no pair identity. The ordering rule is transcribed from the pinned SPIRV-Cross tree, and an internal cross-check against the sampler uniforms the emitted GLSL actually declares (`SD0217`) is what catches a drift from it. (Phase 51 A7, 2026-07-29)
- Chose to number the GL `ps_s{slot}` uniforms and their `.mgfx` records by the pair's HLSL DECLARATION index, not by the pair's position in SPIRV-Cross's first-use list, because that is how fxc (and therefore mgfxc) allocates OpenGL sampler slots. Measured on three shapes against the pinned mgfxc, including one with every `register` annotation stripped: declaration order in all of them, so the rule is not merely "honour `register(sN)`". The constraint the earlier decision was protecting (the record must name a uniform *our own* GLSL declares) is preserved by numbering BOTH from one shared `SpirvCombinedSamplerPairs.ResolveSlots` rather than by conceding the numbering to SPIRV-Cross. **This supersedes the A7-era position that ShadowDusk had to follow SPIRV-Cross's first-use numbering and that the divergence was behaviorally invisible** — it was not: `SpriteBatch` owns unit 0, so a `register(s0)` sampler that was not sampled first read the sprite. The evidence that had been cited for "invisible" (`validation/SamplerPairsGl` arm B, maxd 0) could not support it, because that arm gives its two textures identical pixels by design. Where two pairs share one texture their declaration indices collide and there is no mgfxc golden for the shape, so `ResolveSlots` falls back to positional numbering rather than inventing an answer. (GitHub issue #189, 2026-08-02; rung-4 proved by `validation/SamplerRegisterOrderGl`.)
- Chose to model fxc's OpenGL sampler-register ALLOCATOR rather than to special-case declaration forms: in texture-declaration order, a pair whose sampler declared an explicit register takes it, and every other pair takes the lowest register neither already taken nor reserved by a modern `SamplerState : register(sN)`. One rule, verified against the pinned mgfxc on 10 shapes. It removes what looked like an arbitrary asymmetry: at `ps_3_0` a texture and a sampler are ONE object in ONE register namespace, so a legacy `sampler X : register(sN)` IS the combined object and lands on N, while a modern `SamplerState` is a sampler-only object that occupies its register and forces the synthesized combined samplers around it (one texture + `S : register(s0)` yields `ps_s1`, not `ps_s0`). A superseded earlier reading of this — "mgfxc simply ignores modern registers on OpenGL" — was drawn from too few samples and was wrong; it is corrected here rather than left in place. (GitHub issue #189, 2026-08-02.) Superseded detail, kept because the measurement stands: `mgfxc` emits `ps_s2` at unit 2 for `sampler X : register(s2);` (at `ps_3_0` the legacy sampler IS the combined sampler, so the clause pins its SM3 register), but for `Texture2D T : register(t3); SamplerState S : register(s2);` its OpenGL build puts the pair on unit 0 regardless, allocating by texture declaration order. Honouring modern registers would therefore be a divergence, so both behaviours are pinned by tests that fail if either is "corrected" later. The clause is RECORDED in `FxParseResult.ExplicitGlSamplerSlots` rather than re-emitted into the rewritten HLSL, because re-emitting it would change what DXC compiles and move the DirectX/DX12/Vulkan/FNA bytes for a defect none of them have. (GitHub issue #189 sparse half, 2026-08-02; rung-4 proved by `validation/SamplerRegisterOrderGl` arm "sparse".)
- Chose to rank a combined sampler's declaration index by SPIR-V MODULE order rather than by its `Binding` decoration, because the two agree only while DXC auto-allocates: once the source carries explicit registers the binding equals REGISTER order, and `mgfxc` allocates by DECLARATION order. Measured: for `Texture2D TexA : register(t3); Texture2D TexB : register(t2);` mgfxc puts TexA (declared first) on unit 0, where a binding-ordered rank puts TexB. This was a pre-existing divergence the first #189 fix inherited, found by an adversarial "modern registers must NOT be honoured" test rather than by any render. (GitHub issue #189, 2026-08-02)
- Chose to leave DirectX 11 and Vulkan sampler-slot allocation alone while fixing the OpenGL one, even though both also ignore `register(sN)`, because each is internally consistent with its own binding mechanism and no failure is reported against either: on DX11 fxc itself auto-assigns `t` registers by first use (measured — mgfxc puts the *second*-declared sampler's texture on `t0`), so matching the annotation there would move us AWAY from the reference compiler, and Vulkan binds through a descriptor layout rather than by slot number. The DX11 sampler-slot divergence (we emit 0/1 where mgfxc emits the declared 2/3) is recorded as a measured, unfixed divergence rather than silently corrected, because changing it would require re-proving two rung-4 backends for no reported symptom. (GitHub issue #189, 2026-08-02)
- Chose to keep naming the GL texture parameter after the TEXTURE (`DiffuseMap`), not to adopt mgfxc's MojoShader `<sampler>+<texture>` combined spelling (`TextureSampler+DiffuseMap`), even though mgfxc's own OpenGL goldens use the latter for every modern-syntax shader. Three reasons: MonoGame resolves a sampler's texture through the record's `Parameter` **index**, never the name (`EffectPass.SetShaderSamplers` does `_effect.Parameters[sampler.parameter]`), so the two spellings are behaviorally identical; renaming would break every existing consumer's `Parameters["DiffuseMap"]` lookup, which the backwards-compatibility directive forbids; and ours is the same name the DX, DX12, Vulkan, and FNA targets use, so one game's code works on every backend, whereas mgfxc's spelling is GL-only and makes an effect's parameter names backend-dependent. "Same as mgfxc" is behavioral equivalence plus `Effect`-loadability, not byte identity, so this is inside the promise. (Phase 51 A7, 2026-07-29)
- Chose to make `RuntimeProfileDetector.Recommend` throw for a target no `CapabilityProfile` models, not return the OpenGL profile, because a set `Profile` overrides `CompilerOptions.Target`: the fall-through silently compiled Vulkan/DX12/Metal to a GL artifact the consumer's runtime cannot load. Setting `Target` directly with `Profile` left null stays the supported path.
- Chose pipeline-side SYNTHESIZED register backing for the issue-#187 phantom-parameter class (a reflected numeric parameter whose only reads DXC's `-spirv` backend folds away, dropping its cbuffer from the SPIR-V), not won't-fix, not reflecting from the shipped SPIR-V, and not a DXC flag. Reflecting from shipped SPIR-V (`SpirvReflector`) removes the parameter NAME and was already tried and reverted (PR #186) — name presence is consumer-load-bearing (ShaderFiddle.Web keys ShaderToy detection on it); `-fspv-preserve-bindings` does not exist in the pinned DXC 1.7.2212.40 (a 1.8.x flag — re-evaluate at the DXC pin bump the DX12 `maxd 1` gap already motivates); won't-fix leaves ShadowDusk's own output structurally self-inconsistent and the regression test unwritable. Synthesis completes the one-directional layout→parameter join on our side of the compiler boundary (the blessed `D3d9BytecodePatcher` pattern), reproduces the mgfxc golden's exact structure for the one known member, matches the shape real mgfxc's DirectX profile ships for dead uniforms, and changed one pre-existing corpus output. Sized by the runtime's transposed matrix write model (Columns registers), never Rows — MonoGame/KNI `ConstantBuffer.SetParameter` writes `ColumnCount` 16-byte rows, so Rows-sizing crashes the first `EffectPass.Apply` on non-square matrices. (issue #187, 2026-08-01)

## Output format and compatibility

- Chose MGFX v10 as the default, not v11 or KNIFX, because v10 is the one format both MonoGame 3.8.2+ and KNI load, making it the most backwards-compatible choice.
- Chose to ship MGFX v11 and KNIFX as additive opt-ins (`CompilerOptions.MgfxVersion`, `CompilerOptions.Container`), not as a default or a required flag, because the consumer must never pick a version to get correct output. The old `--mgfx-version 11` was corrupt (v10 body with a v11 version byte) and was fixed rather than kept.
- Chose to emit raw `.mgfx` from core, not `.xnb`, because wrapping is the content-pipeline layer's job; a hand-rolled XNB writer would be the first divergence from `mgfxc` parity and would duplicate and risk desyncing the Phase 29 plugin's validated envelope. Re-open only as a deliberate, explicitly-scoped feature if a downstream (e.g. XnaFiddle project export) needs pre-wrapped `.xnb`. (2026-06-08)
- Chose to emit `mgfxc`'s `#define ps_oC0 gl_FragColor` form, not a raw `gl_FragColor` write, because KNI's HiDef runtime converter only rewrites that form, so one artifact serves Reach and HiDef with no consumer flag and is strictly more `mgfxc`-faithful.
- Chose to emit the correct full uniform-array layout, not `mgfxc`'s compacted MojoShader layout, because `mgfxc` + MonoGame GL is itself broken for statically-partially-read arrays.
- Chose `PlatformTarget.Fna` as a fully separate `RunFnaAsync` pipeline emitting a raw `.fxb`, not a variant of the `.mgfx` path, because a separate pipeline cannot change existing GL or DX output; the additive-and-cannot-regress property is the point.
- Chose vkd3d on every host for FNA output, never the `d3dcompiler` oracle, because that keeps the shipped bytes host-independent; `fxc /T fx_2_0` is a Windows test oracle only.
- **MGCB integration is the content-processor PLUGIN (`ShadowDusk.MgcbPlugin`), not a PATH-based `mgfxc` drop-in.** The original decision chose "Tier 1" (a drop-in binary named `mgfxc` on `PATH`) over a plugin, on the belief that MGCB shelled out to `mgfxc`. **That premise was measured false** (2026-07-28, Phase 52 Area E): `dotnet mgcb` compiles `.fx` in-process at 3.8.2.1105, 3.8.4.1, and 3.8.5 alike and launches no external `mgfxc` (a logging `mgfxc.exe` first on `PATH`: zero invocations, valid `.xnb` each time), so there was never a process for a PATH alias to intercept. [Phase 29](plan/DONE/PHASE-29-mgcb-content-processor-plugin.md) built the plugin (2026-07-31) and it is now the supported native route; the CLI-plus-`/copy:` route and runtime compilation remain valid and documented. The CLI is still a faithful `mgfxc` drop-in for anything that really does invoke `mgfxc` — that is just not MGCB.
- Chose to make the MGCB plugin a **TOOLS-ONLY package** (everything under `tools/net8.0/any/`, no `lib/`), not a normal library package, because MGCB's `/reference:` takes a path to an assembly and resolves that assembly's dependencies from its own directory: a `lib/`-shaped package would put the plugin somewhere its ShadowDusk and Vortice dependencies are not, and would also flow a build-time content-pipeline plugin into the consumer's shipped game assembly. `DevelopmentDependency` + `SuppressDependenciesWhenPacking` make that explicit. (Phase 29, 2026-07-31)
- Chose to give the MGCB plugin its own `AssemblyLoadContext.ResolvingUnmanagedDll` fallback rather than changing ShadowDusk's existing native loaders, because the problem is host-shaped, not loader-shaped: inside MGCB, `AppContext.BaseDirectory` and `NATIVE_DLL_SEARCH_DIRECTORIES` both point at MGCB, so every existing probe legitimately misses. `ResolvingUnmanagedDll` is the runtime's LAST resort, so the shim can never displace a native the normal loaders found, and it changes nothing outside an MGCB host. It loads the same pinned natives, so it is a lookup path and not a substitute compiler. (Phase 29, 2026-07-31)
- Chose to exempt `ShadowDusk.MgcbPlugin` from the no-MonoGame guard **by name, with a second test pinning `IncludeAssets="compile" PrivateAssets="all"`**, not to weaken or delete the guard, because an MGCB plugin cannot exist without the `ContentImporter`/`ContentProcessor` contract while the guard's real concern (a MonoGame assembly shipping inside a ShadowDusk package, or a MonoGame dependency edge reaching a consumer) still has to hold. The exemption is the reference existing; the two attributes are what make it harmless. (Phase 29, 2026-07-31)
- Chose to pin the golden-generation `mgfxc` to the `dotnet-mgcb` version in `.config/dotnet-tools.json` and assert the MGFX version byte it writes, not to take the newest `mgfxc` on the machine, because the goldens are canonical v10 and "newest" resolved to two different broken answers at once: mgfxc 3.8.5 emits **v11** (0 of 46 goldens matched), and the `dotnet-mgcb-editor-windows` 3.8.4.1 `mgfxc.exe` cannot run at all (ships without `SharpDX.D3DCompiler.dll`). mgfxc 3.8.2.1105 and 3.8.4.1 reproduce all 46 goldens byte-for-byte, so the pin is a verified range, not a magic build. (2026-07-28, Phase 52 Area C)

## Scope and product shape

- Chose to treat `.fx` compilation as same-trust-domain, not untrusted input, because compiling a shader you chose to run is like compiling copied C++ or C#; the earlier path-traversal, size-limit, and macro-validation findings were removed as not-real-harm rather than answered with input-validation theater. (2026-06-12, closed by `SECURITY.md` 2026-06-15)
- Chose a synchronous `CompilationPipeline.Run` core with `CompileAsync` as a thin shell over it, not two pipelines, because sync and async output must be byte-identical by construction rather than by test; the only genuinely async work is the one-time WASM module load.
- Chose to publish `ShadowDusk.ShaderToy` as a standalone NuGet from 0.9.0, not to leave it unpackaged as originally deferred, because it is pure-managed with zero native dependencies and purely additive to the pipeline, so shipping it costs nothing.
- Chose to judge the ShaderToy frontend by pixel-fidelity against the original GLSL, not by mgfxc-equivalence, because `mgfxc` never compiles ShaderToy GLSL and so provides no oracle; calling it an mgfxc-equivalence proof would be dishonest.
- Chose to fold the MonoGame `ShaderToyEffect` runtime helper into `samples/ShaderToyViewer` as a single source file, not to keep (or resurrect) a shared `ShadowDusk.ShaderToy.Runtime` project, because a project by that name looks like a shippable `ShadowDusk.*` package and invites exactly the MonoGame-in-product mistake `NoMonoGameInProductLibrariesTests` exists to prevent; its one other consumer (the out-of-band render-proof driver) source-links the file instead. Revisit only if a third MonoGame consumer of the helper appears. (Phase 51 A4, 2026-07-31)
- Chose build-time precompile to `.mgfx` as the documented default for shipping Android games, not on-device compile, because build-time works today with zero Android-specific work; on-device stays additive reach.
- Chose to vendor Gum and Apos.Shapes shaders verbatim as fixtures, not to synthesize approximations, because the real third-party shaders surfaced real gaps our own corpus could not (the Gum FnaSample shader is what exposed Phase 41 GAP-1).
- Chose to resolve `#include` paths exactly as the host file system does and to WARN (`SD0008`) when a case-only mismatch resolved anyway, not to add the case-insensitive resolution fallback bug-hunt M12 proposed for Linux, because a fallback would open a file the file system says does not exist, is ambiguous wherever two real case twins live side by side, and hides a build break the author is about to ship to Android at the one moment they could still fix it. The comparer that decides whether two spellings are one file asks an injectable `IIncludePathCanonicalizer` rather than checking the OS, with **ordinal as the default and case-insensitivity as the exception**: wrongly merging two paths suppresses a header or invents a cycle, while wrongly separating two spellings of one file only costs a duplicated expansion the cycle check still terminates. (Bug-hunt N17 + M12, 2026-07-31)
- Chose to bound the native loaders' dev-convenience `tools/` walk-up to a directory carrying a repo marker, and to run it AFTER the packaged-native probe, not before and unbounded, because the unbounded form reached the Windows volume root (a `tools/vkd3d/` directory directly under `C:\`), which any local user can create: an uncontrolled search path that both enabled DLL planting across a privilege boundary and could silently displace the pinned, hash-verified native.

## Process and infrastructure

- Chose a single `<Version>` in `Directory.Build.props`, not per-csproj `PackageVersion` properties, because per-project versions desync and collide by name with Central Package Management items.
- Chose dispatch-only release triggering with a version-input guard, not tag-push triggering, because publishing must be a deliberate human action and a mismatched version should fail before anything is packed.
- Chose to fail the release red when a packed nupkg is missing a native, not to warn, because a stopped release beats shipping the FNA target and `DxbcBackend.Vkd3d` broken for a consumer RID.
- Chose a hard `SHADOWDUSK_REQUIRE_GL` gate over letting headless hosts soft-skip GL tests, because a skip reported as a pass is indistinguishable from real coverage and had already masked three latent failures.
- Chose to gate the PR integration lane behind a `run-integration` label, not run it on every PR, because it is heavyweight and antivirus-scan sensitive.
- Chose to reuse the normal build's CLI binary in `CliBinaryFixture`, not a per-construction `dotnet publish -c Release`, because the cold Release build plus antivirus scan made the suite take 21m43s.
- Chose one collector phase (51) for leftover tails, not leaving parent phases open at 95%, because a phase open for one or two items obscures what is actually done.
- Chose to keep the Phase-41 structural-divergence appendix outside `plan/DONE/`, not archive it with its phase, because `dotnet test` regenerates it on every run, making it a live artifact rather than a record.
- Chose to make the local Windows render gate a hard pre-release requirement, not advisory, because CI structurally cannot produce that evidence and `release.yml` does not check it either.
- **Chose Shouldly over staying on FluentAssertions 7.2.2 (issue #171, 2026-07-30), and banned FluentAssertions outright.** The cap was a licence workaround, not a technical one: 8.x relicensed to the Xceed *"Community License Agreement (for Non-Commercial Use)"*, which requires a paid commercial licence for any organisation that earns revenue, so 7.2.2 (the last Apache-2.0 release) was pinned. But a pin only defers — the 7.x line receives no further fixes, so the real choice was "migrate now" or "migrate later from a frozen, unmaintained dependency", and later is strictly worse. Shouldly is **BSD-3-Clause at every version** with no commercial gate. (Issue #171 says MIT; the package's own nuspec says BSD-3-Clause. Both are permissive and ungated, so the reasoning holds, but BSD-3-Clause is the accurate licence.)
- **Chose to enforce that ban as a written rule, not a scanner test (owner directive, 2026-07-30).** A guard test that greps the repo for `FluentAssertions` and `.Should()` was written and then removed: the failure mode being guarded against is *an author reaching for the familiar API*, and that is addressed by the rule being stated where an author already reads (`project_facts.md`, `project_rules.md`, `CLAUDE.md`, the `Directory.Packages.props` comment). A repo-scanning test buys little over that and costs a permanent maintenance surface, including its own allow-list of files permitted to mention the name.
- **Chose to spell out `Case.Sensitive` on every string `ShouldContain`/`ShouldNotContain`, not to accept Shouldly's default.** Shouldly defaults string containment to `Case.Insensitive`; FluentAssertions' `Contain`/`NotContain` are case-**sensitive**. Taking the default would have silently *weakened* ~900 `ShouldContain` assertions over generated GLSL/HLSL, where case is meaningful (`texCoord` vs `TexCoord`, `vs_v0`, `MainPS`) — a coverage loss that no test failure would reveal. The explicit argument also forces the string overload: `string` is `IEnumerable<char>`, so a two-argument call can otherwise bind the *enumerable* overload instead.
