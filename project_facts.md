# Project Facts

Source of truth for statements about the project. One short fact per line. Update in place; delete facts that become false.

## What ShadowDusk is

- ShadowDusk is a cross-platform HLSL shader compiler for MonoGame, KNI, and FNA, delivered as a drop-in `mgfxc` replacement.
- The product is the in-memory library (`IShaderCompiler.CompileAsync(fx) -> .mgfx bytes`); the CLI and the MGCB plugin are delivery shapes of it.
- The browser/WASM shader-fiddle is only a sample of reach, never the product; sample work must not redefine the goal.
- "Works" means the real-engine render proof (the evidence ladder in CLAUDE.md, rung 4), not a green test suite.
- "Same as `mgfxc`" means behaviorally equivalent and `Effect`-loadable, never byte-identical; byte-identity with `mgfxc` is an explicit non-goal.
- Determinism means ShadowDusk-vs-itself: same version + same source + same target = same bytes, on every host, for the targets the cross-host byte-identity manifest covers (OpenGL, DirectX_Vkd3d, FNA); DirectX 12 is the one carve-out, because its DXIL signing is Windows-only.
- Repository is github.com/kaltinril/ShadowDusk; the owner/operator is Jeremy Swartwood (GitHub `kaltinril`).
- Ships as ten NuGet packages (`ShadowDusk.{Core,HLSL,GLSL,ShaderToy,Slang,Compiler,Cli,Wasm,MgcbPlugin,ContentPipeline}`) at one shared version, plus the `ShadowDuskCLI` dotnet tool.
- `ShadowDusk.Metal` is a stub, not a shipped package.
- The two build-time delivery-shape projects are the ONLY `src/` projects allowed to reference MonoGame, because the `ContentImporter`/`ContentProcessor` contract IS their seam: `ShadowDusk.MgcbPlugin` (Phase 29, the `.mgcb`/MGCB plugin; its reference is `IncludeAssets="compile" PrivateAssets="all"`, so no MonoGame assembly ships beside it and no MonoGame dependency edge reaches a consumer) and `ShadowDusk.ContentPipeline` (Phase 63, issue #203, the same five source files as a `lib/net8.0` library for MonoGame 3.8.5's Content Builder project; its reference is a REAL dependency, deliberately, because a Builder project needs the edge and the runtime assets). `NoMonoGameInProductLibrariesTests` exempts exactly those two by name, pins the plugin's two attributes, pins the library's edge as NOT private/compile-only, and pins that the library's `<Compile Include>` set equals the plugin's `.cs` file set. The exception does not weaken the guard: its concern was MonoGame reaching a *game* through a ShadowDusk *compiler* package, and a Content Builder is build-time tooling like MGCB; the shipped compiler libraries (`Core/HLSL/GLSL/Compiler/ShaderToy/Wasm`) stay MonoGame-free.
- The C# namespace of the importer/processor pair is `ShadowDusk.ContentPipeline` in BOTH packages (moved from `ShadowDusk.MgcbPlugin` in Phase 63; the plugin's assembly name and `tools/net8.0/any/` path are untouched). Safe because MGCB's `PipelineManager` resolves `/importer:`/`/processor:` by simple `Type.Name` and the 3.8.5 Builder matches `DefaultProcessor` the same way - measured green on `dotnet-mgcb` 3.8.4.1 and 3.8.5 after the move; no released consumer referenced the C# namespace (the tools-only package could not be referenced from C#, which is the whole issue #203).
- The `ShadowDusk.MgcbPlugin` package is **tools-only**: no `lib/`, everything under `tools/net8.0/any/` (~81 MB, the pinned DXC/SPIRV-Cross/vkd3d natives for every RID). MGCB's `/reference:` takes a path to an assembly and resolves that assembly's dependencies from its own directory, so the plugin and everything it needs must sit in one directory a consumer can point at. It is `DevelopmentDependency`, packs with `SuppressDependenciesWhenPacking`, and is packed **without** `-p:IncludeSymbols` (a package with no build output fails `NU5017` trying to build a `.snupkg`).
- **MonoGame 3.8.5's Content Builder is ordinary C# the consumer owns** (`MonoGame.ContentBuilder.CSharp` template, a console project referencing `MonoGame.Framework.Content.Pipeline` 3.8.5 + `MonoGame.Framework.Native`), so it needs the importer/processor as a compile-time reference, which only the library-shaped `ShadowDusk.ContentPipeline` gives it. Measured 2026-09-09 against the real 3.8.5 package and `v3.8.5` source (Phase 63): `ContentBuilderHelper.LoadAssemblies` `Assembly.Load`s every transitively referenced assembly (skipping `System.*`) and calls `GetTypes()` on each **with no guard** (MGCB's own `PipelineManager` guards the same scan), so one unloadable type anywhere in a consumer's graph kills the whole build - which is why `Vortice.Direct3D12` left `ShadowDusk.HLSL` and `DependencyGraphScanTests` reproduces the walk; the 3.8.2.1105-compiled pair binds in the 3.8.5 process; `Include` with no instances auto-discovers by extension and picks MonoGame's stock pair silently (instances must be passed); `BuildConfiguration` is always `""` there (so `DebugMode.Auto` optimizes); processor parameters are C# properties on the instance and take part in the per-asset cache hash; the stock 3.8.5 `EffectProcessor` compiles in-process (bundled DXC 1.8.2505 + MojoShader) and writes **MGFX v11**, so a render oracle for its output must be a 3.8.5 runtime.

## The drop-in contract

- Drop-in means the whole `mgfxc` surface: same CLI flags, same `.mgfx` output format, same exit codes, and stderr diagnostics in a format MGCB can parse.
- **ShadowDusk writes the content-pipeline `.xnb` itself** (Phase 60, issue #199, 2026-08-13; render-proven on every consumer family by [Phase 64](plan/DONE/PHASE-64-xnb-fna-kni-content-load-proof.md), 2026-09-09): `CompiledShader.ToXnb()` on the library, or an `.xnb` output path on the CLI (extension-driven, no flag). The consumer keeps `Content.Load<Effect>("Foo")` and changes no code; MGCB is not involved. A container only — the payload is the same proven `.mgfx`/`.knifx`/`.fxb` bytes, wrapped. The XNB **platform byte is derived from the target** (`OpenGL`→`'d'`, `DirectX`→`'w'`, `DirectX12`→`'G'`, `Vulkan`→`'V'`, `Fna`→`'w'`, matching what `dotnet-mgcb` 3.8.4.1/3.8.5 writes for DesktopGL/Windows/WindowsDX12/DesktopVK), and MonoGame's, KNI's and FNA's `ContentManager` all validate it only for *whitelist membership*, never against the running platform (measured: a GL payload as `'w'`/`'b'`/`'G'` loads on MonoGame and KNI; FNA's smaller list — no `'V'`/`'G'`/`'b'` — is why the FNA target maps to `'w'`, and an unlisted byte on FNA does not throw at the byte but falls to FNA's raw-asset path and fails in MojoShader with `Not an Effects Framework binary`). **The type-reader manifest is the XNA-4.0 name** (`Microsoft.Xna.Framework.Content.EffectReader, Microsoft.Xna.Framework.Graphics, Version=4.0.0.0, Culture=neutral, PublicKeyToken=842cf8be1de50553`, what KNI's own pipeline and XNA write), NOT the mgcb-shaped one (`…, MonoGame.Framework, Version=3.8.4.1, …`) Phase 60 first emitted: **KNI ≤ 4.2.9001 cannot load the mgcb-shaped name** (nor any stock-mgcb effect `.xnb`) — KNI's `ContentTypeReaderManager.ResolveReaderType` appends its own assembly name to the stripped `…EffectReader, MonoGame.Framework` and `Type.GetType` throws `FileLoadException: The given assembly name was invalid.` before its `MonoGame.Framework` fallbacks run; KNI 4.3.9001 catches it and loads. The version/token values are inert on every runtime; the shape is load-bearing (MonoGame strips the version only when `PublicKeyToken` is present; FNA requires the full Version/Culture/PublicKeyToken triple). The mgcb-shaped string never shipped in a release. **Rung-4 proven, maxd 0 everywhere:** MonoGame WindowsDX (`validation/XnbContentLoad`) and DesktopGL (`validation/XnbContentLoadGl`, 3.8.2.1105; probe also 3.8.1.263 and 3.8.5); KNI 4.2.9001 and 4.3.9001 SDL2.GL with v10 AND KNIFX payloads (`validation/KniXnbContentLoad`, which also pins that stock mgcb output is rejected on 4.2); FNA 26.06 (the `.xnb` arm of `validation/FnaValidation`, 17/17 within 4/255 of the fxc oracle). MGFX v11 (`--target-runtime monogame-gl-v11`) in an `.xnb` is a MonoGame-3.8.5-only container and KNI rejects it by design. `SpriteEffect.fx` (`TECHNIQUE()` macro, GAP-1) cannot be in the GL-based gates. The CLI warns (`SD0029`) when an `.xnb` is written with the implicit `DirectX_11` default, because a DesktopGL/KNI-GL game rejects that payload with a message naming neither the profile nor the tool; never an error, never a required flag. The MGCB plugin route on KNI ≤ 4.2 is unmeasured and inherits MGCB's mgcb-shaped manifest (validation-matrix §7).
- MGCB compiles `.fx` **in-process** and never launches an external `mgfxc`, so a PATH-based `mgfxc` override does not route a `.mgcb` build through ShadowDusk. Measured 2026-07-28 against `dotnet mgcb` 3.8.2.1105, 3.8.4.1, and 3.8.5 (a logging `mgfxc.exe` first on `PATH`: zero invocations, valid `.xnb` each time); no `mgcb`/`Content.Pipeline` assembly in any of the three references `mgfxc` or `MGFXC_WINE_PATH`. Native MGCB integration is the **`ShadowDusk.MgcbPlugin` content-processor plugin** (Phase 29, 2026-07-31); the CLI-plus-`/copy:` route and runtime compilation still work and remain documented.
- MGCB DOES load a `/reference:`d plugin assembly by reflection (`Assembly.LoadFrom` + attribute scan for `[ContentImporter]`/`[ContentProcessor]`), and MonoGame's own effect `ContentTypeWriter` serializes a plugin-produced `CompiledEffectContent` into a byte-identical `.xnb` envelope. Measured on `dotnet mgcb` 3.8.2.1105, 3.8.3, 3.8.4, 3.8.4.1, and 3.8.5. A plugin compiled against the `MonoGame.Framework.Content.Pipeline` **3.8.2.1105** contract loads into all of them (that version is a floor, not a pin) - but only the TYPE contract is stable across 3.8.x: **MonoGame renumbered `TargetPlatform` in 3.8.5** (`Stadia=12, Web=13` became `Web=12, DesktopVK=13, WindowsDX12=14, XboxSeries=15`), so anything compiled against the older enum that keys on members sees the wrong platform on a 3.8.5 host. `MgcbPlatformMap` therefore keys on `platform.ToString()` (the host's own enum names it), which is also what lets `DesktopVK` and `WindowsDX12` derive Vulkan / DirectX 12 seamlessly on 3.8.5 (Phase 63 Area B, 2026-09-09; the member-keyed map shipped through 0.18.0 and built an OpenGL payload for `/platform:DesktopVK`).
- A plugin loaded into MGCB cannot find ShadowDusk's natives by any of the normal mechanisms: `AppContext.BaseDirectory` is MGCB's directory and `NATIVE_DLL_SEARCH_DIRECTORIES` comes from MGCB's `deps.json`. `ShadowDusk.MgcbPlugin`'s `PluginNativeLibraryResolver` hooks `AssemblyLoadContext.Default.ResolvingUnmanagedDll` (the last-resort hook, so it can never displace a native the normal loaders resolved) and probes its own install directory. Without it a real `.mgcb` build fails `SD0103 SPIRV-Cross native library not found`.
- **DXC needs an EARLIER hook than the last-resort one inside MGCB** (Phase 63, measured 2026-09-09 on real `dotnet-mgcb` 3.8.5). Vortice.Dxc's resolver probes `AppContext.BaseDirectory/runtimes/<rid>/native` (a miss in MGCB), then polls its public `Dxc.ResolveLibrary` subscribers (first non-zero wins), then falls back to a BARE-NAME load that walks the OS `PATH`. Two consequences shipped through 0.18.0: on a box with a `dxcompiler.dll` on `PATH` (the Vulkan SDK puts one there) every MGCB build through the plugin compiled with **that** DXC, a silent substitute compiler (the DirectX 12 bytes differed from the CLI's; the corpus's GL/Vulkan SPIR-V happened to match); and even with the pinned DXC loaded, DXC's own internal `LoadLibrary("dxil.dll")` never reaches any .NET hook, so **DirectX 12 through MGCB was unsigned** (DXC warns "DXIL signing library not found"). The fix is now `DxcLoader` itself (issue #270): it probes beside the ShadowDusk assemblies (the plugin directory in MGCB), checks the pair is the pinned build, loads `dxil.dll` then `dxcompiler.dll` by absolute path and answers `Dxc.ResolveLibrary` first; the plugin's own Phase 63 DXC hook (`PluginNativeLibraryResolver.ResolveDxc`, no identity check, never consulted once `DxcLoader` went first) was removed, and the plugin resolves only `spirv-cross` and `vkd3d-shader`; `validation/MgcbPlugin` runs the plugin-arm MGCB with a decoy `dxcompiler.dll` **and `dxil.dll`** first on the child's `PATH` (a bare-name load takes them: DXC dies at `DxcCreateInstance`, or DX12 comes out unsigned) and requires DX12 payloads to equal the CLI's signed bytes.
- `MonoGame.Framework.Content.Pipeline` 3.8.2.1105 declares **no dependency on `MonoGame.Framework`**, yet `ContentProcessorContext.TargetProfile` returns `GraphicsProfile` from it, so anything subclassing `ContentProcessorContext` must reference MonoGame.Framework itself. It also ships `mgfxc.dll` as a *contentFiles* asset, which is why `mgfxc` is present next to MGCB without ever being invoked.
- MonoGame 3.8.5 split `mgfxc` into its own `dotnet-mgfxc` tool package (it used to ship inside `dotnet-mgcb` and `dotnet-mgcb-editor-windows`), and moved MGCB's own effect compilation from SharpDX `D3DCompiler` to bundled DXC + MojoShader native tool packages. 3.8.5's new code-centric Content Builder is a C# project over `MonoGame.Framework.Content.Pipeline` and has no external-tool seam either.
- The CLI and the WASM library produce byte-identical output; only the invocation differs, and `IShaderCompiler` abstracts both.
- `dotnet publish -r <rid> --self-contained` must produce a working single-file CLI that bundles every native dependency.

## Packaging and WASM interop

- WASM interop uses `[JSImport]`/`[JSExport]` to reach WASM-compiled DXC, SPIRV-Cross, and vkd3d.
- `ShadowDusk.Wasm` is a self-registering Razor SDK package: a consumer needs only a `PackageReference`, no wiring.
- **The browser host exports OpenGL, Vulkan, DirectX (DX11) and FNA, and refuses `DirectX12` up front with `SD1906`** (issue #272), before any WebAssembly module loads, on both the `.fx` (`WasmShaderCompiler`) and full-Slang (`WasmSlangCompiler`) routes. The check (`ShadowDusk.Core`'s internal `BrowserHostTargets`) resolves the target the way the pipeline does (a set `Profile`'s `GraphicsTarget` wins); `Metal` is left to the pipeline's `SD0200`, so it reads the same on every host. A new `PlatformTarget` member must be classified there (`BrowserHostTargetsTests.EveryPlatformTargetMember_IsClassified`).
- **Desktop/Android natives never enter a browser build** (issue #273). `ShadowDusk.HLSL`/`GLSL` copy the restored `tools/` natives to build output with `CopyToOutputDirectory` (the loaders' dev-run base-directory probe), and such items flow into every referencing project's output; the referenced project cannot see who references it. The root `Directory.Build.targets` therefore filters on the consuming side: in a project whose `TargetPlatformIdentifier` is `browser` (or RID `browser-wasm`), every copy-to-output and copy-to-publish item sourced under `tools/` is dropped. It also applies to `samples/ShaderFiddle.Web`, which isolates itself only from the root `Directory.Build.props`. NuGet consumers were measured unaffected without it (a cold `net8.0-browser` app on locally packed `ShadowDusk.Wasm`: zero natives, since `runtimes/<rid>/native` is never selected for browser-wasm). `wasm.yml` fails if a native reappears in the sample's publish.
- Central Package Management is on; third-party versions live in `Directory.Packages.props`, the ShadowDusk version in `Directory.Build.props`.

## Vocabulary

- Effect pass: a single vertex+pixel shader pair compiled to a `PassBlob`.
- Effect technique: one or more named passes; maps to MonoGame's `Technique`.
- Platform blob: the platform-specific compiled binary (DXBC, SPIR-V, DXIL, or MSL source).
- ShaderIR: ShadowDusk's internal representation between parsed HLSL and platform emission.
- Rung 4 / render-proven: the real-engine render proof. The full four-rung ladder is defined in CLAUDE.md.

## Targets, and what constrains them

> **Proof status is NOT recorded here.** How far each target is proven changes as evidence advances, so it has one home: `docs/validation-matrix.md` (with a cold-start summary table in CLAUDE.md). This section records only what constrains the targets, which does not change when a gate goes green.

- Shader model and output format per target: OpenGL SM3 GLSL, DirectX 11 SM5 DXBC, DirectX 12 SM6 DXIL, Vulkan SPIR-V, FNA SM1-3 fx_2_0.
- **`mgfxc` enforces a per-target floor on the `compile <target>` profile token, and the accepted sets are not derivable from the profile names.** Measured 2026-07-31 by sweeping every recognized profile through the pinned `mgfxc` (`dotnet-mgcb` 3.8.4.1). `DirectX_11` accepts **only** `{vs,ps}_4_0_level_9_1`, `_4_0_level_9_3`, `_4_0`, `_4_1`, `_5_0` — `_4_0_level_9_0` is refused, and so is **every SM6 profile**, so a `major >= 4` rule is wrong in both directions. `OpenGL` caps at SM 3.0; `Vulkan` requires exactly `*_6_0`. `DirectX_12`'s floor is **unmeasured** (its reference compiler is mgfxc 3.8.5, outside the golden-oracle pin). ShadowDusk enforces the DirectX one as `SD0015`; the OpenGL and Vulkan ones are open gaps (`docs/validation-matrix.md` §8.1).
- The stock MonoGame `#if OPENGL … #else …` header cannot serve ShadowDusk's FNA target: FNA's macro set is `{FNA, HLSL, SM3}` with no `OPENGL`, so it takes the `#else` (DirectX, SM4) arm while its `fx_2_0` output is capped at SM3. Gate on **`SM4`** instead when one header must serve DirectX + OpenGL + FNA; `SM4` is defined by MonoGame's own `DirectX_11` profile and by nothing else, verified against `mgfxc`. This is what `ShaderToyConverter` emits.
- The OpenGL feature ceiling is the consumer runtime's, not ours: MonoGame and KNI both still use MojoShader for GL, so an SD0210 rejection (vertex texture fetch, texture arrays) is a runtime constraint to respect, never a compiler gap to fix. The DirectX target has no such cap and emits the SM4/5 features the GL path refuses.
- KNI ships no Vulkan platform and no DirectX 12 platform, which is why those two targets are MonoGame-only.
- **raylib (Phase 59) is a source-text output, not a target**: `RaylibConverter` emits `glsl330` fragment shaders for `LoadShaderFromMemory(null, fs)`, so the only interface available is what raylib's built-in vertex shader writes (`fragTexCoord` vec2, `fragColor` vec4), the draw texture is always `texture0`, and every other uniform is bound by name. MonoGame (posFixup) and raylib (`BeginTextureMode`) flip render targets in opposite directions, so `SV_Position`/`gl_FragCoord` and `ddy`/`dFdy` read different values in the two runtimes and are refused. Raylib-cs 8.1.0's desktop native is a GL 3.3 build whose built-in shaders are `#version 330`, and macOS GL cannot compile GLSL ES, so `glsl100` cannot be rendered by any harness here.
- **Where a source path can reach the output bytes** (issue #274, measured 2026-10-01). Only an MGFX v11 container (always DirectX 12 and Vulkan; any target under `MgfxVersion = 11`) stores a source name: one string per shader record, and because the header's effect key is an MD5 of the body, that string moves the 4-byte key too. Unset, it is `CompilerOptions.SourceFileName` exactly as passed, which is `mgfxc` CLI parity (both CLIs write their source argument at the same offset) and must not change for the CLI's `.mgfx` output. `ShadowDuskEffectProcessor` (both delivery shapes), and the CLI when its output path ends in `.xnb` (issue #280: `mgfxc` has no `.xnb` mode, so MGCB is the reference there), set `CompilerOptions.EmbeddedSourceFileName = "<unknown>"`, which is what the stock MGCB 3.8.5 `EffectProcessor` writes (`.xnb` offset `0xa0` = `09 3c 75 6e 6b 6e 6f 77 6e 3e` on `DesktopVK` and `WindowsDX12`), because the content pipeline hands a processor the effect's ABSOLUTE path. So on a v11 target the processor's bytes, and the CLI's `.xnb` payload, are the CLI's `.mgfx` with that string and the key different, and nothing else; the CLI `.xnb` payload equals the MGCB plugin's byte for byte (`validation/MgcbPlugin` asserts it). MGFX v10, KNIFX and FNA `fx_2_0` store no source name: OpenGL, DirectX 11 and FNA bytes do not depend on `SourceFileName`, with or without `Debug`.
- **With `Debug` on, DXC also records `SourceFileName` in its own debug information**, and no ShadowDusk option hides it: as plain strings in Vulkan SPIR-V (5 occurrences on a one-shader effect), and inside DirectX 12 DXIL as bit-packed LLVM bitcode, which a string search does NOT find (only the size delta shows it: the output grows by the path's length a second time). Stock MGCB 3.8.5 with `DebugMode=Debug` also puts the absolute path in Vulkan SPIR-V but not in DirectX 12 output. **`DebugMode=Auto` never turns debug on, whatever the content build configuration** (issue #280): stock's `EffectProcessor.cs` sets `Debug = DebugMode == EffectProcessorDebugMode.Debug` at `v3.8.5` (and adds `/Debug` under the same condition at `v3.8.2`), never reading `BuildConfiguration`, and a real `dotnet-mgcb` 3.8.5 `/config:Debug` build equals its release build; `ShadowDuskEffectProcessor` does the same, and `validation/MgcbPlugin` re-measures both on every run. So only an explicit `DebugMode=Debug` content build (or CLI `/Debug`) makes a DirectX 12 / Vulkan output vary with the checkout directory, which is what debug information is for.
- DirectX 12 output is host-dependent: DXIL validation and signing run through the Windows-only `dxil.dll`, so a non-Windows DX12 compile emits unsigned DXIL (warned `SD0214`) that retail D3D12 rejects at pipeline-state creation. DX12 is therefore excluded from the cross-host byte-identity manifest.
- KNI loads the same `.mgfx` as MonoGame; the only divergence is its HiDef profile, whose runtime converter rewrites `mgfxc`'s `#define ps_oC0 gl_FragColor` form and nothing else.
- FNA is proven against a different oracle: `fxc.exe /T fx_2_0`, not `mgfxc`.
- **vkd3d's own diagnostic coordinates are wrong in three independent ways, so they are never surfaced as-is** (issue #202): its preprocessor ignores `#line` (ShadowDusk blanks the directives in `Vkd3dCompileContract.PrepareSource`, the one step both hosts run, so the 5-line macro prelude counts), it drops skipped `#if` arms and block-comment interiors from its line count, and its HLSL front end lexes the internal HLSL template behind `atan`/`atan2` (+20 lines), `asin`/`acos` (+11), `tanh`/`lit` (+7), `refract` (+6), `sincos`/`smoothstep`/`sinh`/`cosh`/`dst`/`faceforward`/`modf` (+4), `fwidth`/`determinant` (+3) against the user file's line counter, uncached, at every call site (`hlsl.l` `++ctx->location.line` on the shared context, never restored by `hlsl_compile_internal_function`). Its columns count in its own re-spaced token stream (one space between tokens, indentation dropped). `Vkd3dSourceLocator` recovers the author's file/line/column by planting a sentinel syntax error and bisecting with parse-abort probes of the same request (vkd3d measures its own drift, so macros, skipped arms, comments and templates are all accounted for), then replaying the un-blanked text's `#line` directives. That covers the raw vkd3d output printed under the summary too: every `file:line:col:` prefix in `RawDiagnostics` that names the compiled source moves the same way, the text after it stays verbatim, all or nothing (one unplaceable line leaves the whole block as vkd3d wrote it). A failing compile can emit thousands of lines (4 165 lines, 934 distinct locations on the current upstream Apos.Shapes file), so the block is not bisected per line: one parse-only compile prefixes every statement start with a marker, `[__shadowdusk_line_N__] if(0){}`, which vkd3d answers with the non-fatal located warning `W5302: Unrecognized attribute '…'`, measuring every statement start at once; a line between two measurements is inferred from them and only what they cannot pin is bisected (22 vkd3d calls in total for that file: 2 real compiles, 11 summary probes, 1 marker compile, 8 more probes; pinned by `FnaDiagnosticLocationTests`). **A probe whose sentinel vkd3d never sees (planted in a skipped `#if` arm or a block comment) does not abort, so it would run the whole failing compile again; every probe therefore ends with a terminator line, an unbalanced `)`**, a syntax error that is deliberately not the sentinel's. Measured: one such probe, in Apos.Shapes' `#if VULKAN` arm, doubled the time to the error. The `# N "file"` marker vkd3d's lexer does honour is legal only between top-level declarations, which is why markers could not be the fix. Both the desktop and the WASM host relocate through it. **The sentinel's diagnostic text is spelled by the bison that generated the native's parser, not by vkd3d:** `syntax error, unexpected invalid token` from bison 3.6+ (the MinGW win-x64 DLL, both Homebrew macOS dylibs) but `syntax error, unexpected $undefined` from bison 3.5.1, which is what the linux-x64 `.so.1` gets from its Ubuntu 20.04 (glibc 2.31 baseline) build container; the locator matches both, and `Compile_TheSentinel_IsSpelledOneOfTheTwoBisonWays_OnThisHost_Issue202` pins the running host's spelling to that set (a third spelling fails loudly there instead of silently returning raw coordinates). Re-measure the template table on any vkd3d pin bump; the locator itself needs no table.
- **vkd3d prints `vkd3d:NNNN:fixme:vkd3d:preproc_yyparse #line directive.` to stderr once per `#line` directive it is shown, and ShadowDusk blanks them before every vkd3d call on every host** (issue #319, measured 2026-10-02 on the 91-compile DX + FNA corpus: 93 lines on one node gate run, one per directive). The fixme goes through vkd3d's debug channel, not its message buffer: `VKD3D_DEBUG=none` does not reliably reach the native `getenv` on the desktop and the WASM module has no environment, so the only reliable way to a silent success is not to show vkd3d the directive. Measured, the directives change neither the emitted bytes nor the position of any diagnostic (the line count is preserved by blanking, not deleting), so the text is console noise only; `Vkd3dCompileContract.PrepareSource` is the single owner of the preparation (the desktop marshals its result, the browser sends it through the shim), and the vkd3d gates replay the bytes read back from the desktop's native call. The CR of a CRLF directive line is consumed with the directive (the LF stays); that is the long-standing desktop behavior and is pinned, since changing it would move what vkd3d is handed.
- **vkd3d's message buffer is populated on a SUCCESSFUL compile too, and both hosts surface it as `CompiledShader.Warnings` through one shared path** (issue #335). Both hosts compile at `VKD3D_SHADER_LOG_WARNING`, so a non-fatal diagnostic (`W5300 Implicit truncation of vector type`, `W5301 Floating point division by zero` on SM4+, `W5302 Unrecognized attribute`, measured on 2.1) comes back in the same buffer that carries errors on failure. The text becomes warnings in exactly one place, `Vkd3dCompileContract.MapCompileWarnings` (every entry a warning, text verbatim, whitespace-only text is no warning), and is relocated by `Vkd3dSourceLocator` the same way a failure's diagnostic is; the browser shim's `compile()` returns `{ code, messages }` so the browser host has the text at all (it used to return the bytes alone and the browser's `Warnings` was empty while its bytes were identical to the desktop's, which no byte gate could see). - **WebAssembly stack size is a correctness setting, not a tuning knob** (PR #266 review, measured 2026-10-01). The DXC, SPIRV-Cross and vkd3d modules had the same 64 KB default (issue #271, measured 2026-10-02, `.wasm-build/WASM-STACK-DEPTH.md`) and it was worse there, because with emscripten's data-first layout an overflow silently corrupts static data instead of trapping: DXC **hung** on a 100-term add chain and gave a wrong diagnostic on 200 else-ifs, SPIRV-Cross corrupted itself on **about a dozen nested ifs or else-ifs**, vkd3d trapped at 75 else-ifs. - **The `setlocale`/`fork()` deadlock does not occur on glibc Linux, so `DxcForkGate` stays macOS-only** (issue #256, measured on ubuntu CI 2026-10-01): 16 fork-probe runs of 6 s over two CI runs and both TFMs, about 8,200 DXC compiles racing about 8,100 `Process.Start`s and 10,000 real libc `fork()`s, never hung. - **Vortice.Dxc's resolver order matters, so ours goes first.** Vortice's static constructor subscribes its own `Dxc.ResolveLibrary` handler, and `+=` appends after it. Its probe is `AppContext.BaseDirectory + "runtimes\\<rid>\\native"` with **literal backslashes** (a real directory only on Windows; it also maps every arch to `win-*`), then bare-name `TryLoad("dxil")`/`TryLoad("dxcompiler")`. On Linux in a plugin host whose `NATIVE_DLL_SEARCH_DIRECTORIES` miss ours, that bare `dlopen` can take a `libdxcompiler.so` from `LD_LIBRARY_PATH`, and our absolute-path load does not dedupe it (the SONAME is `libdxcompiler.so.3.7`). `DxcLoader` therefore inserts its handler at the FRONT of the event's backing delegate (`Dxc.ResolveLibrary` field, by reflection; plain `+=` if the field ever moves). **Known residual:** if the host process drove Vortice.Dxc before ShadowDusk's first use, the runtime has already cached Vortice's P/Invoke binding to whatever `dxcompiler` the host loaded, and no resolver runs again.
- `d3dcompiler_47.dll` and `fxc.exe` are Windows-only test oracles and never ship to consumers.
- DXC cannot produce DXBC at all: it only emits SM6 DXIL, and `ID3D11Device::CreateVertexShader` rejects DXIL unconditionally.
- glslang is not used anywhere in the pipeline; MojoShader is a consumer-runtime component, not one of ours.
- vkd3d-shader is LGPL-2.1+ and ships as a dynamically-linked native binary with a third-party notices file packed into the nupkg root.
- The SPIRV-Cross binding is raw P/Invoke against the C API rather than `Veldrid.SPIRV`; the rationale was never recorded.
- `Vortice.Dxc` was chosen as the DXC wrapper because it bundles prebuilt natives for all platforms; whether other wrappers were evaluated was never recorded.

- A CLI OpenGL compile of `Minimal.fx` (`ShadowDuskCLI.exe`, Release, Windows desktop, 16 logical cores, 2026-10-02) costs 0.21 s at the median idle (min 0.20, p99 0.25, max 0.26 over 400 sequential runs; the first spawn after a fresh build 0.34 s), 0.54 s median and 0.97 s max with 20 compiles running at once on all 16 cores (3,000 runs), and 2.9 s median, 6.1 s p99, 7.7 s max with 48 compile loops plus 16 CPU spinners (2,880 runs, about 4x oversubscription); no run hung. - **vkd3d compile time is roughly quadratic in the size of the fully inlined shader, and that is a known gap ShadowDusk cannot work around (issue #255).** The current upstream Apos.Shapes pixel shader takes about 5 s at `ps_5_0` and 5.5 s at `ps_3_0` on one Ryzen 7 5800X core (3.3 s on a fast Apple core), against about 1.2 s for the whole OpenGL compile through DXC. It produces a 457 KB DXBC blob, because vkd3d inlines every SDF call and unrolls the fixed-count glyph loops. Nearly all of that time is one `vkd3d_shader_compile` call in the HLSL optimizer. Measured with callgrind on official-tarball builds (2026-10-01): on Apos.Shapes, `vectorize_exprs` is 67% of instructions, `evaluate_conditionals_recurse` 16% self (235 million calls) and copy propagation about 27% (overlapping); on the synthetic repro below, 82% is the vectorizer (`vectorize_exprs` / `find_vectorizable_expr_groups` / `record_vectorizable_expr`) and the whole folding pass only 7%. The quadratic is inside a single pass, not repeated fixpoint iterations (those run a constant 5 or 10 times whatever the size): `record_vectorizable_expr` searches linearly through every group recorded so far. Measured with a direct P/Invoke harness, CPU time, same input and same options, vkd3d 2.1 is slower than 1.17: 5.3 s against 3.3 s at `ps_5_0` (reproduced independently on official-tarball Linux builds at about 1.5x; vkd3d master `6ee3db29` behaves like 2.1). **The regression arrived in 1.18, not 2.1:** bisected to upstream commit `4d5a1528` ("Flatten conditional branches containing stores"), which merges branch bodies into the top-level block so the vectorizer's linear scan covers about twice the candidates; marking the `if`s `[branch]` removes the extra cost. 1.17 cannot compile the file at `ps_3_0` at all (`E5017`, SM1 int `cmp`). In a synthetic pixel shader made of N inlined calls to a small SDF with an `if`/`else` chain, time grows about 3.5-4x per doubling of N on both versions, and 2.1 is about 2x slower than 1.17 (N=1600: 5.7 s against 2.7 s). Straight-line code with no branches scales the same way, but 2.1 is no slower there (1.6 s against 1.8 s). So the 2.1 slowdown is specific to control flow, and 2.1 also emits about 35% smaller code. Limiting Apos.Shapes' glyph loops from 16 to 1 iteration only cuts it from 4.8 to 3.1 s, so the cost is the whole inlined call tree, not one construct. vkd3d 2.1 has no compile option that reduces optimizer work (`vkd3d_shader_compile_option_name` has none), and the faithful-pipeline rule rules out another compiler, so the only fix is upstream. ShadowDusk itself does what it can without changing output: each distinct entry-point request is compiled once per `Compile` call (`MemoizingDxbcCompiler`; the stock `BasicEffect` went from 64 vkd3d calls to 30 on both DirectX and FNA). The DXC-based targets (OpenGL, Vulkan, DX12) have not been audited for the same per-pass repetition. Under CI load (two TFM hosts at once, up to 7 vkd3d compiles in flight per host) a compile of that size stretches 5-15x.
- **Every native compiler call runs on a `NativeCompileStack` worker with a 64 MB stack, never on the caller's thread** (issue #306, measured 2026-10-02 on Windows x64). DXC, vkd3d and SPIRV-Cross recurse once per nesting level of the source, and a native stack overflow is not catchable: the process exits (`0xC00000FD` on Windows, `SIGSEGV`/abort on Unix) with no diagnostic. On the 1.5 MB stack the .NET host gives a Windows thread the ceilings were 2,167 additive terms (`x + x + ...`, OpenGL and DirectX 12; 2,817 on Vulkan, whose SPIR-V-only compile has smaller frames than the DXIL one), 1,619 `else if` branches on DirectX 12 (OpenGL/Vulkan get DXC's clean SPIR-V nesting-depth error first, at about 1,025), and between 3,200 and 6,400 chained function calls through vkd3d (DirectX/FNA). With the 64 MB worker: 94,400 additive terms compile on OpenGL and DirectX 12 (96,000 kill the process; 47 s on OpenGL), 122,336 on Vulkan (123,584 kill it; 203 s); 51,200 else-ifs (DirectX 12, 329 s; 12,800 in 14 s) and 25,600 chained calls (DirectX, 74 s) compile, with time rather than stack as the limit (an additive chain of 51,200 terms takes about 19 s). Stack per nesting level is shape-dependent: about 0.7 KB per additive term, 2 to 4 KB per unary operator (`-+-+...x`, one source byte per level), 1 to 2 KB per unparenthesised nested ternary, so the shortest source that still kills a 64 MB worker is a chain of roughly 20,000 unary operators. Macro expansion hides depth from any source scan (twelve `#define A{n} A{n-1} + A{n-1}` lines are a 4,096-term expression), which is why there is no pre-check. Linux and macOS ceilings are not measured in numbers; CI proves the same depths compile there on the worker and that a 100,000-term chain still overflows a default thread stack (`DeepShaderStackTests`). Through the synchronous `Compile` only the native call moves to the worker (the pipeline, the pre-parser and every consumer callback stay on the calling thread; about 0.4 ms per effect, one handoff of about 0.1 ms per native call, measured on a 10 ms effect); `EffectCompiler.CompileAsync` hands the whole pipeline from its thread-pool thread to one worker, so the native calls inside run inline and the cost is not measurable in a loop (the Release CLI, one compile per process, pays 2 to 3 ms of one-time worker start and JIT, about 1% of its 230 ms). The bytes do not depend on the thread or the arrangement (corpus byte-identical with the worker on and off; `Compile` and `CompileAsync` identical). Compiles that find no idle worker start another, so parallelism is unchanged; a worker exits after 5 s idle, which also releases the stack pages a deep compile committed.
- A test's `CancellationToken` cannot interrupt a native compile: vkd3d, DXC and SPIRV-Cross each run as one uninterruptible P/Invoke, so a per-test timeout around one is only a wall-clock assertion checked between calls, never a hang guard. On DirectX and FNA the pipeline checks the token before every entry-point compile, including one served from the per-run memo, and `Vkd3dSourceLocator` checks it before each diagnostic-relocation probe. That one check serves both vkd3d hosts, since the desktop backend and the browser backend each hand their token to the locator; in the browser it cannot fire today, because nothing can cancel a token while a synchronous compile is on the single-threaded runtime's stack. The integration step's `--blame-hang-timeout 3m` is the hang guard (it kills the host and dumps every thread's stack, the host's and its children's, uploaded as `integration-hang-dumps-<os>`). It is an inactivity timer: every test that starts or finishes resets it, so it fires 3 minutes after the last test event anywhere in the assembly, not after the stuck test began (measured locally with a deliberately hung test beside tests finishing every 8 s: the dump came 15 s after the last of them, and with a shorter session cap it never came). The VSTest `TestSessionTimeout` is absolute and aborts with no dump, so the integration step sets it to 10 minutes inline, above a healthy assembly run (3 min 20 s measured worst) plus the blame timeout plus dump time; `CiHangGuardTests` enforces the inequality. Its headroom is about 1.8x: the slowest healthy test is `SlangRoute_Bytes_MatchCommittedManifest`, max about 101 s on a CI runner (issue #258) against 13 s on a Windows desktop. It spawns slangc once per entry point for each of three compiles per corpus shader (the captured assembled `.fx`, then OpenGL and DirectX), and the captured OpenGL assembly repeats the OpenGL compile's slangc work, so folding those two is the obvious cut (about a third of the spawns) if the headroom ever gets tight. Raise the timeout or make that cut before adding a slower test; never let a healthy test approach 3 minutes.
- **On Windows a window dies with the thread that created it, so `ShadowDusk.ImageTests`' GL window lives on a dedicated thread the fixture owns** (issue #345). `GlContextFixture` used to create its hidden GLFW window on whatever thread xUnit ran `InitializeAsync` on, a thread-pool worker. The pool retires a worker after 20 s idle, which a 3 s ImageTests run alone never reaches but a loaded full-solution `dotnet test` does; the window was then destroyed and the next `wglMakeCurrent` failed with `The handle is invalid` (or `The requested transformation operation is not supported`). The failure then hung the host, because the fixture threw out of make-current while holding a `Monitor`, and the next test, on another thread, waited on it forever. Running the net8.0 and net10.0 hosts concurrently is not itself a collision (30/30 clean concurrent runs, measured before the fix); it only lengthens the run enough for the retirement. The project's runtime config sets `System.Threading.ThreadPool.ThreadTimeoutMs` to 100, which makes the old failure happen on every run (measured 7/7), so every ImageTests run re-proves the owner thread. GL use is also serialized across ImageTests hosts by the named mutex `ShadowDusk.ImageTests.GlContext` (held for the GL collection's lifetime, bounded 10-minute wait, abandoned mutex taken over), and every claim of the context goes through `GlContextGate`: a make-current failure fails that test and every later one at once, a claim waits at most 2 minutes, and a test holding the context for 3 minutes ends the host with `Environment.FailFast`, so a GL fault always fails the run and never needs a hand kill.
- `packages.lock.json` records each `ShadowDusk.*` project reference at the version current when the file was last regenerated, and neither a normal restore nor CI's `--locked-mode` rewrites or rejects a stale range, so they drift on every version bump unless the release rewrites them (`RELEASING.md`, issue #258). `dotnet restore --force-evaluate` regenerates them but drops project references whose source is absent on the box (`validation/FnaValidation`'s gitignored `external/FNA`).
- A working tree checked out before a `.gitattributes` `eol=lf` rule existed can still hold CRLF copies of those files while `git status` reports it clean (git compares the normalized content). Byte-hashing tests then fail only on that box: `SlangMonoGameEffectsTests.Fixtures_AreByteIdenticalToMonoGameV385` failed on the long-lived `main` checkout on 2026-10-01 while fresh worktrees and CI passed. Fix by deleting and re-checking-out every `eol=lf` file that contains `\r` (`git ls-files -z | xargs -0 git check-attr eol` lists them); never by re-pinning the hash.
- Publishing is driven by the `NUGET_API_KEY` repository secret; no credentials live in the repo.
- The Phase-41 structural-divergence appendix stays outside `plan/DONE/` because `dotnet test` regenerates it on every run; diffing it across a change is the cheapest oracle for an unintended `.mgfx` structural change.
- `SamplerReflection.TextureName` is never assigned by any reflection backend; it is always null, so any texture/sampler pairing must key on bind slot or fall back to the sole shared sampler.
- SPIRV-Cross's `build_combined_image_samplers` declares one GLSL sampler per (texture, sampler) PAIR; neither the reflected texture list nor the reflected sampler list is that pair list. `SpirvCombinedSamplerPairs` derives it, in order, from the SPIR-V.
- The order SPIRV-Cross *declares* those pairs in is **first-use order, deduplicated** — not HLSL declaration order, not bind-slot order. The trigger is `OpSampledImage` during a walk of the entry-point function's blocks in binary order, recursing into `OpFunctionCall` with a parameter remapping; the synthesized variable ids come from `increase_bound_by(2)` so they sort after every original id, and the GLSL emitter walks variables in id order while skipping every separate image/sampler. Read from the pinned SPIRV-Cross tree in `.wasm-build/spirv-cross-src` (tag `vulkan-sdk-1.4.335.0`, the same tree the WASM module is built from), then confirmed against real output with dimension-tagged probes.
- **The pair *list* is in first-use order, but the texture UNIT each pair binds to is its HLSL DECLARATION index** (`CombinedSamplerPair.TextureDeclarationIndex`, ranked by the raw SPIR-V `Binding` decoration, which DXC allocates in declaration order). `SpirvCombinedSamplerPairs.ResolveSlots` is the single definition of that rule, used by BOTH `MonoGameGlslRewriter` (which names the uniforms `ps_s{slot}`) and the `.mgfx` sampler table, so the table and the GLSL it describes cannot drift apart. Records are then emitted sorted by slot, matching how `mgfxc`'s goldens lay the table out. Two pairs *can* share one texture (one texture through two `SamplerState`s), which would collide; there is no committed `mgfxc` golden for that shape, so `ResolveSlots` falls back to positional numbering for the whole stage rather than inventing an answer.
- SPIRV-Cross's readable `SPIRV_Cross_Combined<Image><Sampler>` name is applied by its **command-line tool**, not by `build_combined_image_samplers`, so through the C API the combined uniforms arrive as bare `_<id>` (`uniform sampler2D _40;`) carrying no pair identity. The emitted GLSL therefore cannot be used to recover which pair a declaration is.
- **`mgfxc` allocates GL sampler slots in HLSL DECLARATION order, honouring `register(sN)`; ShadowDusk now does the same** (GitHub issue #189, fixed 2026-08-02). Measured against the pinned `mgfxc` 3.8.4.1 on three shapes: `SharedSamplerPair.fx` (`ps_s0` = `DiffuseMap`, declared first), `SamplerPairMirror.fx` (`ps_s0` = `LinearTexture`, declared first, sampled *second*), and a two-sampler probe with the annotations stripped (`ps_s0` = the first-declared sampler). Declaration order in all three, annotated or not.
  - **This superseded a claim that was WRONG and shipped a real defect.** Until 2026-08-02 this file asserted that ShadowDusk *must* follow SPIRV-Cross's first-use numbering and that the divergence was "invisible in the picture, proven at maxd 0 by `validation/SamplerPairsGl` arm B". Arm B could not prove that: its two textures hold IDENTICAL pixels — deliberately, so the arm isolates per-pair sampler *state* — which is precisely what makes it blind to which unit each pair lands on. With DISTINCT textures the numbering is very much visible, because `SpriteBatch` owns unit 0.
  - The record does still have to name the uniform *our own* GLSL declares; that constraint is satisfied by numbering BOTH from `ResolveSlots` rather than by conceding the numbering to SPIRV-Cross.
- **An explicit `register(sN)` on a LEGACY sampler declaration pins the OpenGL texture unit, and ONLY the legacy form does** (issue #189 sparse half, closed 2026-08-02). Measured against the pinned `mgfxc`:
  - **Legacy** `sampler X : register(s2);` — `mgfxc` emits `ps_s2` at unit 2. It honours the annotation because, compiled at `ps_3_0`, the legacy sampler IS the combined sampler and the clause pins its SM3 sampler register directly. ShadowDusk matches: `FxPreParser` **records** the index (`FxParseResult.ExplicitGlSamplerSlots`, texture-keyed) before its SM4 rewrite drops the clause, and `SpirvCombinedSamplerPairs.ResolveSlots` prefers it over the declaration-index ranking.
  - **Modern** `SamplerState S : register(sN)` — the register is **RESERVED, not assigned**: the pair is allocated *around* it. Measured: one texture + `S : register(s0)` yields `ps_s1`; `S : register(s1)` with two textures yields `ps_s0`+`ps_s2` (1 skipped, not shifted); `P : register(s0)` + `Q : register(s1)` yields `ps_s2`+`ps_s3`. A modern `register(tN)` on the TEXTURE is ignored entirely. (On **DirectX** the modern registers ARE honoured outright, by both compilers, straight from `TextureReflection.BindSlot`.)
  - **One rule covers both**, which is why the legacy form is not a special case: at `ps_3_0` a texture and a sampler are ONE object in ONE register namespace. In texture-declaration order, a pair whose sampler declared a register takes it (legacy: the sampler *is* the combined object); every other pair takes the lowest register neither taken nor reserved. Verified against the pinned `mgfxc` on **10 shapes**, legacy and modern, annotated and not — all match.
  - The clause is **recorded, not re-emitted**: preserving it in the rewritten HLSL would change what DXC compiles and move the DirectX/DX12/Vulkan/FNA bytes, none of which have a reported defect. Recording changes the OpenGL slot allocation only.
  - Mixed sets resolve per-sampler and are exercised by the real `apos-shapes-aa.fx` (explicit `s0`, an unannotated sampler, explicit `s2` → units 0/1/2, byte-identical to the `mgfxc` golden).
  - Where two pairs would land on the same unit — two `SamplerState`s over one texture, or two samplers annotated onto one register — `ResolveSlots` falls back to positional numbering for the whole stage rather than dropping a uniform onto an occupied unit.
  - The SPIR-V ranking `SpirvCombinedSamplerPairs` uses recovers declaration ORDER but never the register VALUE, because DXC's `Binding` namespace is flat and auto-allocated. That is why the value has to come from the pre-parser rather than the SPIR-V.
- `mgfxc` bakes sampler state from a legacy `sampler2D X = sampler_state { … }` block but **not** from a modern `SamplerState X { MinFilter = …; }` block with D3D9 state names (fxc maps D3D10-style names such as `Filter` there). ShadowDusk bakes both, so the modern-block spelling is a real ShadowDusk-vs-`mgfxc` divergence on baked state. Corpus fixtures that need baked state must use `sampler_state` (as `SamplerStatesFull.fx` and `SamplerPairMirror.fx` do) or they diverge from their own golden.
- On the GL path there is no legacy/pre-combined sampler case to model: the pre-parser's `RewriteToSm4` mode (every target except FNA) rewrites `sampler2D`/`tex2D` into `SamplerState` + `<texture>.Sample(...)` before DXC sees the source, and SM6 HLSL has no combined sampler type, so every emitted GLSL sampler uniform is a synthesized pair.
- MonoGame binds a sampler's texture through the record's `Parameter` **index**, never its name (`EffectPass.SetShaderSamplers` does `_effect.Parameters[sampler.parameter]`). The record's `Name` matters only on GL, where it must match the GLSL uniform for `glGetUniformLocation`.
- `SpriteBatch` forces the sprite texture onto texture unit 0 **after** `EffectPass.Apply()` (`SpriteBatcher.FlushVertexArray` assigns `_device.Textures[0] = texture` immediately after `pass.Apply()`), so a PS-only render harness can only test units 1+ through effect parameters.
- `docfx/images/pipeline-overview.svg` is regenerated by `tools/render-diagrams.{ps1,sh}`, which downloads and SHA-256-verifies a pinned PlantUML jar into `tools/plantuml/`; the site embeds the SVG, never the `.puml`.

## Known upstream bugs we live with (not ours)

- MonoGame's Vulkan runtime has a `SlotOffset` byte-wrap bug that crashes on `mgfxc`'s own auto-numbered output, blocking the Vulkan pixel diff for auto-numbered resources (effects using explicit registers already diff pixel-for-pixel).
- `mgfxc` + MonoGame GL mis-handles statically-partially-read uniform arrays (MojoShader register compaction); we deliberately emit the correct full layout instead.
- `mgfxc`'s own GL compile of the current Apos.Shapes revision renders solid black, so GL has no trustworthy golden for that shader.
- `mgfxc`'s GL `Dots` is GPU-sensitive: its `sin` reduction uses a truncated 1/2π, so on Intel UHD it renders maxd 19 off the DX11 render (ShadowDusk GL, KNI and DX agree within 1; NVIDIA and llvmpipe match). `validation/compare_kni.py` forgives a `Dots` golden miss only when the golden also misses DX11 and KNI matches DX11 (issue #215, PR #359).

## Known gaps in our own reach

- **FNA `Dots` reads maxd 23 on Intel UHD and is an accepted limit** (issue #360). `fxc` hoists the uniform-only `sin(angle)`/`cos(angle)` into a CPU preshader; our `.fxb` computes them per pixel on the GPU, and Intel's imprecise hardware `sin` is then multiplied by hundreds of radians (a fit, not an isolated proof). Fixing it needs a preshader-style hoist. Run `-IncludeFna` on a discrete GPU or cite `docs/validation-matrix.md` §7.
- raylib output is `glsl330` only; `glsl100` (raylib web/GLES2) is not emitted because no harness here can render it, and the ES 1.00 lowerings live inside `MonoGameGlslRewriter`'s 110 dialect rather than at the modern-GLSL seam.
- The Linux and macOS Vortice DXC builds reject `tex3D`, `tex2Dlod`, and `tex2Dgrad` family intrinsics that the Windows DXC accepts; `Phase34TextureBreadthTests` is Windows-only for that reason.
- **DirectX 11's `d3dcompiler_47` oracle backend (`DxbcBackend.D3DCompiler`, Windows-only, never ships) now sets the same fxc flags mgfxc itself uses — `EnableBackwardsCompatibility` + `OptimizationLevel3`** — found 2026-09-09 by decompiling `mgfxc.dll` (`ilspycmd` against MonoGame.Framework.Content.Pipeline 3.8.2.1105's `ShaderCompiler.CompileHLSL`); the oracle previously set neither. Both sides load the same system `d3dcompiler_47.dll` (no private copy on either side), so this was a genuine flag bug, not a DLL-version mismatch. Fixing it changed the oracle's compiled bytes (confirmed by diff) but did **not** close the Apos.Shapes gallery's maxd 1 on 18/30 cells against the real `mgfxc` `DirectX_11` golden — the residual is a machine-dependent sub-ULP fast-math scheduling difference between two independent fxc invocations, the same class of non-defect as DX12's (below), just with no DXC-style version pin to point at. Tolerance for that comparison is 1, not 0; see `docs/validation-matrix.md` §7.
- **DirectX 12 renders the Apos.Shapes gallery at maxd 1 on 11 pixels of 402,984 against the real `mgfxc` `DirectX_12` golden, and that is the DXC PIN, not a defect** (root-caused 2026-07-31). We compile DXIL with `dxcoob 1.7.2212.40 (e043f4a12)`; the golden was built with MonoGame 3.8.5's bundled `dxcoob 1.8.2505.32 (b106a961d)`. Our own pre-parsed HLSL and our own flags, put through a DXC 1.8 build, reproduce the golden's DXIL instruction-for-instruction and render at maxd 0 with zero differing pixels, so nothing on our side of the DXC seam differs. It shows up at all only because the shader adds ±half an 8-bit LSB of dither right before quantization, so a sub-ULP difference flips whichever pixels sit on the rounding boundary; that is also why the affected pixel set moves between builds. **maxd 1 is the honest DX12 tolerance until the DXC pin moves**, and moving it is a cross-target re-baseline, not a bug fix.
- Our DirectX 12 DXIL container carries a `STAT` part (and the HLSL identifier names) that the real `mgfxc` golden strips; behaviorally inert, one `-Qstrip_reflect` away, unfixed because it moves DX12 bytes. Phase 54's claim that both `RTS0` and `STAT` were removed is wrong about `STAT`.
- **Never trust a per-cell name from the Apos.Shapes gallery harness without checking it against the view transform.** The gallery renders through a 1.15x scale + (6,4) translate, so a shape in layout cell (3,3) lands in screen cell (4,4); `AposGalleryRenderer.Cells` used the untransformed rectangles until 2026-07-31 and mislabelled every divergence it reported. - **The `.fx` route's OpenGL sampler-register facts are decided on a managed preprocessed view, like `mgfxc`: both the RESERVATION a modern `SamplerState X : register(sN)` makes (issue #283) and the unit a LEGACY `sampler X : register(sN)` pins its texture to (issue #299).** `FxMacroPreprocessor` (`ShadowDusk.HLSL`) evaluates `#if`/`#elif` and expands macros over the include-flattened RAW source with the compile's platform + user macros; the OpenGL target and the raylib converter read both maps off that one view via `FxPreParser.CollectGlSamplerSlots` (`GlSamplerReservation.Collect`). Pure C#, so identical on every host (the browser's DXC has no `-P` export, which is why DXC is not asked). It feeds a compiler only in the issue #308 recovery below (the pipeline's and, since issue #327, the raylib and SkSL converters'), after the raw compile has failed. A shape it cannot evaluate is `SD0009`, deferred until DXC has accepted the source. `FxParseResult.ReservedGlSamplerSlots` and `FxParseResult.ExplicitGlSamplerSlots` themselves are still the raw-token reading of whatever text the parser was given; nothing in the compile reads them on OpenGL any more.
- **The legacy explicit map joins two sources on purpose** (issue #299): the sampler NAME and register come from the preprocessed view, the sampler-to-TEXTURE binding comes from the raw pre-parse that feeds the compile (`FxParseResult.LegacySamplerTextures`, internal), because that is the texture the rewritten HLSL samples through. **Both names of that join are resolved through the preprocessor first** (`FxMacroPreprocessor.Process(…, identifiers)`, the macro table at end of source): the raw parse knows a sampler or texture by the token the author wrote, which can itself be a macro (`#define SAMP MySampler` / `sampler SAMP : register(s1);`), while the view and the SPIR-V only show the expansion. Joining on the raw name loses the pin of every macro-named sampler (measured: it turned an already-correct `ps_s1` into `ps_s0`), and resolving the texture name fixes a shape the raw reading never got right (`#define TEX RealTex` / `Texture = <TEX>`: `mgfxc` `ps_s1`, raw `ps_s0`). Measured against the pinned `mgfxc` 3.8.4.1 `/Profile:OpenGL`, `sampler` and `sampler2D`, `sampler_state` block / brace form / bare form alike: a register only in the inactive `#if` branch pins nothing (`ps_s0`; the raw reading said `ps_s1`), a different register in each branch takes the active one (`ps_s2`, raw `ps_s1`), and `#define REG s1` / `register(REG)` pins (`ps_s1`, raw `ps_s0`).
- **Three fixtures' explicit-slot map changes with the preprocessed reading while their OpenGL bytes do not**: `VsTransformColorTexture.fx`, `VsWaveQuadIntrinsics.fx` and `apos-shapes-sm6.fx` write `SamplerState X : register(sN)` in their `#if SM6` arm and declare the same name through the legacy syntax in the arm OpenGL compiles, so the raw reading used to map the SM6 arm's register onto the legacy arm's texture. With the dead arm gone the allocator reaches the same units on its own (declaration order; for `apos-shapes-sm6.fx` the legacy arm's own `s0` / unannotated / `s2`). Pinned by `Issue299PreprocessedLegacySamplerRegisterTests` and `Issue299ExplicitSlotCorpusSweepTests`.
- **A legacy sampler the pre-parser cannot see in the RAW main file is compiled through a RECOVERY on the preprocessed source** (issue #308): the SM4 rewrite of D3D9 sampler syntax runs on raw main-file tokens, so a `sampler`/`sampler2D` declared in an `#include`d file, one whose register clause or whole declaration is a macro (`sampler S SLOT(s1);`, `DECLARE_TEXTURE(S, 1)`), a `tex2D` in a macro body or an include, or an unused bare `sampler2D U;` reaches DXC unrewritten and is rejected. When a DXC shader compile fails (OpenGL, Vulkan, DirectX 12; DirectX 11 compiles the syntax natively through vkd3d and never recovers) and the text DXC was given still holds legacy sampler syntax once preprocessed (`FxPreParser.HasLegacySamplerResidue`), `CompilationPipeline.Run` repeats the pre-parse on the preprocessed source (`FxPreParser.ParsePreprocessed`: `FxMacroPreprocessor.ProcessForCompiler`, the same managed preprocessor, in a compiler-input form that keeps one output line per flattened input line, keeps whitespace and comment widths, passes active `#line`/`#pragma`/`#error`/`#warning` through and maps every span and error back through the `#line` directives) and runs the whole pipeline again on that text (`LegacySamplerRecovery`). The raylib and SkSL converters run the SAME recovery after their DXC compile has failed (issue #327): `LegacySamplerRecovery.Evaluate` with the OpenGL macro set, then the converter's own validations, the seam (`ModernGlslSeam.CompilePixel` on the preprocessed pre-parse's `StrippedHlsl`, never re-flattened), the raylib sampler-register reading (`FxPreParser.CollectGlSamplerSlots` on `Retry.FlattenedRawSource`) and the mapper, all from `Retry.Parsed.Parsed`; `LegacySamplerRecovery.Apply` is the one copy of the outcome handling (retry, `Rejected`, `Unmodelled`, not applicable) for all three callers. Measured for the converters on the 164-file corpus with the fix off and on: raylib 79/79 and SkSL 33/33 (69/69 with the varyings opt-in) conversions byte-identical, 11 fixtures now convert, and each recovered shape is byte-identical to its directly written twin (`RaylibConverterLegacySamplerRecoveryTests`, `SkslConverterLegacySamplerRecoveryTests`); `validation/RaylibRoute` renders the include and macro fixtures (15/15 maxd 0). **This is the one place the managed view feeds a compiler, and it is reached only after the raw compile has failed**, so an effect that compiles from its raw source is compiled from exactly that text, byte for byte: measured on the 160-file corpus for OpenGL and DirectX_11 with the fix off and on (117 + 125 byte-identical, 34 + 35 fail with the same diagnostics). The nine vendored MonoGame `Include.fxh` effects (`Bevels`, `BlackOut`, `ColorFlip`, `CustomSpriteBatchEffect`, `Grayscale`, `HighContrast`, `Invert`, `NoEffect`, `RainbowH`) compile for OpenGL through it, on `mgfxc`'s units. The recovered compile is byte-identical to the directly written declaration on all three DXC targets (pinned by `Issue308LegacySamplerRecoveryTests`), and the compiler-input view is token-for-token identical to DXC `-P` on every corpus fixture (`Issue308PreprocessorFidelityCorpusTests`). In the preprocessed re-parse only, an unused bare `sampler1D/2D/3D/CUBE` declaration becomes `SamplerState U;` (fxc drops the unused object, DXC has no such type); one a modern `.Sample` reads is left alone because `mgfxc` rejects it (X3013). Unmodelled shapes are `SD0016`, appended after the compiler's own verbatim diagnostics: legacy syntax still left after the recovery (a `sampler2D` function parameter), a conditional that tests a compiler-predefined macro (`__HLSL_VERSION`, `__hlsl_dx_compiler`, `__SHADER_TARGET_*`, `__DXC_VERSION_*`, `__spirv__`, `__LINE__` …; the managed view evaluates it as undefined like `mgfxc`'s preprocessor, DXC does not, so the text may not be the one DXC would compile), or a view that cannot be built (`SD0009`'s reasons) when the effect uses legacy sampler syntax at all. - **Every sampler type keyword with an explicit `register(sN)` RESERVES that OpenGL unit, used or not, in every entry point** (issue #309; measured against the pinned `mgfxc` 3.8.4.1 `/Profile:OpenGL` on 20 shapes, 2026-10-02): `sampler S : register(s0)` read through `Tex.Sample(S, uv)` is `ps_s1` (ShadowDusk said `ps_s0`: the matcher recognised only the exact keyword `SamplerState`), bare or with a `sampler_state` block; an UNUSED `sampler`, `sampler2D`, `samplerCUBE` or `SamplerComparisonState` with `register(s0)` next to an unannotated `SamplerState S` is `ps_s1` too; two textures through `sampler S : register(s1)` are `ps_s0`+`ps_s2`; and a legacy `sampler X : register(s0)` that one pixel shader reads through `tex2D` keeps s0 reserved in a second pixel shader that never reads it (`sampler2D Y` there is `ps_s1`; with `X : register(s1)` and two samplers, `ps_s0`+`ps_s2`). fxc keeps an explicitly bound register out of circulation for the whole source, whatever the keyword and whether or not the entry point being compiled uses the object. So `FxPreParser`'s reservation matcher accepts every `SamplerTypeKeywords` entry plus `SamplerComparisonState`, and a legacy sampler a `tex2D` reads is both pinned (pass 1 of `ResolveSlots`, its own pair) and reserved (pass 2, every other pair). `sampler2D S` read through `Texture.Sample` is rejected by `mgfxc` (X3013) and still fails here. A register only in an inactive branch still reserves nothing; one spelled through a macro or declared in an include reserves, because the matcher runs on the preprocessed view. No existing fixture's bytes moved.
- **Geometry, hull, domain, and compute shaders can never be supported on stock MonoGame or KNI, and this is settled, not open.** Re-measured from source 2026-08-05: MonoGame at BOTH `v3.8.5` and `develop` declares `ShaderStage` as exactly `{ Vertex, Pixel }` and decodes the stage from **one bool**, in a reader that is shared managed code (so the 3.8.5 `DesktopVK`/`WindowsDX12` backends inherit it and did not open a door); KNI `v4.29001-hotfix2` is stricter still, switching on a two-value byte with a throwing `default`, with `Shader` abstract over exactly two concrete subclasses. Upstream issues #4567 (2016) and #7533 (2021) are open but **undesigned**, so there is no format to target. ShadowDusk rejects these with **`FX0014`**, and the reject set is mgfxc-faithful and measured, not inferred: the pinned mgfxc refuses all four stages in both the `= compile` and the `= NULL` form. **The `cpt-max/MonoGame` fork is a second container, not a superset** — `(int)ShaderStage` vs a 1-byte bool, minus the two v11 `SourceFile`/`Entrypoint` strings, so every shader record diverges from its first byte and stock MonoGame would misparse fork output rather than ignore it; a fork target could therefore never be a silent auto-upgrade. Whether some compute/geometry *workloads* can be **converted** to vertex/pixel form is a separate open question ([plan/DONE/PHASE-58-extended-shader-stages.md](plan/DONE/PHASE-58-extended-shader-stages.md) Area D), and if it ever lands its bar is source-fidelity, not `mgfxc`-equivalence.

- **When DXC folds an algebraic identity that fxc keeps, the OpenGL pipeline synthesizes register backing for the reflected parameter** (issue #187, fixed 2026-08-01; sole pre-existing member corpus-wide: `GradientToy.fx`/`iResolution`, 147-fixture sweep).
