# Project Facts

Source of truth for statements about the project. One short fact per line. Update in place; delete facts that become false.

## What ShadowDusk is

- ShadowDusk is a cross-platform HLSL shader compiler for MonoGame, KNI, and FNA, delivered as a drop-in `mgfxc` replacement.
- The product is the in-memory library (`IShaderCompiler.CompileAsync(fx) -> .mgfx bytes`); the CLI and the MGCB plugin are delivery shapes of it.
- The browser/WASM shader-fiddle is only a sample of reach, never the product; sample work must not redefine the goal.
- "Works" means the real-engine render proof (the evidence ladder in CLAUDE.md, rung 4), not a green test suite.
- "Same as `mgfxc`" means behaviorally equivalent and `Effect`-loadable, never byte-identical; byte-identity with `mgfxc` is an explicit non-goal.
- Determinism means ShadowDusk-vs-itself: same version + same source + same target = same bytes, on every host, for the targets the cross-host byte-identity manifest covers (OpenGL, DirectX_Vkd3d, FNA); DirectX 12 is the one carve-out, because its DXIL signing is Windows-only.
- Repository is github.com/kaltinril/ShadowDusk; the owner/operator is Jeremy Swartwood (GitHub `kaltinril`).
- Ships as eight NuGet packages (`ShadowDusk.{Core,HLSL,GLSL,ShaderToy,Compiler,Cli,Wasm,MgcbPlugin}`) at one shared version, plus the `ShadowDuskCLI` dotnet tool.
- `ShadowDusk.Metal` is a stub, not a shipped package.
- `ShadowDusk.MgcbPlugin` is the MGCB content-processor delivery shape (Phase 29), and it is the ONLY project allowed to reference MonoGame: the `ContentImporter`/`ContentProcessor` contract IS the plugin seam. That reference is `IncludeAssets="compile" PrivateAssets="all"`, so no MonoGame assembly ships beside it and no MonoGame dependency edge reaches a consumer; `NoMonoGameInProductLibrariesTests` exempts this one project by name and pins those two attributes.
- The `ShadowDusk.MgcbPlugin` package is **tools-only**: no `lib/`, everything under `tools/net8.0/any/` (~81 MB, the pinned DXC/SPIRV-Cross/vkd3d natives for every RID). MGCB's `/reference:` takes a path to an assembly and resolves that assembly's dependencies from its own directory, so the plugin and everything it needs must sit in one directory a consumer can point at. It is `DevelopmentDependency`, packs with `SuppressDependenciesWhenPacking`, and is packed **without** `-p:IncludeSymbols` (a package with no build output fails `NU5017` trying to build a `.snupkg`).

## The drop-in contract

- Drop-in means the whole `mgfxc` surface: same CLI flags, same `.mgfx` output format, same exit codes, and stderr diagnostics in a format MGCB can parse.
- MGCB compiles `.fx` **in-process** and never launches an external `mgfxc`, so a PATH-based `mgfxc` override does not route a `.mgcb` build through ShadowDusk. Measured 2026-07-28 against `dotnet mgcb` 3.8.2.1105, 3.8.4.1, and 3.8.5 (a logging `mgfxc.exe` first on `PATH`: zero invocations, valid `.xnb` each time); no `mgcb`/`Content.Pipeline` assembly in any of the three references `mgfxc` or `MGFXC_WINE_PATH`. Native MGCB integration is the **`ShadowDusk.MgcbPlugin` content-processor plugin** (Phase 29, 2026-07-31); the CLI-plus-`/copy:` route and runtime compilation still work and remain documented.
- MGCB DOES load a `/reference:`d plugin assembly by reflection (`Assembly.LoadFrom` + attribute scan for `[ContentImporter]`/`[ContentProcessor]`), and MonoGame's own effect `ContentTypeWriter` serializes a plugin-produced `CompiledEffectContent` into a byte-identical `.xnb` envelope. Measured on `dotnet mgcb` 3.8.2.1105, 3.8.3, 3.8.4, 3.8.4.1, and 3.8.5. A plugin compiled against the `MonoGame.Framework.Content.Pipeline` **3.8.2.1105** contract loads into all of them (that version is a floor, not a pin).
- A plugin loaded into MGCB cannot find ShadowDusk's natives by any of the normal mechanisms: `AppContext.BaseDirectory` is MGCB's directory and `NATIVE_DLL_SEARCH_DIRECTORIES` comes from MGCB's `deps.json`. `ShadowDusk.MgcbPlugin`'s `PluginNativeLibraryResolver` hooks `AssemblyLoadContext.Default.ResolvingUnmanagedDll` (the last-resort hook, so it can never displace a native the normal loaders resolved) and probes its own install directory. Without it a real `.mgcb` build fails `SD0103 SPIRV-Cross native library not found`.
- `MonoGame.Framework.Content.Pipeline` 3.8.2.1105 declares **no dependency on `MonoGame.Framework`**, yet `ContentProcessorContext.TargetProfile` returns `GraphicsProfile` from it, so anything subclassing `ContentProcessorContext` must reference MonoGame.Framework itself. It also ships `mgfxc.dll` as a *contentFiles* asset, which is why `mgfxc` is present next to MGCB without ever being invoked.
- MonoGame 3.8.5 split `mgfxc` into its own `dotnet-mgfxc` tool package (it used to ship inside `dotnet-mgcb` and `dotnet-mgcb-editor-windows`), and moved MGCB's own effect compilation from SharpDX `D3DCompiler` to bundled DXC + MojoShader native tool packages. 3.8.5's new code-centric Content Builder is a C# project over `MonoGame.Framework.Content.Pipeline` and has no external-tool seam either.
- The CLI and the WASM library produce byte-identical output; only the invocation differs, and `IShaderCompiler` abstracts both.
- `dotnet publish -r <rid> --self-contained` must produce a working single-file CLI that bundles every native dependency.

## Packaging and WASM interop

- WASM interop uses `[JSImport]`/`[JSExport]` to reach WASM-compiled DXC, SPIRV-Cross, and vkd3d.
- `ShadowDusk.Wasm` is a self-registering Razor SDK package: a consumer needs only a `PackageReference`, no wiring.
- Central Package Management is on; third-party versions live in `Directory.Packages.props`, the ShadowDusk version in `Directory.Build.props`.

## Vocabulary

- Effect pass: a single vertex+pixel shader pair compiled to a `PassBlob`.
- Effect technique: one or more named passes; maps to MonoGame's `Technique`.
- Platform blob: the platform-specific compiled binary (DXBC, SPIR-V, DXIL, or MSL source).
- ShaderIR: ShadowDusk's internal representation between parsed HLSL and platform emission.
- Rung 4 / render-proven: the real-engine render proof. The full four-rung ladder is defined in CLAUDE.md.

## Targets, and what constrains them

> **Proof status is NOT recorded here.** How far each target is proven changes as evidence advances, so it has one home: `docs/validation-matrix.md` (with a cold-start summary table in CLAUDE.md). This section records only what constrains the targets, which does not change when a gate goes green.

- Shader model and output format per target: OpenGL SM3 GLSL, DirectX 11 SM5 DXBC, DirectX 12 SM6 DXIL, Vulkan SPIR-V, FNA SM1-3 fx_2_0.
- **`mgfxc` enforces a per-target floor on the `compile <target>` profile token, and the accepted sets are not derivable from the profile names.** Measured 2026-07-31 by sweeping every recognized profile through the pinned `mgfxc` (`dotnet-mgcb` 3.8.4.1). `DirectX_11` accepts **only** `{vs,ps}_4_0_level_9_1`, `_4_0_level_9_3`, `_4_0`, `_4_1`, `_5_0` — `_4_0_level_9_0` is refused, and so is **every SM6 profile**, so a `major >= 4` rule is wrong in both directions. `OpenGL` caps at SM 3.0; `Vulkan` requires exactly `*_6_0`. `DirectX_12`'s floor is **unmeasured** (its reference compiler is mgfxc 3.8.5, outside the golden-oracle pin). ShadowDusk enforces the DirectX one as `SD0015`; the OpenGL and Vulkan ones are open gaps (`docs/validation-matrix.md` §8.1).
- The stock MonoGame `#if OPENGL … #else …` header cannot serve ShadowDusk's FNA target: FNA's macro set is `{FNA, HLSL, SM3}` with no `OPENGL`, so it takes the `#else` (DirectX, SM4) arm while its `fx_2_0` output is capped at SM3. Gate on **`SM4`** instead when one header must serve DirectX + OpenGL + FNA; `SM4` is defined by MonoGame's own `DirectX_11` profile and by nothing else, verified against `mgfxc`. This is what `ShaderToyConverter` emits.
- The OpenGL feature ceiling is the consumer runtime's, not ours: MonoGame and KNI both still use MojoShader for GL, so an SD0210 rejection (vertex texture fetch, texture arrays) is a runtime constraint to respect, never a compiler gap to fix. The DirectX target has no such cap and emits the SM4/5 features the GL path refuses.
- KNI ships no Vulkan platform and no DirectX 12 platform, which is why those two targets are MonoGame-only.
- DirectX 12 output is host-dependent: DXIL validation and signing run through the Windows-only `dxil.dll`, so a non-Windows DX12 compile emits unsigned DXIL (warned `SD0214`) that retail D3D12 rejects at pipeline-state creation. DX12 is therefore excluded from the cross-host byte-identity manifest.
- KNI loads the same `.mgfx` as MonoGame; the only divergence is its HiDef profile, whose runtime converter rewrites `mgfxc`'s `#define ps_oC0 gl_FragColor` form and nothing else.
- FNA is proven against a different oracle: `fxc.exe /T fx_2_0`, not `mgfxc`.
- Reach and WebGL1 cannot do 3D textures or fragment LOD at all; that is a platform wall, not a gap to close.
- **Android's file system is CASE-SENSITIVE, and `OperatingSystem.IsLinux()` returns FALSE there** — so any `IsLinux() ? caseSensitive : caseInsensitive` shape is wrong on Android in the most misleading way possible (it compiles, it is quiet, and it is wrong only on the device). **macOS is not a safe "case-insensitive" answer either**: APFS can be formatted case-sensitive. Never derive file-system case behavior from the OS; ask the storage (`IIncludePathCanonicalizer` is the include path's answer). This bit the `#include` comparer for over a year (bug-hunt N17).

## Pins, natives, and supply chain

- The product's compatibility commitment is the **output format (MGFX v10)**, not a MonoGame version. No shipped `ShadowDusk.*` package depends on MonoGame at all, and no project that references the central `Directory.Packages.props` MonoGame version (3.8.2.1105) is even in `ShadowDusk.slnx` — that number is only the default the GL validation harnesses render against. MGFX v11 and KNIFX exist as additive opt-ins.
- The unchanged v10 output is render-proven across **seven consecutive MonoGame releases: 3.8.1.263, 3.8.1.303, 3.8.2.1105, 3.8.3, 3.8.4, 3.8.4.1, and 3.8.5 stable** — the same bytes, pixel-identical on every one (max delta 0 between runtimes), all within tolerance of the mgfxc goldens (`validation/ForwardCompat`, 70 renders, 2026-07-28). The opt-in v11 output is render-proven on 3.8.5 stable (`validation/MonoGameV11`).
- **3.8.1.263 is the measured floor.** MonoGame **3.8.0.1641 rejects** our v10 output with *"This MGFX effect seems to be for a newer release of MonoGame"* — its loader predates MGFX v10. That is a real MonoGame version boundary, not a ShadowDusk gap. Newer MonoGame releases are proven against, never pinned to.
- The golden-generation `mgfxc` is pinned to the `dotnet-mgcb` version in `.config/dotnet-tools.json` (3.8.4.1), and `tools/compile-fixtures.ps1` asserts the MGFX version byte of everything it writes. Never take "the newest mgfxc on the machine": mgfxc **3.8.5 emits MGFX v11**, and `dotnet-mgcb-editor-windows` 3.8.4.1's `mgfxc.exe` cannot run at all (packaged without `SharpDX.D3DCompiler.dll`). mgfxc 3.8.2.1105 and 3.8.4.1 each reproduce all 46 committed goldens byte-for-byte on OpenGL and DirectX_11.
- vkd3d-shader is pinned at 1.17 for all four desktop RIDs plus the WASM build. **Upstream has since shipped 1.18, 1.19, and 2.0** (checked 2026-07-28).
- **vkd3d "2.0" is a project-version bump, NOT an ABI break** — researched 2026-07-28 so nobody has to fear the major number. The libtool soname is unchanged: `-version-info` goes `16:0:15` (1.17) → `19:0:18` (2.0), and soname major = `current - age` = **1 in both**, so `libvkd3d-shader-1.dll` / `.so.1` / `.1.dylib` stay correct and `Vkd3dLoader` needs no change. `age` rising in lockstep with `current` is the "interfaces added, none removed or changed" signal. Our call surface is tiny and untouched (`vkd3d_shader_compile` with `compile_info` → `hlsl_source_info`, `Options = NULL`), and the new behaviour is opt-in: denormal modes and `CONST_GLOBAL_UNIFORMS` are compile options we do not pass, and the stricter `VKD3D_SHADER_API_2_0` failure modes only apply if we explicitly declare that API version, which we do not.
- The vkd3d 1.17 → 2.0 upgrade is scoped as **[Phase 56](plan/PHASE-56-vkd3d-shader-2.0-upgrade.md)**; that doc holds the full research, the task sequencing (upside-probe first), and the acceptance bar.
- **What a vkd3d bump would actually cost is OUTPUT CHURN, not compatibility.** 1.18-2.0 add a common-subexpression-elimination pass, a better register allocator, and output-write hoisting — the notes call the register work out as "particularly relevant for shader model 1-3 target profiles", i.e. exactly our FNA target — plus branch flattening and more constant folding. Every DirectX `.mgfx` and FNA `.fxb` byte would move, so it is a full goldens + byte-identity-manifest regeneration and a full render-gate re-proof, plus an emscripten rebuild of the WASM artifact. **There is real upside**, not just currency: the register-allocator work may lift the documented `SD0305` register-pressure rejections (BasicEffect/SkinnedEffect on FNA), and 2.0 adds SM2-3 loop support, `tex3Dbias`/`tex3Dlod`/`texCUBElod`, and `SV_ClipDistance`/`SV_CullDistance`.
- **Only two package families reach a consumer**: `Silk.NET.SPIRV.Cross.Native` (in `ShadowDusk.GLSL`) and `Vortice.*` (in `ShadowDusk.HLSL`). Everything else in `Directory.Packages.props` is test/validation/build-only and cannot affect shipped output — that is the line between a safe bump and a breaking one.
- **Dependency currency, audited 2026-07-28: zero vulnerable packages and zero deprecated-for-security packages** across every project (`dotnet list package --vulnerable --include-transitive`). Test tooling was brought current the same day (`xunit` 2.9.3, `xunit.runner.visualstudio` 3.1.5, `Microsoft.NET.Test.Sdk` 18.8.1, `coverlet.collector` 10.0.1, `docfx` 2.78.5; **`Apos.Shapes` was NOT bumped** — see below); the assertion library moved off `FluentAssertions` 7.2.2 to `Shouldly` 4.3.0 on 2026-07-30 (issue #171); `Silk.NET` 2.23.0 is already latest; GitHub Actions are all on current majors. xunit 2.x is flagged "Legacy" in favour of xunit.v3 — a framework migration, not a security issue.

## Where things run and get proven

- `validation/*` drivers are deliberately outside `ShadowDusk.slnx`, so `dotnet test` never runs them.
- The in-process OpenGL render gates run in CI on Linux via Mesa llvmpipe (`validation-render.yml`); the KNI WebGL smoke runs in `wasm.yml`.
- CI's browser smoke renders on SwiftShader, which is structurally blind to ANGLE-D3D11 behavior such as the issue-#136 gradient poisoning. (This is *why* the ANGLE probe in the local gate cannot move to CI.)
- The integration lane runs automatically on pushes to `main` but on PRs only when the `run-integration` label is applied.
- Slow `ShadowDusk.Integration.Tests` runs are environmental (antivirus scanning cold native binaries), not algorithmic; `--settings ShadowDusk.runsettings` gives a 5-minute session backstop.
- Publishing is driven by the `NUGET_API_KEY` repository secret; no credentials live in the repo.
- The Phase-41 structural-divergence appendix stays outside `plan/DONE/` because `dotnet test` regenerates it on every run; diffing it across a change is the cheapest oracle for an unintended `.mgfx` structural change.
- `SamplerReflection.TextureName` is never assigned by any reflection backend; it is always null, so any texture/sampler pairing must key on bind slot or fall back to the sole shared sampler.
- SPIRV-Cross's `build_combined_image_samplers` declares one GLSL sampler per (texture, sampler) PAIR, and `MonoGameGlslRewriter` numbers those `ps_s{k}` in declaration order; neither the reflected texture list nor the reflected sampler list is that pair list. `SpirvCombinedSamplerPairs` derives it, in order, from the SPIR-V.
- That declaration order is **first-use order, deduplicated** — not HLSL declaration order, not bind-slot order. The trigger is `OpSampledImage` during a walk of the entry-point function's blocks in binary order, recursing into `OpFunctionCall` with a parameter remapping; the synthesized variable ids come from `increase_bound_by(2)` so they sort after every original id, and the GLSL emitter walks variables in id order while skipping every separate image/sampler. Read from the pinned SPIRV-Cross tree in `.wasm-build/spirv-cross-src` (tag `vulkan-sdk-1.4.335.0`, the same tree the WASM module is built from), then confirmed against real output with dimension-tagged probes.
- SPIRV-Cross's readable `SPIRV_Cross_Combined<Image><Sampler>` name is applied by its **command-line tool**, not by `build_combined_image_samplers`, so through the C API the combined uniforms arrive as bare `_<id>` (`uniform sampler2D _40;`) carrying no pair identity. The emitted GLSL therefore cannot be used to recover which pair a declaration is.
- **`mgfxc` numbers `ps_s{k}` by SAMPLER REGISTER; SPIRV-Cross numbers combined samplers by FIRST USE.** They coincide whenever use order matches register order, which is why the whole corpus is unaffected, but they diverge when it does not: for `SamplerPairMirror.fx` (`LinearSampler` at `s0`, sampled second) `mgfxc`'s golden makes `ps_s0` the Linear pair while ours makes it the Point pair. ShadowDusk must follow SPIRV-Cross, because the record has to name the uniform *our own* GLSL declares. Each build is internally consistent, so the renumbering is invisible in the picture — proven at **maxd 0** by `validation/SamplerPairsGl` arm B, which exists specifically to hold that claim. This is the "behaviorally equivalent, not byte-identical" bar working as intended. Note the pre-A7 GL table numbered by register (like `mgfxc`) while the GLSL was SPIRV-Cross-ordered, i.e. it was internally *inconsistent* — that was the bug.
- `mgfxc` bakes sampler state from a legacy `sampler2D X = sampler_state { … }` block but **not** from a modern `SamplerState X { MinFilter = …; }` block with D3D9 state names (fxc maps D3D10-style names such as `Filter` there). ShadowDusk bakes both, so the modern-block spelling is a real ShadowDusk-vs-`mgfxc` divergence on baked state. Corpus fixtures that need baked state must use `sampler_state` (as `SamplerStatesFull.fx` and `SamplerPairMirror.fx` do) or they diverge from their own golden.
- On the GL path there is no legacy/pre-combined sampler case to model: the pre-parser's `RewriteToSm4` mode (every target except FNA) rewrites `sampler2D`/`tex2D` into `SamplerState` + `<texture>.Sample(...)` before DXC sees the source, and SM6 HLSL has no combined sampler type, so every emitted GLSL sampler uniform is a synthesized pair.
- MonoGame binds a sampler's texture through the record's `Parameter` **index**, never its name (`EffectPass.SetShaderSamplers` does `_effect.Parameters[sampler.parameter]`). The record's `Name` matters only on GL, where it must match the GLSL uniform for `glGetUniformLocation`.
- `SpriteBatch` forces the sprite texture onto texture unit 0 **after** `EffectPass.Apply()` (`SpriteBatcher.FlushVertexArray` assigns `_device.Textures[0] = texture` immediately after `pass.Apply()`), so a PS-only render harness can only test units 1+ through effect parameters.
- `docfx/images/pipeline-overview.svg` is regenerated by `tools/render-diagrams.{ps1,sh}`, which downloads and SHA-256-verifies a pinned PlantUML jar into `tools/plantuml/`; the site embeds the SVG, never the `.puml`.

## Consumers and stakeholders

- External users drive a large share of the backlog: vchelaru (Gum, FlatRedBall, XnaFiddle) and Apostolique (Apos.Shapes) file issues that become phases.
- Gum's and Apos.Shapes' real shaders are vendored verbatim (both MIT) as compile-level regression fixtures.
- Apos.Shapes 0.7.7 serves as both harness and golden for the shape-gallery render proof, via its effect-injection `ShapeBatch` constructor. **That pin is evidence, not currency**: the baseline arm is only a valid comparison because 0.7.7's embedded effect *is* the vendored `apos-shapes-sm6.fx` (upstream commit `a85a31c`, identical modulo one comment). Checked 2026-07-28 — **0.7.12 pins a different commit (`b69bd73`) whose shader differs by ~1150 lines and adds a fourth sampler** (`ArcTex` at `t2`, pushing `BlueNoiseTex` to `t3`), so bumping it points the baseline arm at a different shader than the candidate. Moving it requires vendoring the new revision and re-running the Phase 55 proof.
- The security trust model is stated in `SECURITY.md`: the shader author and the compiler-runner are the same trust domain.

## Known upstream bugs we live with (not ours)

- MonoGame's Vulkan runtime has a `SlotOffset` byte-wrap bug that crashes on `mgfxc`'s own auto-numbered output, blocking the Vulkan pixel diff for auto-numbered resources (effects using explicit registers already diff pixel-for-pixel).
- `mgfxc` + MonoGame GL mis-handles statically-partially-read uniform arrays (MojoShader register compaction); we deliberately emit the correct full layout instead.
- `mgfxc`'s own GL compile of the current Apos.Shapes revision renders solid black, so GL has no trustworthy golden for that shader.

## Known gaps in our own reach

- The Linux and macOS Vortice DXC builds reject `tex3D`, `tex2Dlod`, and `tex2Dgrad` family intrinsics that the Windows DXC accepts; `Phase34TextureBreadthTests` is Windows-only for that reason.
- **DirectX 12 renders the Apos.Shapes gallery at maxd 1 on 11 pixels of 402,984 against the real `mgfxc` `DirectX_12` golden, and that is the DXC PIN, not a defect** (root-caused 2026-07-31). We compile DXIL with `dxcoob 1.7.2212.40 (e043f4a12)`; the golden was built with MonoGame 3.8.5's bundled `dxcoob 1.8.2505.32 (b106a961d)`. Our own pre-parsed HLSL and our own flags, put through a DXC 1.8 build, reproduce the golden's DXIL instruction-for-instruction and render at maxd 0 with zero differing pixels, so nothing on our side of the DXC seam differs. It shows up at all only because the shader adds ±half an 8-bit LSB of dither right before quantization, so a sub-ULP difference flips whichever pixels sit on the rounding boundary; that is also why the affected pixel set moves between builds. **maxd 1 is the honest DX12 tolerance until the DXC pin moves**, and moving it is a cross-target re-baseline, not a bug fix.
- Our DirectX 12 DXIL container carries a `STAT` part (and the HLSL identifier names) that the real `mgfxc` golden strips; behaviorally inert, one `-Qstrip_reflect` away, unfixed because it moves DX12 bytes. Phase 54's claim that both `RTS0` and `STAT` were removed is wrong about `STAT`.
- **Never trust a per-cell name from the Apos.Shapes gallery harness without checking it against the view transform.** The gallery renders through a 1.15x scale + (6,4) translate, so a shape in layout cell (3,3) lands in screen cell (4,4); `AposGalleryRenderer.Cells` used the untransformed rectangles until 2026-07-31 and mislabelled every divergence it reported. The same transform, against a target sized to the untransformed layout, also clipped 10 of the 30 cells off-screen entirely while the visibility check still read 30/30. Both are fixed; the lesson is that a diagnostic label is evidence only once it has been checked.
- GL macro-defined techniques (Phase 41 GAP-1, GL half) remain blocked on DXC legacy-SM2 codegen.
- `spirv-cross.wasm` exports exactly 11 `spvc_*` functions and is an out-of-band emscripten build, so any new SPIRV-Cross C API used on the desktop path (e.g. `spvc_compiler_get_combined_image_samplers`) would break the CLI-vs-WASM byte-identity promise until that module is rebuilt.
- ShadowDusk's OpenGL texture parameter keeps the plain texture name (`DiffuseMap`) where `mgfxc`'s own OpenGL goldens use MojoShader's `<sampler>+<texture>` spelling (`TextureSampler+DiffuseMap`) for every modern-syntax shader. Deliberate and behaviorally equivalent (MonoGame binds by parameter index, not name) — see `project_decisions.md`.
- DirectX 12 writes the GL-style positional `ps_s{k}` into the sampler record's name field where real `mgfxc` writes the HLSL sampler name (`SpriteTextureSampler`). Harmless (DX12 binds through the resource table) and rung-4 proven in that form, but a real divergence from the golden; changing it needs its own DX12 render re-proof.
- One texture read through two `SamplerState`s with different filters produces the correct records but **cannot be distinguished by a render** in MonoGame 3.8.2's GL backend: it has no GL sampler objects and applies filtering with `glTexParameteri` on the bound **texture** object, so both units get whichever filter was applied last. Measured 2026-07-29 (both channels equal, and they flipped together when the pair order was reversed). A runtime limitation that applies equally to `mgfxc`'s output; `validation/SamplerPairsGl` arm B uses two distinct textures for that reason.
- On DirectX and DirectX 12 the same shape (one texture, two `SamplerState`s) emits one record, so only the slot-0 sampler's baked state is applied and the second sampler's state is dropped. Pre-existing, unchanged by Phase 51 A7, and not yet scoped.
