## How to read a cell (the evidence levels, in plain English)

Every cell is at one of these levels. "Proven" always means **compared to the official reference compiler
(`mgfxc` for MonoGame/KNI, `fxc /T fx_2_0` for FNA), same graphics backend, same scene.**

| Mark | Level | Plain meaning |
|---|---|---|
| ✅ | **Render-proven** | Actually rendered in the **real engine** and the picture matches the reference compiler, pixel-for-pixel. The strongest proof. |
| 🟦 | **Load-proven** | The real engine **loads** the output without error, but the rendered picture has not yet been compared. |
| 🟡 | **Compile-only** | ShadowDusk **produces well-formed output**, but no real engine has loaded or rendered it. |
| 🌐 | **Browser-proven (dated)** | Rendered in a real **browser** runtime (KNI WebGL / Blazor) and compared, but the proof predates a current engine version, treat as stale until re-run. |
| 🚫 | **Blocked** | No shipping runtime exists to validate against yet (e.g. KNI has no Vulkan; "modern GLSL" has no GL runtime). Not a defect, a dependency. |
| ⬛ | **Not implemented** | ShadowDusk does not target this yet. |
| — | **N/A** | The combination does not exist (e.g. FNA is not MGFX-versioned). |

> **Why most of the naive 3 x 4 x 4 x 4 cross-product is not real:** FNA uses one fx_2_0 `.fxb` for *all* its
> backends (not MGFX, not v10/v11). KNI ships no Vulkan, Metal, or DX12; FNA3D has no D3D12 backend.
> ShadowDusk has no Metal target yet; DX12 is now fully rung-4 proven (PS corpus + VS-driven, see
> §1). The tables below show only the **valid** combinations.

## 2. Shader format / version / graphics profile

> **Format roadmap (committed):** ShadowDusk will emit **v10 *and* v11 *and* KNIFX**, each a real, faithful
> output a consumer can select and use, not just v10 with a promise that newer runtimes still load it. v10
> stays the **default** because it loads on every MGFX-lineage runtime (the seamless baseline), but v11 and
> KNIFX are **first-class additive outputs** so consumers can use the newer containers' features (and take the
> bytes for their own runtime if they like). Forward-compatibility of v10 is a nice-to-have, **not** a reason
> to stop short of v11/KNIFX. The newer formats are opt-in or auto-selected from the target, **never a flag a
> consumer must set to get correct output** (the seamless rule still holds). **All three are now BUILT and
> render-proven (2026-06-14):** v10 (default, everywhere), **MGFX v11** (`MgfxVersion = 11`, render-proven in
> MonoGame 3.8.5), and **KNIFX v11** (`Container = Knifx`, render-proven in KNI 4.02). **The
> auto-select/override seam is now built too:** a closed `CapabilityProfile` set names each
> (runtime, format) contract, `CompilerOptions.Profile` (and CLI `--target-runtime`) selects one (a
> profile implies its backend), and `RuntimeProfileDetector` recommends a proven profile from the
> loaded framework assembly, all byte-identical when unset. A `ShaderFeatures` axis
> (`ShaderFeatureSupport.Validate`) **rejects loudly with `SD0201`** any shader that needs a capability
> no shipping runtime supports yet (e.g. vertex texture fetch / texture arrays on the GL/MojoShader
> path), so an unsupported feature fails at compile rather than silently mis-rendering. KNIFX
> `columnsActual` is now **validated
> against a KNIFXC golden** (full matrices match exactly; the partially-used-matrix divergence is
> render-safe, a storage-only difference, see the KNIFX spec).

## 3. OS coverage (where the proof actually ran)

ShadowDusk's **output bytes are OS-independent** (proven byte-identical on Windows/Linux/macOS by
`CrossHostByteIdentityTests`), so compiling is cross-OS-solved. What varies by OS is where a **render** was
actually run.

> **One carve-out: `DirectX12` output is host-dependent.** The byte-identity manifest covers
> `DirectX_Vkd3d`, `FNA`, and `OpenGL` only. DXIL validation/signing runs through the Windows-only
> `dxil.dll`, so a DX12 compile on Linux/macOS emits **unsigned** DXIL that retail D3D12 rejects at
> pipeline-state creation — a compile-time `SD0214` warning, not an error. DX12 content must be
> built on Windows until cross-platform signing ships (see §7).

## 5. How a cell advances (the workflow to turn 🟡/🟦 into ✅)

1. **Compile** the fixture to the target (already automated, see below).
2. **Load** it in the real engine (`new Effect(gd, bytes)` for MonoGame/KNI; FNA `Effect`).
3. **Render** a frame and pixel-compare to the reference compiler's output for the *same backend + scene*
   (tolerance is the established bar: max per-channel delta <= 1 for dyadic inputs).
4. Mark the cell ✅ with the date and the test/harness that proves it.

### 6.1 The reference-compiler (oracle) pin — do not let it float

Almost every row above is "vs the `mgfxc` golden", so **which `mgfxc` built the goldens is part of the
evidence.** Settled on measurement 2026-07-28 ([Phase 52](../plan/DONE/PHASE-52-monogame-3.8.5-support.md)
Area C): the committed goldens are canonical **MGFX v10**, and `tools/compile-fixtures.ps1` now resolves
mgfxc from the **`dotnet-mgcb` version pinned in `.config/dotnet-tools.json`** (3.8.4.1) and **asserts the
container version byte of everything it writes**, refusing to overwrite the corpus with a different one.

It used to take "the highest `mgfxc.exe` in the NuGet cache", which was wrong twice over:

- **mgfxc 3.8.5 emits MGFX v11**, not v10 (verified: version byte 11, every file 58-2232 bytes larger,
  **0 of 46 matched its golden** on either profile). Correct for a 3.8.5 consumer, useless as the v10 oracle.
- The **`dotnet-mgcb-editor-windows` 3.8.4.1** package ships `mgfxc.exe` **without
  `SharpDX.D3DCompiler.dll`**, so it throws on every shader — and that was exactly the binary the old probe
  selected, meaning a golden regeneration would have compiled **0/46** and reported them all as failures.

Verified equivalence behind the pin: mgfxc **3.8.2.1105** and **3.8.4.1** (from the intact `dotnet-mgcb`
payload) each reproduce **all 46 committed goldens byte-for-byte on both OpenGL and DirectX_11**, so the pin
is a floor-to-3.8.4.1 range, not a single magic build. `validation/ReservedWordGl` resolves its bonus mgfxc
arm through the same pin for the same reason. **Moving this pin means regenerating goldens deliberately,
with a recorded corpus diff.**

**The "test programmatically" goal:** the path to a fully self-checking matrix is (a) promote the
`validation/*` render gates into CI jobs (where a software/headless driver exists), and (b) back this matrix
with a machine-readable coverage manifest a test asserts against (so a cell cannot be marked ✅ without a
passing test). **(a) is now partly done (Phase 44 C + issue #204):** the **eight** in-process, self-asserting **GL** render
gates (`StateFidelity`, `CbufferModel`, `TextureBreadthValidation`, `ReservedWordGl`,
`SamplerPairsGl`, `DeferredSpriteMrtGl`, `ShaderToyRouteGl`) run in CI on ubuntu under
xvfb + Mesa llvmpipe via **`validation-render.yml`** (push-to-main + the `run-validation-render` PR label),
so a GL render regression turns the lane red. **Issue #204 (2026-09-10) closed most of the "no headless DX
driver" gap the same way**: a `windows-latest` job in the same workflow pins three DX gates to **WARP**
(Windows' bundled software D3D rasterizer, the same recipe `vchelaru/SkiaGameRendering`'s WindowsDX CI job
proved) — `DxModernFeatures`, `KniWinFormsDX`, and the `BaselineDx`+`CandidateDx` corpus — via an opt-in
`SHADOWDUSK_DX_WARP=1` env var (`validation/SharedDx/DxHeadlessRasterizer.cs` for MonoGame's static
`GraphicsAdapter.UseDriverType`; a local `PreparingDeviceSettings` hook in `KniWinFormsDX/Program.cs` for
KNI's per-device `PresentationParameters.UseDriverType`), so a developer's plain `dotnet run` still renders
on their real GPU. **The `BaselineDx12`+`CandidateDx12` DX12 corpus was also tried here and initially measured
RED**: `MonoGame.Framework.Native`'s SDL2 window creation requires a Vulkan surface regardless of the WARP
pin (compiled in, not a runtime flag — `native/monogame/sdl/MGP_sdl.cpp` unconditionally adds
`SDL_WINDOW_VULKAN` for any DX12 build), and `windows-latest` has no GPU, Vulkan loader, or Vulkan ICD at
all — a windowing precondition, not a D3D-rendering one, so WARP cannot route around it. **Fixed
([issue #209](https://github.com/kaltinril/ShadowDusk/issues/209), 2026-09-10)**: installing Google
SwiftShader (a CPU Vulkan ICD, via `jakoch/install-vulkan-sdk-action`) gives the runner both a Vulkan
loader (`vulkan-1.dll`, added to `PATH`) and a registered ICD, satisfying SDL's window-creation probe —
Vulkan is load-bearing only for that probe, WARP still does the actual D3D12 rendering. Measured green on a
real `windows-latest` run: maxd 0, 10/10. `VsDrivenDx`/`VsDrivenDx12` (the Apos.Shapes gallery) and
`ShaderToyRouteDx` stay manual — not because WARP or the SwiftShader fix fails for them, but because they
weren't the smallest first step; the fix should carry over to `VsDrivenDx12` (same SDL precondition) as a
follow-up. **Vulkan has its own lane since 2026-10-01**: a third job (`vulkan-render-gates`, ubuntu) renders
both Vulkan gates on real MonoGame DesktopVK (`MonoGame.Runtime.Linux.Vulkan`'s `libmgruntime.so`) through
Mesa **lavapipe** under xvfb, with the **Khronos validation layer** forced on by
`validation/run-with-vk-validation.sh`, so a layer error fails the gate even when the pixels match. Lavapipe on
ubuntu was picked over SwiftShader on `windows-latest` because it hosted DesktopVK on the first measured run
(VS-driven maxd 0, gallery maxd 0, PS corpus 10/10, zero layer errors or warnings) and needs only `apt`, not
the registry workarounds an elevated Windows runner forces on a non-SDK ICD. Two positive controls in the same
job prove it can fail (see the §6 row).

## 8. ShaderToy / GLSL frontend — a DISTINCT evidence axis (NOT `mgfxc`-equivalence)

`src/ShadowDusk.ShaderToy` (Phase 47) converts a single-pass ShaderToy / GLSL image shader to a
self-contained `.fx`, which the **existing, unchanged** pipeline then compiles. Its evidence bar is a
**separate rung from the headline `mgfxc`/`fxc`-equivalence bar** and must never be conflated with it:

- **There is NO `mgfxc` oracle for ShaderToy input** — a `.glsl` is not an `mgfxc` input, so there is
  nothing to be byte/render-equivalent *to* on the input side. The frontend's honest bar is
  **pixel-fidelity vs the ORIGINAL GLSL**: render the original ShaderToy GLSL in a raw GL context
  (ground truth) vs OUR converted `.fx`→`.mgfx` through MonoGame, diff per pixel. Phase 46's
  out-of-band `render-proof --fidelity` gate: **46/46 deterministic shaders match the original at mean
  0.00/255** (gallery 72/72). This driver stays out-of-band like `validation/*`.
- **The DOWNSTREAM half is unchanged.** Once the converter emits `.fx`, the `.fx`→`.mgfx`/`.fxb` step is
  the SAME faithful, `mgfxc`-equivalent pipeline proven by the existing corpus — the promotion changes
  neither bar (proven additive: existing `.fx` output byte-identical; converter is pure-managed, no
  native/MonoGame dep — guarded by `NoMonoGameInProductLibrariesTests`).
- **CLI `.glsl` route** (`ShadowDuskCLI shader.glsl out.mgfx /Profile:...`): backed by
  `CliShaderToyInputTest` (compile OpenGL/DX, located-reject error path, byte-identity CLI ≡
  Convert+pipeline).
- **The route is render-proven on OpenGL since 2026-07-29** (Phase 51 A5, `validation/ShaderToyRouteGl`,
  in CI). The oracle question above cuts finer than "no oracle exists": there is none for the

### 8.0 Slang input frontend — the same distinct axis (added 2026-08-13, Phase 61; reworked 2026-08-14)

`ShadowDusk.Compiler.Slang.SlangFrontend` (issue #198) accepts the **HLSL-compatible subset of
Slang** and produces `.fx` text for the **existing, unchanged** pipeline. It is a **pure managed
text transform** (owner direction 2026-08-13: no Slang toolchain shipped or invoked, anywhere):
entry points come from Slang's `[shader("vertex")]` / `[shader("fragment")]` attributes, the
technique is synthesized (Slang has no technique/pass concept), the attributes are stripped, and
the body — near-HLSL by Slang's own design — compiles through the same DXC as every `.fx`. The
same evidence rules as the ShaderToy axis apply:

- **There is NO `mgfxc` oracle for Slang input** — `mgfxc` cannot read Slang at all, so no route
  through this frontend is ever called `mgfxc`-equivalent. The claim is simpler: the generated
  `.fx` compiles through the same faithful pipeline as any other, to the same proven targets.
- **Proven today (compile-level):** the two-stage `Desaturate.slang` fixture (cbuffer, texture,
  matrix, VS+PS) converts and compiles to `.mgfx` on **OpenGL and DirectX**, with the decoded
  effect carrying exactly the user's parameter names verbatim (the body rides through untouched,
  so there is no name mangling to undo). `SlangRouteTests` — **ungated**, since the route needs
  only the natives every suite lane already has — plus 14 pure tests over the frontend.
- **The reject set:** Slang-only language features (`import`, `module`, `extension`,
  `associatedtype`, generics) → `SD0600` naming the construct; a stage no `Effect` can hold
  (compute/mesh/raytracing) → `SD0602`; no/ambiguous entry points → `SD0603`/`SD0604`. Nothing
  is silently narrowed; subtler Slang-isms fall through to DXC's own verbatim diagnostics.
- **The cross-compiler proof exists and is measured (2026-08-14):** a 17-shader corpus, every
  one accepted by the REAL pinned slangc (gate 1), and the 8-shader uniform-free procedural
  subset rendering **pixel-identical at maxd 0** through ShadowDusk's route vs through slangc's
  own HLSL emission (gate 2, same DXC/SPIRV-Cross downstream on both sides). See the §6 row
  (`validation/SlangCorpus`) for the mechanism. In-suite, all 17 convert + compile on OpenGL and
  DirectX (`SlangCorpusCompileTests`).
- **Not yet proven:** render equivalence for the uniform/texture-driven corpus members (the
  parameter-plumbing on the slangc side is what gate 2's subset design avoids — extending it
  means solving slangc's name mangling in the harness), and the FNA arm (modern-syntax bodies vs
  the SM2–3 fx_2_0 ceiling — the OQ2 target-reach limit, to be measured not assumed).

### 8.0a Full slangc-backed Slang input (`ShadowDusk.Slang`) — the real-compiler route (added 2026-09-11, Phase 66)

`ShadowDusk.Slang.SlangCompiler` is a NEW, separate, OPTIONAL package (the `ShadowDusk.ShaderToy`
precedent — zero size/dependency cost for a consumer who does not add it) for a consumer who
wants genuine Slang: `import`, generics, `interface` conformances — everything real slangc
accepts, none of which §8.0's HLSL-compatible-subset frontend can compile. The route is
`.slang → [real slangc, -target hlsl] → HLSL → [the SAME unchanged faithful DXC pipeline every
.fx uses]`. §8.0's subset frontend is untouched and stays the free, zero-toolchain default; this
is the opt-in complete answer, not a replacement.

- **There is still NO `mgfxc` oracle for Slang input** — same rule as §8.0, unchanged: no route
  through either Slang frontend is ever `mgfxc`-equivalent, and `.slang` is never a section 1 cell.
- **Real slangc rides IN the package**, not invoked as a test-time oracle, for **win-x64,
  linux-x64, osx-x64 and osx-arm64** (issue #227): the slangc executable + the slang-compiler
  library per RID, the measured minimal set (Phase 66 A1/A2 on win-x64; re-measured for the Unix
  RIDs: 24/24 entry points byte-identical to the unmodified release with only those two files,
  24/24 failing without the library), packed into `runtimes/<rid>/native/`. Host floors come from
  the upstream binaries: Linux needs `GLIBCXX_3.4.29` (Ubuntu 22.04+); macOS needs 26+ (the
  upstream `minos`), reported as `SD0620`. A consumer who does not add `ShadowDusk.Slang` pays
  zero size/dependency cost — the subset frontend above is unaffected. The `slang-llvm`
  exclusion is also measured structurally on every Unix binary (2026-10-01, ELF `DT_NEEDED` and
  Mach-O `LC_LOAD_DYLIB` read from the pinned release zips): nothing links it, and the pinned
  Linux zip does not ship it. **linux-arm64 and win-arm64 are not bundled** although upstream
  publishes them: the core pipeline is incomplete there (linux-arm64: no DXC, no vkd3d;
  win-arm64: no vkd3d, unproven), so those hosts get `SD0620`
  (`project_decisions.md`).
- **Cross-host byte identity (issue #227):** `SlangCrossHostByteIdentityTests` pins, per corpus
  shader, the assembled `.fx` text (slangc's own emission) and the OpenGL + DirectX_Vkd3d `.mgfx`
  bytes in `tests/fixtures/golden/byte-identity/slang-manifest.json` (generated on osx-arm64) and
  asserts it on every CI OS. osx-arm64 and osx-x64 (Rosetta) slangc emit byte-identical HLSL for
  all 24 entry points (measured 2026-10-01). This is what transfers gate 3's Windows-only real
  `Effect` load to Linux and macOS.
- **The three-band accept/reject rule (Phase 66 A5):** slangc's own syntax errors surface
  verbatim (band 1); a non-VS/PS entry stage (`SD0602`) or an SM6-only Wave/Quad intrinsic on a
  target whose backend cannot represent SM6 HLSL (`SD0624`) reject loudly by name (band 2);
  everything else compiles, no curated allow-list (band 3).
- **Name mangling and the OpenGL `layout(row_major)` gap are both closed (Phase 66 A4):**
  `-no-mangle` keeps every symbol that feeds a consumer's reflected parameter table (cbuffer
  names/members, texture/sampler declarations) at the author's original spelling; stripping
  slangc's own redundant `#pragma pack_matrix(column_major)` restores OpenGL's existing
  row-major convention. The shipped 21-shader corpus (the 17-shader `tests/fixtures/shaders/slang/`
  set + 4 Phase 65 Gum/generics-probe shaders) is 21/21 on both DirectX_11 and OpenGL.
- **Generic instantiation and MonoGame's own effects (issues #228, #231, measured 2026-10-01 on
  osx-arm64 slangc 2026.14.1):** `-no-mangle` is collision-free inside one entry point, but
  slangc numbers symbols per entry in first-use order, so entries that instantiate one generic
  differently collided on a name. `SlangHlslMerger` renames the later unit's colliding
  structs/functions/statics and rejects an unrenamable cbuffer/resource collision (`SD0625`);
  `SlangGenericsCollisionTests` compiles four adversarial fixtures
  (`tests/fixtures/shaders/slang-adversarial/`) on all five targets and proves each entry's call
  graph matches its own slangc output. MonoGame v3.8.5's `Macros.fxh` effects (6 files, 66
  entries) compile 0/66: `technique`, then the legacy `sampler` type. They are `.fx` input and
  the Slang route rejects them (`SD0626`); `SlangMonoGameEffectsTests` pins the measurement,
  including the control that all 66 compile once those two constructs are removed.
- **Platform macros are forwarded to slangc's own preprocessor (Phase 66 A6):** the same
  `OPENGL`/`SM4`/`VULKAN`/`SM6`/`HLSL`/`GLSL`/`MGFX`/`FNA`/`SM3`/`__KNIFX__` set the ordinary
  `.fx` route already defines, found via a 15-fixture residue sweep across 5 targets that
  surfaced a real, general platform-macro-forwarding gap (fixed, not a per-shader workaround).
- **The cross-compiler render proof (Phase 66 A7, measured 2026-09-11):** `validation/SlangFullCorpus`
  — a distinct driver from `validation/SlangCorpus` (§8.0's gate; that one stays validating ONLY
  the subset frontend). Compile sweep: the 21-shader corpus through the REAL `SlangCompiler` on
  all four reachable targets, **84/84 (OpenGL/DirectX_11/DirectX_12/Vulkan, FNA excluded to match
  §8.0's own precedent)**. Pixel equivalence (OpenGL, the 8-shader uniform-free procedural
  subset): ShadowDusk's `.fx`-wrapped route vs the exact same slangc invocation `SlangCompiler`
  uses internally, fed straight to DXC with no wrapping — **maxd 0**, proving the wrapping/macro
  pipeline itself is pixel-preserving. Real engine load (DirectX_11): all 21 shaders load into a
  REAL `MonoGame.Framework.WindowsDX` `Effect` and render — **21/21 loaded, 21/21 rendered**. See
  the §6 row for the full mechanism. The DirectX_12/Vulkan/FNA real-Effect arms followed in
  issue #230 (below).
- **Textured shaders on OpenGL, rendered in real MonoGame DesktopGL (issue #252, 2026-10-01):**
  `validation/SlangTexturedGl`. slangc numbers every texture/sampler itself
  (`SamplerState S : register(s0)`), which the GL sampler allocator reads as an author
  reservation (mgfxc's own rule, issue #189), so every textured Slang shader landed on `ps_s1`
  and SpriteBatch's unit-0 texture never reached it. `SlangCompiler` now strips slangc's own
  texture/sampler registers and keeps only the ones the author wrote; all six textured PS-only
  corpus shaders render on unit 0 (Invert maxd 0 vs the `mgfxc` golden of the equivalent `.fx`).
  "The author wrote" is read from slangc's own preprocess-only output (`slangc -E`, the compile's
  macros), so a register in an inactive `#if` branch does not count and one written through a
  macro does (follow-up, 2026-10-01; `SlangGlSamplerSlotTests` pins both shapes on OpenGL and
  DirectX against the hand-resolved declarations on both routes, and `mgfxc` 3.8.4.1 measured on
  the same shapes agrees). **Issue #302 (2026-10-02):** the texture slangc hoists out of a combined
  `Sampler2D Comb` (emitted `Comb_texture_0`) reaches the effect as `Comb`, the name the author
  wrote and the name the hand-written `Texture2D Comb; SamplerState ...` reflects through the `.fx`
  route on every target (measured; `mgfxc` names the legacy `sampler2D Comb`'s parameter `Comb`
  too). A texture hoisted out of a struct, a cbuffer/ParameterBlock or an entry-point uniform has
  no author-written name and fails as `SD0640` (fxc rejects a texture in a struct, `X3090`,
  measured through `mgfxc`). The eighth `SlangTexturedGl` row sets the texture by
  `effect.Parameters["Comb"]` in real DesktopGL and renders (maxd 1); `SlangHoistedTextureNameTests`
  pins the table on DirectX, OpenGL, Vulkan, DirectX12 and FNA.
- **The browser, in-process (issue #257, Phase 67, 2026-10-01):** `ShadowDusk.Slang.Wasm` runs the same pinned slangc in the page as WebAssembly, linked from upstream's own prebuilt wasm libraries behind a glue that replays slangc's `innerMain`, and plugs it into `SlangCompiler` through an internal seam, so the argument list, register strip, merge, `.fx` assembly and downstream pipeline are the desktop route's own code. Upstream's own `slang-wasm.js` was measured unusable for this (its session API takes no flags or macros; 0/20 corpus entries matched native slangc). The module matches native slangc 235/235 (every corpus, entry and target), and in real headless Chromium the corpus compiles to the manifest's bytes 42/42 and renders maxd 0 in KNI WebGL against the subset route. Not a package yet, and Android is open (§7).
- **DirectX_12, Vulkan and FNA in the real engine vs the reference compiler (issue #230,

  `validation/FnaValidation -- slang`. Each compiles the 21-shader corpus through `SlangCompiler`,
  captures the assembled `.fx` the route handed the pipeline, compiles that same text with the

### 8.0b SkSL converter (SkiaSharp) — the image-fidelity axis (added 2026-08-13, Phase 62)

`ShadowDusk.Compiler.Sksl.SkslConverter` (issue #197) converts a pixel-only `.fx` to an SkSL
runtime effect at the pre-rewriter seam (`HLSL → DXC → SPIR-V → SPIRV-Cross → GLSL → mapper`).
Its evidence model was set by owner decision (2026-08-13, `project_decisions.md`):
**rendered-image fidelity, never `mgfxc`-equivalence** — Skia has no reference compiler, and
`.sksl` is never a §1 cell.

- **Proven today:** Skia's own compiler (`SKRuntimeEffect.CreateShader`) accepts the emissions
  with zero errors, and real CPU-raster renders match the **original HLSL's analytically
  computed math** at ±2/255 (SkSL `half` precision — the tolerance is stated, not assumed), with
  a positive control pinning that the known silent-loss failure (Gum's own hand port drops its
  `COLOR0` tint) is measurably absent. `SkslConverterTests` + `SkslSkiaEvidenceTests` (SkiaSharp
  is a test-only dependency; runs in the ordinary suite, no GPU).
- **The reject set is the load-bearing half** (`SD0610`–`SD0615`): no varyings, no vertex stage,
  no derivatives, no computed-UV sampling, no multi-pass — each refused by name, never silently
  narrowed. The default answer to a shader reading an interpolant is refusal with a documented
  opt-in (`TreatVaryingsAsUniforms`). A legacy sampler an `#include` or a macro supplies converts
  through the issue #308 recovery, to exactly the direct declaration's output (issue #327,
  `SkslConverterLegacySamplerRecoveryTests`); MonoGame's own `Grayscale.fx` is the real case.
- **Not yet standing:** a cross-renderer harness diffing the same shader through the proven GL
  backend vs through Skia (the analytic-expectation tests cover the shipped conversions; the GL
  comparison is the stronger general form), and a real Gum/SkiaGum consumer trial.

### 8.0c raylib converter (Raylib-cs) — the image-fidelity axis (added 2026-10-01, Phase 59)

`ShadowDusk.Compiler.Raylib.RaylibConverter` converts a single-pass, pixel-only `.fx` to a raylib
`glsl330` fragment shader at the same pre-rewriter seam the SkSL converter uses. Its evidence model
was set by owner decision (2026-10-01, `project_decisions.md`, the SkSL decision's model):
**rendered-image fidelity, never `mgfxc`-equivalence** (raylib has no reference compiler), so it is
never a §1 cell.

- **Proven today (2026-10-01, Raylib-cs 8.1.0 / raylib 6.0):** `validation/RaylibRoute` (§6) renders
  15 shaders in real Raylib-cs and pixel-diffs each against the same `.fx` built for OpenGL and
  rendered in real MonoGame DesktopGL: **13/13 at maxd 0** on macOS (Apple GL 4.1 core) and on
  Linux CI (Mesa llvmpipe, `validation-render.yml`, PR #239), and **15/15 at maxd 0** on Windows
  (2026-10-02, issue #327: the `LegacyInclude` / `LegacyMacroDecl` arms, whose legacy samplers an
  `#include` or a macro supplies, joined that day), tolerance
  ±2/255 (stated, non-zero: two runtimes, two GLSL dialects of the same SPIR-V). Positive controls,
  all caught: dropped tint maxd 44 (16073 px over), flipped V maxd 255 (16384 px), curvature +0.01
  maxd 43 (8349 px; 44 and 8400 on llvmpipe).
- **The interface mapping is the claim:** `TEXCOORD0` ↔ `fragTexCoord`, `COLOR0` ↔ `fragColor`
  (SpriteBatch's tint and raylib's draw tint are the same varying, unlike SkSL which has none), the
  unit-0 sampler ↔ `texture0` (the same declaration-order allocator the GL target uses, issue #189).
- **The reject set** (`SD0630`–`SD0636`) is pinned by `RaylibConverterTests` with locations where
  the source has one. A legacy sampler an `#include` or a macro supplies converts through the

  `RaylibConverterLegacySamplerRecoveryTests`). Y-orientation-dependent constructs (`SV_Position`, `ddy`) are refused because
  MonoGame and raylib flip render targets in opposite directions.
- **Not proven:** `glsl100` (not emitted, §7), Windows/NVIDIA/AMD drivers (measured only on Apple GL
  and llvmpipe), and a real consumer trial (the Phase 59 requester).

### 8.1 Reject-fidelity: mgfxc's per-target compile-profile floor (measured 2026-07-31)

Every `KnownProfiles` entry was swept through the **pinned** `mgfxc` (`dotnet-mgcb` 3.8.4.1 —
§6.1's oracle pin) for each of its three profiles. This is the authoritative record of what the
reference compiler accepts, and of how much of it ShadowDusk enforces today.

| mgfxc profile | Accepts | Rejects, with | Enforced by ShadowDusk? |
|---|---|---|---|
| `DirectX_11` | `{vs,ps}_4_0_level_9_1`, `_level_9_3`, `_4_0`, `_4_1`, `_5_0` | *"Invalid profile 'X'. Vertex/Pixel shader 'E' must be SM 4.0 level 9.1 or higher!"* — **including `_level_9_0` and every SM6 profile** | ✅ **yes** — `SD0015` (Phase 51 A10) |
| `OpenGL` | SM ≤ 3 (`{vs,ps}_1_1`…`_3_0`, `_3_sw`; `ps_1_x` is refused by fxc itself) | *"Invalid profile 'X'. Vertex shader 'E' must be SM 3.0 or lower!"* for `_4_0`/`_4_1`/`_5_0`; the `_4_0_level_9_*` forms die later inside MojoShader/fxc instead | ❌ **gap** — ShadowDusk still accepts SM4+ on OpenGL |
| `Vulkan` | `vs_6_0` / `ps_6_0` only | *"Invalid Vulkan vertex profile 'X'! Requires vs_6_0."* | ❌ **gap** — ShadowDusk accepts any recognized profile on Vulkan |
| `DirectX_12` | **not measured** — it exists only in mgfxc **3.8.5**, which is not the pinned golden oracle and is not installed here | — | ❌ **unmeasured**, deliberately not guessed |

The two open gaps are the same class as `SD0015` and each carries its own reject-set blast radius,
so each needs its own corpus sweep before it lands. For scale, measured at the same time: enforcing
the **OpenGL** ceiling would newly reject 7 root fixtures (`Minimal.fx`, `cbuffer.fx`, `textured.fx`,
`multipass.fx`, `multitechnique.fx`, `platform-macros.fx`, `basiceffect-mini.fx`), every one of which
real `mgfxc /Profile:OpenGL` already refuses.
