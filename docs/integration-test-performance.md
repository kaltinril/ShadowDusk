# Integration-test performance (Phase 21)

> Linked from [`CLAUDE.md`](../CLAUDE.md) → *Build & Test*. Read this if an integration-test
> run is mysteriously slow or hangs.

`ShadowDusk.Integration.Tests` is the only project that touches heavyweight external machinery (CLI child-process spawn, native DXC + SPIRV-Cross). If a full run is intermittently very slow (one outlier hit **21m43s** vs the usual single-digit seconds), the cause is **environmental, not algorithmic** — the test logic is identical:

- **Antivirus / Defender on-access scanning** of freshly-built native binaries (`dxcompiler.dll`, SPIRV-Cross) and just-spawned executables is the prime suspect (warm cache → seconds; cold → minutes). **Dev-time mitigation:** add the repo's `**/bin`, `**/obj`, `tools/`, and the test `%TEMP%` paths to the Defender exclusion list (do **not** disable AV globally). Phase 30 CI should account for this.
- `CliBinaryFixture` now **reuses the CLI binary from the normal build** (the test project has a `ReferenceOutputAssembly=false` ProjectReference to `ShadowDusk.Cli`) instead of running a per-run `dotnet publish -c Release` into a fresh temp dir — that nested cold-Release build + fresh native-binary copy was the dominant structural cost.
- **Suite-level timeout guardrail:** pass `--settings ShadowDusk.runsettings` to `dotnet test` (repo-root file) to apply a 5-minute `TestSessionTimeout`. If the suite ever hangs again it now fails fast in bounded time instead of silently eating 20+ minutes. Per-test `CancellationTokenSource` timeouts (30 s/60 s/120 s) bound only managed work: none can interrupt a native compile, so CI's integration step also passes `--blame-hang-timeout 3m`, which kills a hung test host and dumps its threads (artifact `integration-hang-dumps-<os>`). The session cap is the backstop, and it leaves no dump, so CI's integration step raises it to 10 minutes inline (`-- RunConfiguration.TestSessionTimeout=600000`): the blame timer is reset by every test that starts or finishes, so it fires 3 minutes after the *last* test event, and a 5-minute cap pre-empted it whenever a stall began late in the run (issue #312; `CiHangGuardTests` enforces `session >= healthy run + blame timeout + dump time`). The unit lanes keep the file's 5 minutes.
- **Child processes go through one helper** (`tests/ShadowDusk.Integration.Tests/ChildProcess.cs`, issue #316). It drains stdout and stderr concurrently, and on timeout kills the process tree and fails with the elapsed time, the command line, the child's CPU time and thread states, the output so far, and for .NET children a dump taken before the kill (`MiniDumpWriteDump` on Windows, where `createdump.exe` refuses a pid; `createdump` plus gdb or `sample` elsewhere), written under `SHADOWDUSK_HANG_DUMP_DIR` and uploaded with the hang dumps. Read a timeout message before assuming a hang: CPU time near zero means the child was blocked, CPU time near the elapsed time means it was busy or starved, and "the deadline was noticed N s late" means the test host itself could not run.
- **A stalled run names its tests.** `xunit.runner.json` (`longRunningTestSeconds: 60`) makes xUnit print `[Long Running Test] 'Name', Elapsed: ...` for every test in flight for over a minute, so even a run that dies without a dump says what it was holding.
- **A sidecar dumps a stalled host from outside (issue #312).** `--blame-hang-timeout` cannot dump every stall: its timer is reset by every test that starts or finishes, so a few frozen tests among a running suite never trip it, and when it fires VSTest asks the runtime to dump itself, which the runtime does by `fork()`ing `createdump` inside the hung process (measured deadlocked on the same lock as the stall it was meant to capture). CI's integration job on macOS and Linux therefore starts `tools/ci/hang-watchdog.sh` as a separate shell process before `dotnet test`; after 5 minutes it takes lldb/gdb stacks of every thread, a `sample` on macOS, the Linux kernel wait channels and a `createdump --withheap` of every test host still running, then a second stack snapshot 45 s later (a frozen thread shows the same frames), into `TestResults/hang-dumps/`, which the `integration-hang-dumps-<os>` artifact uploads; a dump is also analyzed on the runner with `dotnet-dump analyze` (`threads`, `clrstack -all`, `syncblk`) into `host-<pid>-managed.txt`, since a macOS dump cannot be opened on a Windows box. The host itself also writes `host-hint-<assembly>-<pid>.txt` under `TestResults/probe-hangs/` once a minute after three minutes of uptime (thread counts and `DxcForkGate`'s reader/writer state, nothing spawned). A healthy run logs `nothing to capture`.
